# The window's views — files, gallery, journal, thoughts (v4)

**Status:** concept, 2026-11-17, at the owner's request. **v4.1 shipped (4.1.0); v4.2 shipped (4.2.0); v4.3 shipped
(4.3.0); v4.4 built** (State, Schedule, a reply's tools in the details panel). Placed by the owner as **v4** in the
[ROADMAP](../ROADMAP.md) (§v4.1–v4.5); the later versions moved up by one. The owner's decisions are in
[§Decisions](#decisions-the-owner-2026-11-17). The design brief for Claude Design is
[design/v4/BRIEF.md](../../design/v4/BRIEF.md). The design itself (2026-11-17) is the handoff in
[design/v4/handoff/](../../design/v4/handoff/README.md). Its additions and the corrections made after the export are
listed at the end of the brief.

## Why

Since v2.5 her tools run in the server process on the box. What they produce stays in her data root there, and the
owner has no way to look at it from the Mac short of SSH:

- **files:** her per-user sandbox (`/data/files/owner/` in the container, `~/lumi/prod/data/files/owner/` on the box);
- **pictures:** generated by `generate_image` into `art/`, or put there otherwise;
- **journal:** the diary in `/data/journal/owner/`;
- **thoughts:** the thought stream in the store.

The desktop window (v2.12, `Lili.app`) shows only the chat and her portrait. `/journal` and `/thoughts` are text
commands, and the window's thought strip holds only the thoughts pushed during the current session.

v4 adds **read-only views** of that data to the window, and the read-only server routes they need:
- Files, with a markdown reader;
- Gallery;
- Journal;
- Thoughts;
- State;
- Schedule.

It also shows her pictures in the chat and a turn's tool calls. **Actions** (upload, "show this to her", download,
maybe delete) come last, in v4.5.

## Decisions (the owner, 2026-11-17)

1. **The window only.** The TUI gets nothing new; it keeps `/journal` and `/thoughts`.
2. **Read-only first, actions later.** v4.1–v4.4 only read. The actions are v4.5, chosen before it starts.
3. **A markdown reader** for reading her files, not only a file list (§The markdown reader).
4. **Every addition is in:** State, Schedule, her pictures in the chat, and a turn's tool calls.
5. **A version of its own: v4.** Not v3.5. The old v4–v8 are now v5–v9.
6. **A design brief for Claude Design**, as for v2.12: [design/v4/](../../design/v4/).

**Defaults the owner did not change:**
- The journal is shown in the window, owner-only by rule (§Conflicts with the spec).
- The views do not follow her tool flags: they read data that exists, whatever her tools may do now.

## The server: read-only routes

**Rules for every route of v4.1–v4.4:**

- **Who can call it.** The owner's client token only. The room's token gets 403, like every other owner route. No
  token gets 401.
- **User scope.** Each route reads only the resolved `user_id`'s data (today `owner`). The paths are always
  `files_dir/<user_id>` and `journal_dir/<user_id>`; the v6.2 accounts then need no change here.
- **Read-only.** No route writes her sandbox, journal, store or memory. No route calls a model or a paid API, and
  none takes the turn lock, because a turn can run for minutes. A route reads files, or a copy of the in-memory
  thought list.
- **The sandbox guard.** Every path goes through the shared `safe_path` ([core/files.py](../../core/files.py)):
  absolute paths, `..` and symlinks out of the root are refused with 400.
- **Bounded.** Each route caps its entries per page, the text bytes it returns, the image bytes it serves and the
  image pixels it decodes.
- **Logic lives in core.** The listing, the journal parsing and the thought paging live in core (for example a
  `core/browse.py`, `core/journal.py` `parse_entry`, and `Core.thoughts_page`). The server only maps HTTP to them.

| Phase | Route | Returns | Notes |
|---|---|---|---|
| v4.1 | `GET /v1/files?path=` | `{path, entries:[{name, kind: dir\|file, type: text\|image\|other, size, count, created, modified}], truncated}` | Folders first, then by name. `count` is a folder's number of entries (the design's "74 items"); `null` for a file. `created`/`modified` are the v0.29 `_stat_dates`. Empty `path` is the root. At most 1,000 entries. |
| v4.1 | `GET /v1/files/text?path=` | `{path, text, size, cut, type: markdown\|plain\|code\|data}` | A text file (utf-8, the sandbox's text types): `text` is at most 256 KB; `size` is the whole file; `cut` says it was cut (the reader's "Cut at 256 KB · the file is 412 KB"). `type` picks the reader's mode: Formatted/Raw for markdown, a kicker for the rest. Anything not text: 415. |
| v4.1 | `GET /v1/files/raw?path=` | The picture's bytes | Pictures only: png/jpg/webp/gif, **detected by magic bytes, not the extension**, at most 10 MB. Anything else, SVG and HTML included: 415. Headers: `X-Content-Type-Options: nosniff`, `Content-Disposition: inline`, `Cache-Control: private`. A picture's dimensions in the reader and the chat come from the loaded image. |
| v4.2 | `GET /v1/images?before=&limit=&folder=` | `{items:[{path, folder, size, modified, width, height}], next, total, folders:[{folder, count}]}` | Every picture in the sandbox, newest `modified` first, paged by a cursor (`limit` ≤ 100), optionally one folder. `total` and `folders` feed the header ("112 pictures") and the folder filter's counts. `art/` is where `generate_image` writes, so the view says "in art/", never "made by her": no record of who made a file exists. |
| v4.2 | `GET /v1/images/thumb?path=` | A JPEG, longest side 320 px | Made by Pillow (a base dependency) on the first request. Cached in `<data root>/cache/thumbs/<user_id>/`, keyed by the path and `mtime`. The cache is **outside** the sandbox, so her file tools never see it. `Image.MAX_IMAGE_PIXELS` bounds decoding. |
| v4.3 | `GET /v1/journal` | `{days:[{date, sections, size, stamp}]}` | The `YYYY-MM-DD.md` files, newest first. `stamp` (bool) marks a day written with the code-owned stamp (the list's "· no stamp"). Owner-only. |
| v4.3 | `GET /v1/journal/{date}` | `{date, stamp:{mood, biorhythms:[{name, value, label}]\|null, forecast}\|null, sections:[{time, text}], markdown}` | Parsed from the v0.28 layout: the `# date` heading (dropped; an early day's heading isn't the date); the code-owned blockquote stamp (`> **Настрій:**`, `> **Біоритми:**`, `> **Прогноз:**`), each line optional, the biorhythm line as its three cells; the `## HH:MM` sections, prose before the first one an untimed section (`time: null`). An entry without a stamp gives `stamp: null`. A bad date gives 400; a missing day gives 404; a day over 256 KB 413. Owner-only. |
| v4.3 | `GET /v1/thoughts?before=&limit=&kind=&spoken=&date=` | `{items:[{when, kind, text, emotion, spoken}], next, stats:{total, per_day, spoken_share}, days:{date: count}, kinds:[…]}` | Newest first, `limit` ≤ 100; `kind` may repeat (several at once); `date` jumps to a day. `stats` feed the header ("5,512 · about 30 a day · 6% spoken") and `days` the day dividers' counts (a page can cut a day), both over the stream filtered by kind and spoken; `kinds` are the directive names. Filtered by the surfacing rule (`thoughts_for(user_id)`), so a thought sparked with another user never shows up. `seeds` stay internal. |
| v4.4 | `GET /v1/today` | `{date, mood:{resolution, reading, theme, made_at:null}\|null, biorhythms:[{name, value, label, trend: rising\|falling, period, day}], closeness:{level, name}, cycle:{day, length, phase, note, phases}\|null, plan: null}` | The structured form of `/mood`, `/biorhythm`, `/closeness`. `cycle` (added at the owner's request) is the hormonal cycle, drawn in State as a fourth cycle; the state snapshot's `cycle` `{phase, day, length}` names the phase in the portrait panel. `mood` only once today's mood is computed (the route never computes it); `reading` is the body without the resolution and the theme line; `made_at` stays `null` (the mood keeps no time, and a restart restores it from the log). `period` (23/28/33) and `day` (today's place in the cycle) let the window draw the ±14-day sine; `trend` is the sine's direction. `plan` once v5.7 exists. |
| v4.4 | `GET /v1/schedule` | `{now, quiet_hours, day_cap, fired_today, entries:[{name, directive, seeds, show, enabled, trigger:{kind: at\|every\|idle\|between\|cron, interval_s, at, days, window, cron}, last_fired, next_due, if_silent}]}` | The brain host's scheduler: every entry (disabled ones too), `last_fired` from `schedule.state`, `next_due` by the scheduler's own `due` (quiet hours veto all but `at`; a reached cap moves it past midnight); `if_silent` for `idle` ("if silent"). The trigger is structured; the window words it in English ("every day at 08:00"). 404 while no scheduler runs. |

**Additions to existing routes:**
- `GET /v1/state.features` gains `files`, `gallery` (v4.2: the sandbox and the thumbnail cache both served),
  `journal`, `thoughts` (and `today`, `schedule`), so a client shows only the views the server serves. v4.3:
  `journal` is true for the owner whenever a journal root is configured, whether or not the journal tool is on (the
  views read what exists); `thoughts` is true unless `thoughts.show` is `off`, the policy that already turns
  `/thoughts` off.
- **v4.2:** the `message` push and the turn outcome carry `pictures: [path]`. These are the sandbox paths of the
  pictures she sent (`send_image`) or made (`generate_image`) in that turn; the field is absent when there are none.
- **v4.4:** the turn outcome carries `tool_calls: [{name, input, result}]` while `files.trace` is on (`[]` when
  she called none; absent with the trace off). At most 20; `input` one line ≤ 120 characters, `result` one line
  ≤ 160; an image result is the trace's marker. `features` adds `today` and `schedule` (a scheduler running).

## The proxy

The new routes are added to `FORWARDED`, and the proxy relays binary bodies and their `Content-Type`. The token is
still added only in the proxy, never in the page. `test_desktop_contract.py` pins the new list.

## The window

**Navigation.** One row of views: **Chat · Files · Gallery · Journal · Thoughts · State · Schedule**. Each view
appears as its phase lands. A view replaces the chat column, and the portrait panel stays.

**Right panels** (from the design; v4.1).
- Any view but Chat can be pinned to a right panel and/or a bottom-right panel, so it stays beside the chat.
- The panel column is resizable — from 280 px up to the window's width less the portrait panel and a 360 px chat (the
  owner, 2026-11-17: wider than the design's 520 px cap) — and can be split between the two panels. It folds to a 46 px rail
  (⌘\).
- A pinned view always uses its narrow layout. Navigation inside a panel stays in that panel.
- The pins, width, split and folded state are kept per client in `localStorage`, as the window's other preferences
  are.
- Wide layout only; on a phone a pinned view is just a tab.

The exact measurements are in [design/v4/handoff/README.md](../../design/v4/handoff/README.md) §2.

**The chat keeps running.** The push channel (`/v1/events`) stays connected while another view is open. A reply or a
spoken thought that arrives meanwhile marks the Chat tab as unread.

**Language.** The window's own text is English (`strings.en.json`). Her content is Ukrainian and shown as written
(`lang="uk"`).

- **Files (v4.1).** A path bar at the top (each folder clickable) and a table: name, size, created, modified. A text
  file opens in the reader; a picture opens at full size.
- **Gallery (v4.2).**
  - A grid of thumbnails, newest first, loaded page by page, with a folder filter (all · `art/` · `pictures/` · …).
  - Clicking a picture shows it at full size, with its path, date and size, and an "Open in Files" button.
- **Her pictures in the chat (v4.2).** A picture in a message is drawn in the v2.12 picture style and loaded through
  `/v1/files/raw`. Clicking it opens the full size.
- **Journal (v4.3).** A list of dates, newest first. An entry shows the stamp first, as its own block (mood,
  biorhythms, forecast), then each `## HH:MM` section.
- **Thoughts (v4.3).**
  - Her whole stream, newest first, loaded page by page.
  - Filters: kind (the directive), spoken or silent, and a date jump.
  - Each item shows the time, the kind, the text, and the emotion's caption, as the strip does.
  - The strip beside the portrait stays as it is.
- **State (v4.4).** Today's mood reading in full, the three biorhythm values, the closeness level by name, and the
  plan once it exists.
- **Schedule (v4.4).** A table of her directives: the rule, the last firing, the next due time; the quiet hours and
  the day cap above it. It explains where a given thought came from.
- **A turn's tools (v4.4).** The details panel lists the tools she called in the last reply: name, short input, short
  result.

### The markdown reader

Her sandbox is mostly markdown (her notes, canons, concepts, drafts), so the Files view reads it as formatted pages,
not raw text. The reader extends the page's existing safe renderer.

**What it renders:** headings (with anchors), paragraphs, ordered and unordered lists, tables, blockquotes, code
blocks, inline code, bold, italic, horizontal rules.

**Links and images:**
- A **relative link to another file in her sandbox** opens that file in the reader. An `#anchor` scrolls to the
  heading.
- A **relative image** (`![](art/x.png)`) shows inline through `/v1/files/raw`.
- An **external link** (http/https only) is shown with its address and never loaded inside the window. Opening it in
  the system browser is a v4.5 candidate.
- A link that leaves the sandbox is shown as text.

**Navigation inside the reader:**
- an outline of the headings beside a long page;
- back and forward between the files opened in the reader;
- a toggle between the formatted view and the raw text.

**Other text types** (txt, json, yaml, csv, code) are shown as plain monospaced text with line numbers. A file cut at
the 256 KB cap says so at its end.

**Safety:**
- The reader never uses `innerHTML`. Every node is built and every text is set with `textContent`.
- HTML inside her markdown is shown as text.
- Pictures load only from the proxy's own origin.
- No external library and no network access beyond the proxy.

**States.** Every view has an empty state, a loading state and an error line. A server that stops shows the existing
no-server screen.

## Actions (v4.5, later)

These are candidates, chosen with the owner before v4.5 starts:
- upload a file or a picture from the Mac into her sandbox (create-only, a new name, size caps);
- "show this to her": a sandbox picture sent with a typed line as a turn's image;
- download a file to the Mac;
- open an external link in the system browser;
- rename or delete, only if the owner wants them. Her own tools stay non-destructive; a client action would be the
  owner's, logged and confirmed.

**Rules for every action:**
- The owner's token only.
- Every write through `safe_path`.
- Nothing destructive without a confirmation in the window.
- Each action logged.
- Contract-tested like the read routes.

## Contract changes

- **Server API v1, additive.** New routes, and new fields in `features`, `message` and the turn outcome. Each phase
  adds its paragraph to ARCHITECTURE §Contracts (the Server API v1 item).
  `tests/contract/test_server_api_contract.py` pins:
  - the routes;
  - the 401 and the room token's 403;
  - user scope with a second user;
  - the read-only property: a request over fixture roots leaves them byte-identical.
- **A documented rule changes (v4.2).** ARCHITECTURE says of the v2.4 push channel: "no face file, image or path ever
  crosses the API — the face stays a client-side pack". The face rule stays (the `turn` event still carries only the
  emotion and the theme name). The rule is narrowed to the face, and the owner-scoped read routes become the one
  documented way a picture from her sandbox crosses the API.
- **The proxy contract.** `FORWARDED` grows, pinned by `test_desktop_contract.py`.
- No change to the emotion contract, the memory records, the Agora space API, or the isolation invariant. The new
  routes are user-scoped and go through the surfacing filter.

## Conflicts with the spec

- **Journal visibility.** ROADMAP §v9.6 describes the journal as "admin-only, never shown to users". Today the owner
  is the only user and the admin, and `/journal` already shows it to the owner. The journal routes are therefore
  **owner/admin-only by rule** from the start: the token check plus a role check that v6.2's accounts can fill in.
  Another user's token must never read the journal (a contract test with a second token). §v9.6 now says so.
- **The v9.1 gallery.** v9.1 plans a gallery store behind the `Repository`, with metadata and `lili`/`user` tags. The
  v4.2 Gallery view reads the sandbox's picture files, because that is what exists. When v9.1 lands, the view's data
  source changes and the view stays. Until then the view cannot say who made a picture or with what prompt;
  `generate_image` stores no such record. §v9.1 now says so.
- **"Her pictures in the conversation"** moved from v6.3 (the web client) to v4.2. §v6.3 now says the web client
  reuses it.

## Not in this version

- Multi-user accounts (v6.2) and the web client (v6.3). The routes are user-scoped so both can reuse them.
- The v9.1 gallery store and its metadata.
- Search across files (her `search_files` tool exists; a search box could reuse it later).
- The Agora room's data (the space has its own store and no files).
