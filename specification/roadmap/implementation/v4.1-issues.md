# v4.1 — Issues

Issues for phase **v4.1 — Files and the markdown reader** (version **v4 — The window: her files, pictures, journal
and thoughts in Lili.app**), derived from the Tasks and DoD in [ROADMAP.md](../../ROADMAP.md) §v4.1, the concept
[DESKTOP_VIEWS.md](../../features/DESKTOP_VIEWS.md), the design handoff
[design/v4/handoff/](../../../design/v4/handoff/README.md) and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md). This file covers one phase; ids continue from the previous phase
(LUMI-300 → **LUMI-301…304**).

v4.1 gives the desktop window (`Lili.app`, v2.12) its first view of what her server-side tools leave on the box:
- three **read-only** owner routes over her sandbox: list a folder, read a text file, serve a picture;
- the window's **view row** and **right panels**;
- the **Files** view;
- the **markdown reader**.

It builds on the v0.19–v0.32 file sandbox (`safe_path`, `_stat_dates`), the v2.2–v2.6 server API and its token rule,
and the v2.12 window and proxy. It leaves the Gallery and her pictures in the chat (v4.2), the Journal and Thoughts
(v4.3), State, Schedule and a turn's tools (v4.4), and every action (v4.5) to later phases.

## v4.1 — Files and the markdown reader

### LUMI-301 — The browse logic: list a folder, read a text file, read a picture (`core/browse.py`)

**Description:**
A new read-only module, `core/browse.py`, that reads one sandbox root for the window. It is independent of the
server. `Core` gains a `files_root` property: `files_dir/<user_id>`, or `None` when no sandbox is configured. Touches
`core/browse.py` (new), `core/agent.py` (the property), `core/files.py` (only to reuse `safe_path` and
`_stat_dates`, unchanged).

**What needs to be done:**
- `list_folder(root, rel) -> dict`:
  - returns `{path, entries:[{name, kind: "dir"|"file", type: "text"|"image"|"other", size, count, created,
    modified}], truncated}`;
  - folders first, then by name;
  - `count` is a folder's number of entries (`null` for a file);
  - `created`/`modified` come from `_stat_dates` (the v0.29 dates);
  - at most `BROWSE_MAX_ENTRIES` (1,000), with `truncated`;
  - an empty `rel` is the root;
  - entries whose resolved target leaves the root (a symlink out) are skipped;
  - the same entries her `list_files` shows (no hidden-file filter beyond that).
- **Type detection**, by content, never by extension alone:
  - `image`: png/jpg/gif/webp by **magic bytes** in the first 12 bytes;
  - `text`: the first 4 KB contain no NUL and decode as UTF-8, allowing an incomplete last character;
  - anything else: `other`.
- `read_text(root, rel) -> dict`:
  - returns `{path, text, size, cut, type: "markdown"|"plain"|"code"|"data"}`;
  - reads at most `BROWSE_MAX_TEXT` (256 KB);
  - never cuts a UTF-8 character in half (an incomplete tail is dropped);
  - `size` is the whole file; `cut` says it was cut;
  - `type` by extension: `.md`/`.markdown` → markdown; a code set (`.py`, `.js`, `.ts`, `.sh`, `.css`, `.html`,
    `.sql`, …) → code; `.json`/`.yaml`/`.yml`/`.toml`/`.csv` → data; else plain;
  - a file that is not text raises a typed `NotServed` error.
- `read_picture(root, rel) -> (bytes, media_type)`:
  - the media type comes from the magic bytes;
  - at most `BROWSE_MAX_PICTURE` (10 MB), else a typed `TooLarge` error;
  - SVG, HTML and any non-picture raise `NotServed`.
- **Errors are typed** (`BadPath` from `safe_path`'s refusal, `NotFound`, `NotServed`, `TooLarge`) so the server
  maps them to 400 / 404 / 415 / 413.
- **Read-only by construction:** no `open(…, "w")`, no `mkdir`; `Core.files_root` never creates the folder (unlike
  the turn's file tools, which create it lazily).
- `Core.files_root` is a property; no new setting (the caps are module constants, as the Agora limits are).

**Dependencies:** None

**Expected result:**
`core/browse.py` lists, reads text from and reads pictures out of one user's sandbox, bounded and read-only, with
typed errors.

**Acceptance criteria:**
- [ ] A folder lists folders first, then files by name, with type, size, count and both dates; at most 1,000 entries,
      with `truncated`.
- [ ] A png/jpg/gif/webp is `image` by its bytes even with a wrong extension; a `.png` holding text is not an image.
- [ ] Text is cut at 256 KB on a character boundary, with the whole `size` and `cut: true`; a short file is whole.
- [ ] SVG, HTML and a binary file are refused by `read_picture`; a binary file is refused by `read_text`.
- [ ] `..`, an absolute path and a symlink out of the root are refused (`BadPath`); a symlink out is not listed.
- [ ] Nothing under the root changes: a fingerprint of the fixture root (paths, sizes, mtimes, bytes) is identical
      after every call, and `files_root` creates nothing.
- [ ] **Tests:** `tests/unit/test_browse.py` over `tmp_path` fixtures (folders, md/txt/json/py, png/jpg/gif/webp
      bytes, an SVG, a binary, a 300 KB text with a multibyte character at the cut, a symlink out, 1,001 entries).
      No model, no network.
- [ ] **Gates:** `uv run ruff check .`, `uv run pytest -q`.

### LUMI-302 — The read routes: `/v1/files`, `/v1/files/text`, `/v1/files/raw`, `features.files` — the API contract

**Description:**
The three owner routes over `core/browse.py`, plus `features.files` in the state. Touches `server/app.py`,
`specification/ARCHITECTURE.md` (§Contracts, the Server API v1 item, and the v2.4 rule), `docs/SERVER_SETUP.md`,
and `tests/contract/test_server_api_contract.py`.

**What needs to be done:**
- **The routes:**
  - `GET /v1/files?path=` → `list_folder`;
  - `GET /v1/files/text?path=` → `read_text`;
  - `GET /v1/files/raw?path=` → `read_picture`'s bytes with their media type.
- **Every route:**
  - `dependencies=guarded`: the owner's token only; the room's token 403 (`ROOM_ONLY`); no token 401;
  - **never takes `service.lock`**: a turn running for minutes doesn't block a read;
  - no model call; no write.
- **Errors:** `BadPath` 400, `NotFound` 404, `NotServed` 415, `TooLarge` 413; a missing `files_root` → 404
  `files are not served`. The detail is a readable line, never a stack or an absolute path.
- **Headers on `/v1/files/raw`:** `X-Content-Type-Options: nosniff`, `Content-Disposition: inline`,
  `Cache-Control: private, max-age=300`. The JSON routes get `Cache-Control: no-store`.
- `GET /v1/state.features` gains `files: bool` (`core.files_root is not None`). It is independent of
  `files.enabled`: the view reads what exists.
- **ARCHITECTURE §Contracts (Server API v1):**
  - add a "**v4.1 (additive)**" paragraph: the three routes, their shapes, caps, errors, headers, the owner-only rule
    and the no-lock rule;
  - in the v2.4 sentence "no face file, image or path ever crosses the API", note that the face rule is unchanged
    and that v4.1's owner read routes serve sandbox files. The full narrowing of that sentence for pictures in the
    chat is v4.2.
- `docs/SERVER_SETUP.md`: the routes in the API list (one line each).

**Dependencies:** LUMI-301

**Expected result:**
The server serves her sandbox read-only to the owner's token over three pinned routes, and the state says so.

**Acceptance criteria:**
- [ ] The three routes answer with the shapes above; `features.files` is true with a sandbox and false without.
- [ ] 401 without a token; 403 with the room's token (an app built with a space and a room token); 200 with the
      owner's.
- [ ] 400 / 404 / 413 / 415 as mapped; no absolute path in any error.
- [ ] A read answers while the service lock is held (the test holds `service.lock` and reads).
- [ ] **User scope:** two cores with different `user_id`s over one `files_dir` never list or read each other's
      folder; `path=../<other>/x` is 400.
- [ ] **Read-only:** a fingerprint of the fixture sandbox is identical after every route is called.
- [ ] **Tests:** `test_server_api_contract.py`:
  - the pinned route set gains the three routes;
  - shapes, auth, errors, headers, `features.files`, the lock, user scope, read-only.

  A mock model, no network.
- [ ] **Contract:** Server API v1 — ARCHITECTURE §Contracts "v4.1 (additive)", pinned by
      `tests/contract/test_server_api_contract.py`.
- [ ] **Gates:** `uv run ruff check .`, `uv run pytest -q`.

### LUMI-303 — The window's frame: the proxy's new routes, the view row, the right panels, the design's tokens and strings

**Description:**
The window learns to show views beside the chat (design handoff §1–§3 and `LiliWindow.v4-changes.md`). Touches:
- `desktop/proxy.py` (`FORWARDED`, `PASS_RESPONSE`);
- `desktop/ui/index.html`, `app.js`, `style.css`, `tokens.css` (append `tokens.add.css`), `strings.en.json` (merge
  the v4.1 keys of `strings.en.add.json`);

  `tests/integration/test_desktop_proxy_flow.py`;
- the ARCHITECTURE v2.12.1 desktop paragraph and the CLAUDE.md `/desktop` line ("the eight /v1 routes" → eleven).

**What needs to be done:**
- **Proxy:**
  - `FORWARDED` gains the three GET routes;
  - `PASS_RESPONSE` gains `X-Content-Type-Options` and `Content-Disposition`;
  - the relay already streams raw bytes (`iter_raw`); a picture is pinned by an integration test through a fake
    upstream.
  - **Pictures and the key:** `/v1` requires the window's key header and an `<img>` can't send it, so the page loads
    a picture with `fetch` (the key) into a `blob:` URL and revokes it when the view changes. No keyless picture
    path is added to the proxy.
- **The view row** (handoff §1):
  - over the content column, above the banner; Chat · Files in v4.1, so the row ends early (2 tabs);
  - the active tab bar; the unread mark on Chat when a message arrives while another view is open, cleared on
    return;
  - ⌘1/⌘2 (Ctrl elsewhere);
  - a view replaces the message list and the input; the banner stays;
  - the push channel stays connected, and the chat scrolls to the bottom on return.
- **The right panels** (handoff §2), wide layout only:
  - the pin group (pin to the right / bottom-right panel, `aria-pressed`); a view lives in one panel at a time;
  - the panel column (340 px, drag 280–520, ← → ±20) and the split between two panels (0.55, drag 0.2–0.8, ↑ ↓
    ±0.05, minimum 140 px);
  - panel headers with tabs, unpin and collapse;
  - the folded 46 px rail (⌘\);
  - navigation inside a panel stays in it;
  - a pinned view uses its narrow layout;
  - on a phone, pinned views are just tabs.
  - The pins, the active tabs, the width, the split and the folded state are kept in `localStorage`, each access in
    `try`/`catch` like the window's other preferences.
- **A view's frame** (handoff §3):
  - the header bar;
  - the states: loading (the pulse and skeleton rows), empty, error (`role="alert"` + Try again), and offline (the
    existing banner);
  - narrow below 640 px of the view's own width (a `ResizeObserver`).
- **Tokens and strings:**
  - append `design/v4/handoff/tokens.add.css` to `tokens.css` (no existing value changes);
  - merge the v4.1 keys of `strings.en.add.json` (`views.*`, `nav.*`, `files.*`, `date.*`, `reader.*`, `state.*`
    frame states, `panels.*`) into `strings.en.json`;
  - later phases merge their own keys.

**Dependencies:** LUMI-302

**Expected result:**
The window has a view row with Chat and a Files placeholder view, right panels that pin and keep their layout, and
the proxy forwards the three routes.

**Acceptance criteria:**
- [ ] `FORWARDED` = the eight v2.12 routes + the three v4.1 routes, each served by the server
      (`test_desktop_contract`).
- [ ] A picture relays byte-for-byte with its `Content-Type`, `nosniff` and `Content-Disposition` (integration, fake

- [ ] **Gates:** `uv run ruff check .`, `uv run pytest -q`.
- [ ] **Manual (owner)**, on dev, with `./lumi-desktop` from the dev tree against the dev server:

### LUMI-304 — The Files view and the markdown reader

**Description:**
The Files view and the reader (design handoff §4, §5 and §"Markdown → DOM"). Touches `desktop/ui/app.js`,
`desktop/ui/style.css`, `tests/unit/test_desktop_static.py`, `docs/SERVER_SETUP.md` (the desktop section) and
`README.md`'s current-version paragraph at release.

**What needs to be done:**
- **Files** (handoff §4):
  - **Header:** back / forward (⌘[ ⌘], one history over folders and files); the path bar (`lili / notes / …`, each
    segment a button, the current one `aria-current`); the item count. The right end is left free for v4.5's actions.
  - **Table (wide):** Name · Size · Created · Modified. Folders first, with "N items" for a folder. "Today 14:10",
    "Yesterday" or "16 Nov 2026" for dates. Other types are listed muted, with "not shown" and no action.
  - **Narrow rows:** icon, name, then "size · date" under it.
  - **The 1,000+ note** at the end of a cut folder.
  - **Clicks:** a folder opens; a text file opens in the reader; a picture opens full size. In v4.1 that is a simple
    full-size picture page (no gallery navigation). v4.2's full picture view replaces it.
- **The reader** (handoff §5):
  - **Header:**
    - back / forward, the path ending with the file's name, and the size and date;
    - for markdown, Formatted / Raw; for other text, a "Plain text" / "Code" / "Data" kicker;
    - narrow: two header rows and "Contents ▾".
  - **The page:** max 68ch, `--l-read` 17/1.7, the handoff's h1–h4, lists, quotes, code blocks, inline code, tables
    (scrolling sideways), and rules.
  - **Links:**
    - a relative link to another of her files is a button that opens it in the reader, resolved against the file's
      folder and pushed to history;
    - an `#anchor` scrolls to the heading;
    - an external http(s) link is **not a link**: the text with a dotted underline and `↗ host/path`;
    - a link that leaves the sandbox is plain text.
  - **Inline pictures:** `![alt](rel)` resolved against the file's folder and loaded through `/v1/files/raw` with
    the key into a `blob:` URL. The caption is "alt · path · W × H"; W × H comes from `naturalWidth` /
    `naturalHeight`. A click opens the picture full size.
  - **The outline** (≥ 4 headings):
    - wide, a 220 px column that follows the scroll (`aria-current`);
    - narrow, folded under "Contents ▾".
  - **Raw view, and all non-markdown text:** monospaced, with line numbers.
  - **The cut note:** "Cut at 256 KB · The file is {size}…" when `cut`.
- **The parser:** extend the page's safe markdown renderer from the handoff's `parseMd` / `inl`:
  - headings h1–h4, fences, `---`, a picture on its own line, quotes, pipe tables (row 2 the separator), `-`/`*`/`1.`
    lists, paragraphs;
  - inline code, bold, italic and links;
  - everything else is literal text;
  - nodes built with `createElement` + `textContent`, never `innerHTML`; HTML in her markdown shows as text.
- **Keyboard and accessibility** (handoff §Accessibility): real buttons, `aria-current`, `aria-expanded`, and the
  focus ring.
- **Docs:** `docs/SERVER_SETUP.md`, the desktop section, gets Files and the reader in a few lines.

**Dependencies:** LUMI-303

**Expected result:**
From `Lili.app` the owner browses her sandbox and reads her markdown as formatted pages, with working internal links
and pictures.

**Acceptance criteria:**
- [ ] Any folder opens; any text file reads; markdown renders formatted with the handoff's elements; Raw shows line
      numbers.
- [ ] A relative link opens the linked file in the reader; back/forward return; an `#anchor` scrolls; an external
      link is shown, not followed; a link out of the sandbox is text.
- [ ] A relative picture shows inline through a `blob:` URL loaded with the key, and opens full size.
- [ ] A cut file says so; an "other" file is listed but not opened; the states (empty, loading, error, offline) show.
- [ ] **Tests:** `test_desktop_static`:
  - no `innerHTML`, `outerHTML`, `insertAdjacentHTML` or `document.write`;
  - the parser's link handling admits only relative sandbox paths and http(s), and builds no `<a href>` for
    external links;
  - pictures load only through `fetch` + `blob:`;
  - every new string key resolves.

  Rendering itself is the owner's live check, as in v2.12; no browser automation in CI.
- [ ] **Gates:** `uv run ruff check .`, `uv run pytest -q`.
- [ ] **Manual (owner)**, on dev (`./lumi-desktop` from the dev tree, dev server):
  - the dev sandbox browses;

  The dev sandbox has 7 pictures and no markdown today, so put a few sample `.md` files into
  `~/lumi/dev/data/files/owner/notes/` first (the owner, or Claude on the owner's word).
