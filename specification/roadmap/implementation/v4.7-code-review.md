## Findings

### 1. 🟠 MEDIUM — Holding ⌥Space to talk types non-breaking spaces into the input

**Where:** `desktop/ui/app.js` `micKey` (the keydown branch).

**Failure scenario:** the input holds «Привіт» and has the focus. The owner holds ⌥Space to talk, as the hint says.
The first keydown starts the dictation and is prevented. After macOS's repeat delay (about half a second) WebKit
sends a keydown with `repeat: true` every 30–80 ms for as long as the keys are held. `micKey` returns `false` for a
repeat **without** `preventDefault()`, so each repeat runs its default action: on macOS ⌥Space types a
non-breaking space (U+00A0). A 5-second hold puts some 60–150 of them after «Привіт»; the settled phrases are
appended after them («Привіт␣␣␣…␣Як справи?»), and the message is sent with that run of wide blanks in the middle.
`trim()` removes them only at the ends. Esc and an error restore the input, but a normal stop keeps them.

**Fix:** in the keydown branch, swallow an ⌥Space repeat while the mic is shown — `preventDefault()` and return
`true` without starting or stopping anything. A tap and the first keydown of a hold behave as before.

**Test:** run `micKey` in node with a keydown `{altKey, code: "Space", repeat: true}` and stubs: the event is
prevented, the function returns `true`, and neither `dictStart` nor `dictStop` is called; a first keydown still
starts.

### 2. 🟡 LOW — An error late in a long recording also takes away the phrases already settled

**Where:** `desktop/ui/app.js` `onDictEvent` (`error`), `dictStart` (the broken stream).

**Failure scenario:** the owner dictates for three minutes; the settled phrases are already in the input; then
the recognizer breaks (or the connection drops). The error puts the input back as it was **before** the recording,
so three minutes of recognized words disappear along with the failure.

**Why deferred:** this is the rule as written (DESKTOP_VIEWS §Dictation: «An error puts the input back as it was»;
the v4.7 issues; the owner confirmed the behavior). Keeping the settled phrases on a late error, and restoring only
on an error before the first `final`, changes that rule, so it is the owner's call. Home: backlog.

**Decision (the owner, 2026-11-20):** the rule stays as written — an error puts the input back as it was before the
recording. The finding is closed with no change.

### 3. 🟡 LOW — The live line is an `aria-live` region rebuilt about 14 times a second

**Where:** `desktop/ui/index.html` (`#dictation` with `aria-live="polite"`), `desktop/ui/app.js` `renderDictation`.

**Failure scenario:** with VoiceOver on, every `level` event (about ten a second) and every timer tick (four a
second) replaces the whole live region, so the screen reader keeps announcing «Listening 0:03 … Esc — cancel»
instead of the words. Nothing breaks without a screen reader.

**Fix (later):** keep `aria-live` on the phrase only (or announce only the status changes) and update the level bar
and the timer in place. Home: backlog.

### 4. 🟡 LOW — A stop that arrives before the start has claimed the slot is lost

**Where:** `desktop/proxy.py` `_dictation` (`stop` answers `{"stopped": false}` when nothing is claimed),
`desktop/ui/app.js` `dictStop` (ignores the answer).

**Failure scenario:** the page sends `start`, then `stop` on another connection. If the stop's thread runs before
the start's thread reaches `claim()`, `stop()` returns `False`; the start then claims, connects and opens the mic,
while the page shows «recognizing…». The mic stays open until Esc or the 5-minute cap. The window between the two
requests is a few milliseconds, and a human second click or ⌥Space tap comes 100 ms or more after the first, so it
was not reproduced.

**Fix (later):** remember a stop that comes while a start is in flight (a flag `claim()` reads), or have the page
resend the stop when the answer is `stopped: false` and the stream later says `ready`. Home: backlog.

### 5. 🟡 LOW — The Whisper fallback hands the audio over through a temporary file

**Where:** `voice/stt.py` `WhisperSTT.recognize` (a `NamedTemporaryFile`, deleted when the call ends), reached from
`server/dictation.py` batch mode when `dictation.stt_provider` is `whisper`.

**Failure scenario:** ARCHITECTURE §v4.7 says no audio is stored on disk. With the local Whisper provider the WAV
sits in the system's temp folder for the length of the recognition (and stays there if the process is killed in
that moment). The box runs Deepgram, so neither dev nor prod takes this path today.

**Fix (later):** decode the WAV to a float array in memory and pass it to `transcribe`, or name the exception in
ARCHITECTURE. Home: backlog.

## What's solid

- **The handshake.** The route checks the owner's token before it accepts; no token, a wrong one, the room's and a
  server without a recognizer all get a 403 with nothing accepted. A browser page can't add the header, so a LAN page
  can't open the socket.
- **One at a time without a lock.** The busy flag is checked and set on the event loop with no `await` between,
  and cleared in `finally`; the turn lock is never touched, so her turns run while the owner dictates.
- **Every relay path ends bounded.** The stream's open has `websockets`' 10 s open timeout, the batch call
  Deepgram's 30 s, the last results 3 s, silence 10 s, the recording 5 minutes; a dead client or a send into a
  closed socket ends it as `gone`.
- **The phrase hold survives the stop.** `CloseStream`, the wait and `flush()` mean the last phrase said before
  the release is never lost, and the interim line shows the held part, so nothing jumps.
- **The mic.** It opens only after `ready`, and every way out (a stop, a cancel, an error, the cap, a page that
  reloads, the window closing, a cancel that lands while the mic is still opening) closes it; the shell's tests
  pin each one with a fake mic.
- **Nothing kept, nothing leaked.** The audio lives in memory only on both sides; the log lines carry counts and
  outcomes, the page gets an exception's type, and the words are only ever `text` on the page, never HTML.
- **The fallback is the server's.** The shell always streams; whether the box recognizes live or whole is decided
  in one place, and a stream that can't open falls back to batch on its own.
