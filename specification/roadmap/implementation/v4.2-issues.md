# v4.2 — Issues

Issues for phase **v4.2 — Gallery and her pictures in the chat** (version **v4 — The window: her files, pictures,
journal and thoughts in Lili.app**), derived from the Tasks and DoD in [ROADMAP.md](../../ROADMAP.md) §v4.2, the
concept [DESKTOP_VIEWS.md](../../features/DESKTOP_VIEWS.md), the design handoff
[design/v4/handoff/](../../../design/v4/handoff/README.md) §6 and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md). This file covers one phase; ids continue from the previous phase
(LUMI-304 → **LUMI-305…308**).

v4.2 gives the window the second view of her sandbox and puts her pictures into the conversation:
- a **picture listing** over the whole sandbox, newest first, paged, with per-folder counts;
- **thumbnails** made once and cached outside the sandbox;
- the **Gallery** view and the **full picture view** (also used by Files and the chat);
- **her pictures in the chat**: the turn's picture paths on the `message` push and the turn outcome, drawn as the
  v2.12 picture.

It builds on v4.1 (`core/browse.py`, the owner routes and their token rule, the view row, the right panels and the
`blob:` picture loading) and on the v0.23 `generate_image` / v0.24 `send_image` tools. It leaves the Journal and
Thoughts (v4.3), State, Schedule and a turn's tools (v4.4), and every action (v4.5) to later phases.

**Reconciled against the code (2026-11-17):**
- **The v2.12 chat picture was designed but never built.** v2.12.2 deferred it; the page has no picture in a message
  today. LUMI-308 builds it from the v2.12 handoff ("Picture in the conversation") and the v4 handoff §6.
- **v4.1's picture page is a stand-in.** `renderPicturePage` in `desktop/ui/app.js` says so ("v4.2's full picture
  view replaces it"). LUMI-307 replaces it with the full picture view.
- **The core keeps no record of a turn's pictures.** `Core.last_tool_calls` is filled only while `files.trace` is on.
  The picture paths need their own per-turn list, independent of the trace (LUMI-306).
- **`send_image` has no sink on an instance without the bridge** (`server/__main__.telegram_sink_of`: bridge and
  image both on). It then answers "Telegram not connected" and nothing is sent. Only a picture actually sent
  counts; `generate_image` always counts when it saved a file.
- **History in the window is the server's in-memory replay** (the last 50 `message`/`thought` events). `pictures`
  on a `message` replays with it. Nothing is added to the stored `Message` record, so the memory contract is
  untouched.
- **A feature flag for the view.** DESKTOP_VIEWS lists `features.files/journal/thoughts/today/schedule` but no key
  for the Gallery. The v4.1 review #3 rule (show a view only when the server serves it) needs one, so LUMI-306 adds
  `features.gallery` and DESKTOP_VIEWS says so. (`features.image` already exists and means the image *tool*; it
  stays as it is.)
- **The design strings are not merged yet.** v4.1 merged only its own keys; the 23 `gallery.*` and `picture.*` keys
  of `strings.en.add.json` come in with LUMI-307. The tokens (`--l-thumb-min`, `--l-picmeta`) are already in
  `tokens.css`.
- **Pillow is a base dependency** (`pyproject.toml`, `pillow>=11`, since v0.7), so the server image already has it.
- The v4.1 review's deferred LOW #5 (a file name that isn't valid UTF-8 fails the JSON) applies to the picture
  listing too. It stays in the backlog with #4; nothing produces such names.

## v4.2 — Gallery and her pictures in the chat

### LUMI-305 — The gallery logic: list her pictures, make and cache thumbnails (`core/gallery.py`)

**Description:**
A new read-only module, `core/gallery.py`, beside `core/browse.py`. It lists every picture in one sandbox root and
makes a 320 px JPEG thumbnail of one, cached in a folder outside the sandbox. It is independent of the server.
Touches `core/gallery.py` (new) and reuses `core/browse.py` (`_resolve`, `picture_type`, the error classes, the
`BROWSE_MAX_PICTURE` cap) unchanged.

**What needs to be done:**
- `list_pictures(root, *, before=None, limit=100, folder=None)` →
  `{items:[{path, folder, size, modified, width, height}], next, total, folders:[{folder, count}], truncated}`:
  - walks the sandbox without following symlinked folders; an entry whose target leaves the root is skipped (the
    v4.1 `_inside` rule);
  - a picture is typed **by its magic bytes** (`picture_type`, png/jpeg/gif/webp), never by its extension; SVG is
    never a picture;
  - order: newest `st_mtime_ns` first, then by path, so equal times page stably;
  - `modified` is the v0.29 `_stat_dates` string (`YYYY-MM-DD HH:MM`), as in the Files view;
  - `folder` is the picture's folder relative to the root (`""` for the root); the filter matches **that folder
    exactly** (`art` does not include `art/sketches`, as in the design's filter);
  - `total` and `folders` (each folder with its count, sorted by name) count the whole sandbox, not the page or the
    filter, so the header and the filter stay stable while paging;
  - `limit` is 1..100; `before` is the opaque cursor the previous page returned as `next` (`null` on the last page).
    A malformed cursor is `BadPath`; an unknown folder gives an empty page;
  - `width`/`height` are read from the picture's header (Pillow's lazy `Image.open`, no decode) for the page's items
    only; a header Pillow can't read gives `null` for both;
  - the walk visits at most `GALLERY_MAX_SCAN` (10,000) files and then sets `truncated`;
  - the cursor is a pure helper (`encode_cursor` / `decode_cursor`) so it can be tested with plain data.
- `thumbnail(root, rel, cache_dir)` → JPEG bytes, longest side 320 px:
  - the path goes through the sandbox guard (`_resolve`); not a picture → `NotServed`; missing → `NotFound`; larger
    than `BROWSE_MAX_PICTURE` → `TooLarge`;
  - decoding is bounded: a picture over `THUMB_MAX_PIXELS` (from its header, before any decode) is `TooLarge`, and
    Pillow's own `DecompressionBombError` maps to `TooLarge` too. `Image.MAX_IMAGE_PIXELS` is not changed globally;
  - an animated GIF gives its first frame; a picture with transparency is flattened onto a neutral background; the
    EXIF orientation is applied;
  - the cache file is named by a hash of the sandbox path plus the source's `mtime_ns`:
    `<cache_dir>/<sha256(path)[:32]>-<mtime_ns>.jpg`. A hit returns it without opening the source. A miss makes it,
    writes it atomically (a unique temporary name, then `os.replace`) and removes the same path's older thumbnails;
  - `cache_dir` is created on the first miss. The function refuses a `cache_dir` inside `root` (`ValueError`): the
    cache must never be where her file tools can see it.
- Nothing in `root` is ever written, created or touched.

**Dependencies:** None (builds on v4.1's `core/browse.py`).

**Expected result:**
The core can page through every picture in her sandbox and hand back a cached thumbnail of any of them, without
changing anything in the sandbox.

**Acceptance criteria:**
- [ ] The listing: newest first, stable order on equal times, typed by bytes (a `.txt` holding a PNG is a picture, a
      `.png` holding text and an `.svg` are not), the exact-folder filter, `total` and `folders` over the whole
      sandbox, `null` dimensions for an unreadable header, a symlink out skipped, `truncated` past the scan cap.
- [ ] The cursor: a walk of pages by `next` returns every picture exactly once; a malformed cursor is `BadPath`;
      `limit` outside 1..100 refused.
- [ ] The thumbnail: longest side 320 px and JPEG; a cache hit doesn't open the source; a new `mtime` is a miss and
      the old thumbnail goes; too many pixels → `TooLarge`; SVG, text and a missing file refused; traversal refused;
      a cache folder inside the root refused.
- [ ] **Tests:** `tests/unit/test_gallery.py` with real Pillow-made fixture pictures in `tmp_path` (png/jpeg/gif/webp,
      a transparent PNG, an animated GIF), and the v4.1 fingerprint check that the sandbox stays byte-identical
      across listing and thumbnailing. No network, no model.
- [ ] **Gates:** `uv run ruff check .` and `uv run pytest -q`.

### LUMI-306 — The routes and the turn's pictures: `/v1/images`, `/v1/images/thumb`, `features.gallery`, `pictures` on `message` and the outcome; the narrowed face rule

**Description:**
The server maps LUMI-305 to two owner routes, and a turn's pictures reach the clients. Touches `server/app.py`
(the routes, `features.gallery`, `pictures` on the push and the outcome), `server/__main__.py` (the thumbnail cache
folder from the data root), `server/brain.py` (the server's own turns push their pictures too), `core/agent.py`
(`Core.last_pictures`), `specification/ARCHITECTURE.md` and `specification/features/DESKTOP_VIEWS.md`.

**What needs to be done:**
- **The routes** (the v4.1 pattern: `guarded`, the room token 403, no turn lock, no model call, errors through the
  same `BROWSE_STATUS` map, a readable line naming the sandbox path only):
  - `GET /v1/images?before=&limit=&folder=` → `list_pictures` (`limit` 1..100, default 100), `Cache-Control:
    no-store`;
  - `GET /v1/images/thumb?path=` → the JPEG (`image/jpeg`) with the v4.1 raw headers (`nosniff`, `inline`,
    `private, max-age=300`);
  - no sandbox configured → 404 `files are not served`, as in v4.1.
- **The cache folder:** `create_app` takes `thumbs_dir` (default `None` → the thumbnail route answers 404 `thumbnails
  are not served`); `server/__main__` passes `<data root>/cache/thumbs`, and the route uses
  `thumbs_dir/<user_id>`. The folder is under the data root and outside `files_dir`.
- **`GET /v1/state.features.gallery`:** true when both the sandbox and the cache folder are served.
- **The turn's pictures:** `Core.last_pictures: list[str]`, reset at the start of every `reply` (beside
  `last_tool_calls`, including the path that skips `_turn_tools`). It is filled whatever `files.trace` says:
  - `generate_image`: the sandbox path it saved (`created art/x.png …`), only on success;
  - `send_image`: the sandbox path it sent, only when the sink was called (not on "Telegram not connected", not on
    an error);
  - each path once, in order.
- **On the wire:**
  - the turn outcome (`turn_payload`: `/v1/turn` and the streamed `done`) carries `pictures: [path]`;
  - `publish_message("lili", …)` carries the same list: the client turn in `app.py`, the inbox turn and the spoken
    self-turn in `brain.py`;
  - the field is **absent** when there are none (the outcome and the push stay byte-identical for a turn without
    pictures);
  - the `turn` face event is unchanged: emotion, intensity, theme name, origin, never a path.
- **Telegram is unchanged:** `send_image` still writes its photo record through the sink; the window gets the path
  in addition.
- **ARCHITECTURE §Contracts (Server API v1):**
  - a **"v4.2 (additive)"** paragraph: the two routes, the cache outside the sandbox, `features.gallery`, `pictures`
    on `message` and the outcome;
  - the v2.4 sentence "no face file, image or path ever crosses the API" **narrowed to the face**: the `turn` event
    still carries only the emotion and the theme name; a picture from her sandbox crosses only as a sandbox path on
    `message` / the outcome and as bytes from the owner's read routes. The v4.1 note there is folded into this.
- **DESKTOP_VIEWS.md:** `features.gallery` in the additions list.

**Dependencies:** LUMI-305.

**Expected result:**
A client can page her pictures, load their thumbnails, and learn the sandbox path of every picture she made or sent
in a turn, with the face rule unchanged.

**Acceptance criteria:**
- [ ] The routes answer with the shapes above; a bad cursor or path 400, missing 404, too large 413, SVG/text 415;
      no token 401, the room's token 403, on both routes.
- [ ] User scope: a second core with another `user_id` and its own sandbox never sees the first one's pictures or
      thumbnails.
- [ ] Read-only: a listing and a thumbnail leave the sandbox byte-identical (fingerprint); the thumbnail lands in
      `thumbs_dir/<user_id>`, never in the sandbox.
- [ ] The routes answer while a turn holds the lock.
- [ ] `pictures`: present on the outcome and on her `message` push after a turn whose mocked tools made / sent a
      picture; absent otherwise; a failed `generate_image` and an unsent `send_image` add nothing; the inbox turn and
      the spoken self-turn push it too; the `turn` event never carries it.
- [ ] Telegram: `send_image` still calls the sink with the same arguments.
- [ ] **Tests:** `tests/contract/test_server_api_contract.py` (the route set, the v4.2 tests, `features` now with
      `gallery`), `tests/unit/test_server_brain.py` or its existing home for the brain's pushes, a core unit test
      for `last_pictures` with a mock `ImageGen` and a fake sink. No paid calls: the image model is mocked.
- [ ] **Contract:** Server API v1 (the routes, `features.gallery`, `pictures`) and the narrowed face rule —
      ARCHITECTURE §Contracts updated in this commit and pinned by the contract tests above.
- [ ] **Gates:** `uv run ruff check .` and `uv run pytest -q`.
