## Detailed Results

### LUMI-219: The push channel (#219)

**Status:** completed · **Commit:** 30835a9

An `EventBus` (one bounded queue per listener, drop-oldest, `close()` ends every stream) and
`GET /v1/events` (SSE): the current `state` first, a `turn` event `{emotion, intensity, theme, origin}` after
every turn, `state` `{origin, state}` only on change, `:` heartbeats every 15 s. Snapshots are taken by
whoever holds the lock — `GET /v1/state` mid-turn returns the last consistent one (closes v2.2 review #7).
The state gains `closeness {level, name}`; `X-Lumi-Client` becomes the events' `origin`. The server's first
Ctrl+C closes the bus, so a listening client never holds uvicorn's graceful stop open (proven: plain uvicorn
hangs on an open listener). No face asset crosses the API (pinned).

**Validation:** +20 tests (the bus, the route, the contract, a real-uvicorn stop with a listener attached).

### LUMI-220: Directives on the server (#220)

**Status:** completed · **Commit:** 9370d66

`POST /v1/directive {line}` runs `run_directive` under the lock; an open thought is pushed as `thought`

returns the core's `DirectiveOutcome`; `./lumi-cli think [topic]` fires `%think!`.

**Validation:** +10 tests (the route + the push to a second listener, the CLI over a TestClient transport,
the contract).

### LUMI-221: The client lives on pushes (#221)

**Status:** completed · **Commit:** 9884f52

`RemoteCore.listen` / `stop` — a daemon thread on `/v1/events` over a dedicated events client (read timeout
45 s ≈ 3 missed heartbeats); reconnect with backoff (1 s → 30 s), `_offline` once per outage and `_online`
when back, a request that reaches the server cuts the backoff short, a 404 (older server) ends it quietly,
its own thoughts skipped by `origin`. The TUI re-renders status/stats from `state` pushes (not while busy),
shows pushed thoughts as `💭`, says an outage once; typed `%directives` run on the server again.

**Validation:** +12 tests — the listener over a scripted streaming transport, and the real TUI over real
uvicorn on localhost (a thought fired elsewhere arrives unasked; the status line follows a change made
elsewhere; its own `%think!` shows once; a stopped server is said once and a restarted one picked up).

## Fixes applied during execution

- **An empty Gemini answer lost the thought** (found in the live DoD, commit dfaa3fb, pre-existing): the
  first `./lumi-cli think` returned nothing — gemini-2.5-flash ended the thought call with 0 answer tokens.
  The prod cache log showed 59 of 279 thoughts (21%) lost the same way since 2026-10-01. The single-call
  paths had no retry and the blocking loop retried only its structured terminal. Now a tool-less thought, a
  tool-less structured reply and the think-path tool loop each re-ask once (thinking off where the model
  allows it), count both calls, and log why the first was empty; `think()` logs a lost thought instead of
  swallowing it. Regression tests fail on the old code.
- **Port 8766 was taken** by another project's server (migVisor-3-prototype's lineage viewer, which later
  moved to Lumi's prod port 8765). Outside this repo: the machine-wide port registry
  `~/development/PORTS.md` now assigns Lumi 8765 (prod) / 8766 (dev) and lists the conflicts to fix.

## Architecture impact

- API v1 grows additively: `GET /v1/events` (SSE `state` / `turn` / `thought` + heartbeats, `origin`),
  `POST /v1/directive`, `closeness` in the state, `X-Lumi-Client`; no face assets on the API (pinned).
- `GET /v1/state` returns the last consistent snapshot while a turn runs (fresh when idle).
- The server's stop now ends every events stream first (`server/__main__.make_server`).
- Gemini: every single-call path and the text tool loop re-ask an empty answer once — at most one extra
  call, only when an answer is empty.

## Found, for the review

- `GET /v1/events` serves every listener the same events — fine for one owner; the per-user filter is a
  multi-user concern (v4).
- The listener's 401 (a token changed under a running client) retries forever with one outage line — no
  distinct hint.
- The in-process TUI still runs a typed `%directive` on the UI thread (pre-existing; client mode now runs it
  off-thread).
