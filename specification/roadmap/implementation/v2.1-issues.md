# v2.1 — Issues

Issues for phase **v2.1 — Prod & dev: two Лілі, one codebase** (version **v2 — Client/server split: her
brain on the server, the TUI a thin client**), derived from the Tasks and DoD in
[ROADMAP.md](../../ROADMAP.md) §v2.1 and the contracts in [ARCHITECTURE.md](../../ARCHITECTURE.md). This
file covers one phase; ids continue from the previous phase (LUMI-206 → **LUMI-207…210**).

The daily Лілі stops running from the development working tree: a **prod** instance (a release-tag
checkout in `~/lumi/prod`, outside `~/development`, carrying her real memory) and a **dev** instance (the
working tree, disposable data) run side by side and can never open each other's data. Built on the
existing single config entry point (`core/config.py::load_config`, used by the TUI, both Telegram
daemons, the voicer and the dictator); everything unset stays **byte-identical**. No server work — the
server instances (v2.6) and the deploy pipelines (v2.7) inherit this split later.

## v2.1 — Prod & dev: two Лілі, one codebase

### LUMI-207 — LUMI_HOME — the data root every mutable path derives from

**Description:**
All mutable state is pinned to the repo: seven defaults in `core/config.py` compute from
`_REPO_ROOT / ".lumi"` — `DEFAULT_STORE_PATH`, `DEFAULT_FILES_DIR`, `DEFAULT_JOURNAL_DIR`,
`DEFAULT_INBOX_PATH`, `DEFAULT_OUTBOX_PATH`, `DEFAULT_LISTEN_FLAG`, `DEFAULT_SCHEDULE_STATE_PATH`.
Everything else already derives from those (verified in the code): `mood.log`, `face.txt`, `image.txt`,
`usage-ledger.jsonl`/`usage-report.md`, `tool-log.jsonl`, `cache-log.jsonl`/`cache-report.md`,
`lumi.log` and the log-trim dir from `store_path.parent` (`core/agent.py` build, `tui/__main__.py`,
`tui/app.py`, `viewer/__main__.py`); the SQLite `<store>.db` (+ WAL) beside the store; the
`.pos`/`.sent`/`.spoken` pointers and the `telegram-*.log` files from the inbox/outbox paths. One root
moves all of it.

**What needs to be done:**
- `core/config.py`: resolve a **data root** first — `LUMI_HOME` set → `Path(LUMI_HOME).expanduser()`;
  unset → `_REPO_ROOT / ".lumi"` (exactly today). The seven mutable defaults derive from it, resolved
  inside `load_config()` (not frozen at import), so a test or process can set `LUMI_HOME` per run.
- Precedence, unchanged and pinned: an explicit per-path env (`LUMI_STORE_PATH`, `LUMI_FILES_DIR`,
  `LUMI_JOURNAL_DIR`, `LUMI_INBOX_PATH`, `LUMI_OUTBOX_PATH`, `LUMI_LISTEN_FLAG`, the schedule-state env if
  any) > `LUMI_HOME` > the in-repo default.
- **State vs code boundary:** canon, `inner_voice.md`, `styles.md`, `nudges.md`, `think_seeds.md`,
  `schedule.toml`, `emoji.md`, `natal.md`, `closeness.md`, `models.toml` and `viewer/faces` are authored
  code/assets — they stay repo-relative and never follow `LUMI_HOME`.
- Expose the resolved root on `Config` (e.g. `cfg.data_root`) for LUMI-209's guard.
- `scripts/migrate_store.py`: its `--store` default comes from `load_config().store_path` instead of the
  cwd-relative literal `.lumi/store.json`.
- `.env.example`: document `LUMI_HOME` (unset → in-repo `.lumi`).

**Dependencies:** None

**Expected result:**
`LUMI_HOME=~/lumi/prod/data` moves an instance's entire mutable state with one variable; unset, nothing
changes at all.

**Acceptance criteria:**
- [ ] The seven mutable defaults derive from the data root; every authored/code path stays repo-relative
- [ ] Precedence matrix unit-tested: per-path env > `LUMI_HOME` > default; `~` expanded
- [ ] `migrate_store.py --store` defaults to the configured store path
- [ ] **Tests:** `tests/unit/test_config.py` — the root resolution, the precedence matrix, the code-path
  boundary (canon etc. unaffected by `LUMI_HOME`); no model/network involved
- [ ] **Contract:** everything unset → every path literally equals today's `_REPO_ROOT/.lumi/...` value
  (a pinned contract test, `tests/contract/`), so in-place behavior is byte-identical
- [ ] **Gates:** `ruff` + `pytest`

### LUMI-208 — LUMI_ENV + the version badge in the status line

**Description:**
There must never be a doubt which Лілі is listening or what she runs. An environment name in config and a
leading badge in the TUI status line (`tui/app.py::_status_text`), with the version read from the
checkout's `VERSION` file.

**What needs to be done:**
- `core/config.py`: `LUMI_ENV` → `cfg.env` (stripped, lower-cased; unset/empty → `None`).
- The running version: read `_REPO_ROOT / "VERSION"` once (stripped; missing/unreadable → `None`), exposed
  on `Config` (e.g. `cfg.app_version`).
- `tui/app.py::_status_text`: when `cfg.env` is set, prefix the status line with a badge
  `prod v2.1.0` / `dev v2.1.0` (version omitted when unknown) — `prod` prominent (e.g. bold red), any other
  env dim. Present on every status variant (ready, busy, offline). `cfg.env` unset → the status line is
  **byte-identical** to today.
- The Telegram daemons (`telegram/inbound.py`, `telegram/outbound.py`) log `env=<env> version=<v>` in
  their startup line when the env is set (ids/counts only — the existing no-secrets logging rule).
- `.env.example`: document `LUMI_ENV`.

**Dependencies:** None

**Expected result:**
The prod TUI always shows `prod v<version>` at the start of its status line; dev shows `dev v<version>`;
with no `LUMI_ENV` nothing changes.

**Acceptance criteria:**
- [ ] Badge rendered on ready / busy / offline status variants; prod visually distinct from dev
- [ ] Version read from `VERSION`; a missing file degrades to the env-only badge, never an error
- [ ] Daemon startup lines carry env + version when set
- [ ] **Tests:** unit — the env parsing, the version read (present/missing), `_status_text` with prod/dev/
  unset (the TUI test harness, mock model)
- [ ] **Contract:** `LUMI_ENV` unset → `_status_text` output byte-identical to today (pinned)
- [ ] **Gates:** `ruff` + `pytest`

### LUMI-209 — The env guard — a marked data root, a clean tagged tree, at every entry point

**Description:**
The dev tree must be physically unable to open her real memory by accident, and prod must only ever run
released code. A data-root **marker** records which env owns a root; a pure **guard** checks the marker,
`LUMI_ENV` and the tree's git state; every process entry point that opens the root calls it. New module
`core/envguard.py` (pure decision + thin git glue).

**What needs to be done:**
- **Marker:** on the first run with `LUMI_ENV` set, write `<data_root>/env-marker` containing the env
  name. Never rewritten afterwards; `LUMI_ENV` unset → never written.
- **Pure decision** `check(env, marker, git_state) -> Ok | Refusal(reasons)` — refuse when:
  - the root is marked `prod` and `LUMI_ENV` is not `prod` (incl. unset) — dev can't open prod data;
  - `LUMI_ENV=prod` and the root is marked with another env — prod can't run on dev data;
  - `LUMI_ENV=prod` and the tree is not clean or HEAD is not **exactly at a tag**
    (`git describe --tags --exact-match HEAD`; tracked modifications via `git status --porcelain
    --untracked-files=no`) — prod runs only released code.
  - No `.git` / no `git` binary → treated as clean-and-tagged with a logged note (a future tarball install).
- **Refusal is readable:** one message naming each mismatch (marker env vs `LUMI_ENV`, the tag found or
  "not at a tag", the dirty files), the exit non-zero, never a silent start; the TUI prints it before the
  app mounts.
- **Deliberate override:** `LUMI_ALLOW_DIRTY_PROD=1` skips only the clean/tagged check (never the marker
  checks), logged loudly at WARNING on every start.
- **Wire it into every entry point** that opens the data root: `tui/__main__.py`, `telegram/inbound.py::run`,
  `telegram/outbound.py::run`, `voice/voicer.py::run`, `voice/dictator.py::run` (one shared helper, e.g.
  `envguard.enforce(cfg)`; core stays interface-independent — the helper returns/raises, the entry point
  prints).
- `.env.example`: document `LUMI_ALLOW_DIRTY_PROD` (emergencies only).

**Dependencies:** LUMI-207, LUMI-208

**Expected result:**
The dev tree pointed at the prod root refuses to start with a clear message; a dirty or untagged prod
checkout refuses to open her data; normal prod and dev runs start as before.

**Acceptance criteria:**
- [ ] The full decision matrix unit-tested with plain data: marker {none, prod, dev} × `LUMI_ENV`
  {unset, prod, dev} × git {clean+tag, dirty, untagged, no-git} → pass/refuse as specified
- [ ] Marker written once on the first `LUMI_ENV` run; never written when unset
- [ ] Override skips only the git check, logged at WARNING; refusal text names every mismatch
- [ ] All five entry points call the guard before touching the root
- [ ] **Tests:** unit — the matrix, the marker I/O (tmp dir), the git-state parsing (fake runner, no real
  git required); no model/network
- [ ] **Contract:** `LUMI_ENV` unset + an unmarked root → no guard effect, no marker, byte-identical start
  (pinned)
- [ ] **Gates:** `ruff` + `pytest`
- [ ] **Manual (owner):** run the dev tree with `LUMI_HOME` pointed at the prod `data/` → a readable
  refusal; run the prod checkout with a tracked file edited → a readable refusal

### LUMI-210 — The prod home — update script, operator guide, the one-time migration

**Description:**
The prod home outside `~/development`: `~/lumi/prod/{app/, .env, data/, backups/}` — `app/` is a git
checkout at a release tag (its uv venv at `app/.venv`, gitignored, untouched by checkout), `.env` holds
`LUMI_HOME=~/lumi/prod/data` + `LUMI_ENV=prod` + the keys (found by python-dotenv's walk-up from
`app/core/` — `app/` has no `.env`), `data/` is her memory. Code arrives **only** via a tag checkout; the
update script moves code, never data or config.

**What needs to be done:**
- `scripts/prod_update.py` (stdlib only, runs with any `python3`): `prod_update.py --home ~/lumi/prod
  --tag vX.Y.Z`:
  1. **refuse while prod processes run** (any process whose argv starts with `<home>/app/.venv/bin/python`) —
     the SQLite store runs in WAL mode (`store.db-wal`), so a live backup is not safe;
  2. tar-backup `data/` → `backups/data-<YYYYmmdd-HHMM>-<old-tag>.tar.gz`;
  3. `git -C app fetch --tags` → `git -C app checkout <tag>` (refuse an unknown tag);
  4. `uv sync --frozen --all-extras` in `app/` (the venv follows the tag's lock);
  5. print the running tag;
  6. **warn** about keys present in `app/.env.example` but missing from `<home>/.env` — compare keys only,
     never edit the file.
  `--dry-run` prints the steps. It never touches `data/` beyond reading it into the tarball, never writes
  `.env`.
- First-time install documented (clone at a tag into `app/`, `uv sync`, the `.env` template).
- `docs/PROD_SETUP.md` (operator style, like `docs/TELEGRAM_SETUP.md`): the layout; launching prod
  (`~/lumi/prod/app/lumi`, the Telegram daemons via `uv run python -m telegram.inbound|outbound` from
  `app/`); update; **rollback** (update to the previous tag + restore the matching backup); and the
  **one-time migration**: stop the TUI + both daemons → `tar` the in-repo `.lumi` (~324 MB today, incl.
  `store.db`/`-wal`/`-shm`) → move its contents into `~/lumi/prod/data` → write the prod `.env` → start
  prod and verify (`/mood`, a memory recall, a Telegram round-trip) → set `LUMI_ENV=dev` in the dev tree's
  `.env` (a fresh test store; the dev default profile on the cheap tier).
- `specification/ARCHITECTURE.md` §Configuration and secrets: the data root (`LUMI_HOME`), the env name +
  badge (`LUMI_ENV`), the guard; §Deployment and CI/CD: the local prod/dev split precedes the server.
  `CLAUDE.md` "How to work in this repo": never point the dev tree at prod data; prod changes only through
  a release tag.
- The migration itself is the owner's manual step, performed from the guide.

**Dependencies:** LUMI-209

**Expected result:**
Prod and dev run side by side the same evening; updating prod is one script run; editing the tree never
moves prod.

**Acceptance criteria:**
- [ ] `prod_update.py`: refuses with prod processes running; backup before checkout; unknown tag refused;
  `data/` and `.env` untouched; env-key diff warns only; `--dry-run` works
- [ ] `docs/PROD_SETUP.md` covers install, launch, update, rollback, migration; ARCHITECTURE.md + CLAUDE.md
  updated
- [ ] **Tests:** unit — the pure helpers of `prod_update.py` (env-key diff, backup naming, process-match on
  argv, tag validation) with fake runners; no real git/uv/network in CI
- [ ] **Gates:** `ruff` + `pytest`
- [ ] **Manual (owner):** the one-time migration done from the guide; prod (at a tag, real memory, badge
  `prod`) and dev (the tree, test data, badge `dev`) running side by side the same evening; `.env`
  discovery from `~/lumi/prod/app` resolves `~/lumi/prod/.env`; one update + one rollback rehearsed with
  `prod_update.py`

## v2.1 scope notes

**Phase DoD (ROADMAP.md §v2.1):** prod (on the tag, with the real memory) and dev (on the tree, test data)
run side by side the same evening; neither opens the other's root by accident; the badge always says which
one it is; editing the tree never moves prod.
**Contracts touched:** no ARCHITECTURE §Contracts item changes; two new pins — everything unset → today's
paths (LUMI-207) and today's status line + start (LUMI-208/209), byte-identical.
**Owner steps:** the one-time migration of `.lumi` into `~/lumi/prod/data` (stop everything first — WAL);
the prod `.env`; the side-by-side + update/rollback rehearsal. **Pre-release verification:** the prod
checkout needs a tag before `v2.1.0` exists — the owner verifies the DoD on an annotated pre-release tag
(e.g. `v2.1.0-rc1` at the execution head; the guard accepts any exact tag), and the final `v2.1.0` then
reaches prod through `prod_update.py` itself, rehearsing the update path. During the rc the badge reads
the tree's `VERSION` (still `1.6.3`) — expected.
**Not in this phase:** any server/socket work (v2.2+), two instances on the Linux box (v2.6), deploy
pipelines and automated promotion (v2.7), TLS and scans (v4.1). ARCHITECTURE.md / CLAUDE.md / feature specs
still carry the pre-restructure version numbers outside the sections this phase edits — a separate docs
renumbering, not this phase.
