## Findings

### 1. 🟡 LOW — a download and a picture shown to her never reach `actions.jsonl`

**Where:** `files_download`, `turn` and `turn_stream` in [server/app.py](../../../server/app.py).

**Failure scenario:** ROADMAP §v4.5 says every action is logged ("Every action is in `actions.jsonl`"). The server
logs its four writes only. A file saved to `~/Downloads` and a picture sent with «Show to Lili» leave no line, so the
log can't answer "what left her sandbox" or "what did I show her". «Open in browser» never reaches the server and
can't be logged there.

**Proposed fix:**
- log `download` with the path and size;
- log `show` once per picture, and only for a fresh turn, so a retried `turn_id` doesn't log twice;
- skip the line when no log is configured;
- ARCHITECTURE: "every successful write, download and shown picture".

### 2. 🟡 LOW — Restore is offered for an item inside a trashed folder

**Where:** `openRowMenu` in [desktop/ui/app.js](../../../desktop/ui/app.js); `restore` in
[core/actions.py](../../../core/actions.py).

**Failure scenario:**
1. Trash the folder `notes`, which moves to `.trash/2026-11-19/notes/`.
2. Open it in Files and pick «Restore…» on `ideas.md` inside it.
3. The log has no line for `.trash/2026-11-19/notes/ideas.md`, so the server answers 409 «where it came from is
   unknown». Its old folder is gone anyway, because it is the trashed one.

**Proposed fix:** offer Restore only on the items directly inside a day folder (`.trash/<date>/<name>`), the ones the
log knows.

### 3. 🟡 LOW — a file over 10 MB is sent whole before it is refused

**Where:** `uploadFiles` in [desktop/ui/app.js](../../../desktop/ui/app.js); the proxy's body cap.

**Failure scenario:**
- Dropping a 40 MB video sends all 40 MB to the proxy, which reads and drops it, then answers 413.
- Over 64 MB the proxy stops reading and closes the connection. The page then shows a network error («Failed to
  fetch») instead of "too large".

**Proposed fix:** the page refuses a file over 10 MB (the server's largest cap) before sending it, with the same «too
large» reason. The server's exact caps still decide the rest.

### 4. 🟡 LOW — a markdown link in the chat shows only its label

**Where:** `chatLink` in [desktop/ui/app.js](../../../desktop/ui/app.js).

**Failure scenario:**
- A news or web body that tried to steer her could make her write `[Guardian](https://elsewhere.example)`.
- The chat shows «Guardian»; the address is visible only in the hover title and, after the click, in the browser.
- The reader already shows the address beside the label.
- This dates from v2.12; LUMI-326 only routes the click through the proxy. The browser shows the real address, and
  nothing opens without the owner's click.

**Proposed fix:** show the host after a label that differs from the address (`Guardian ↗ elsewhere.example`), as the
reader does. Backlog: it changes how her replies look, so the owner decides.

### 5. 🟡 LOW — rename and restore check the target, then move

**Where:** `rename` and `restore` in [core/actions.py](../../../core/actions.py).

**Failure scenario:**
- Both check `target.exists()` and then call `Path.rename`, which on POSIX replaces a file that appears in between.
- The actions don't take the turn lock (by design: they never wait for a turn). So in theory her `create_file` could
  make the same name in that instant, and the owner's rename would replace it.
- The upload is safe: it opens with `"xb"`.

**Proposed fix:** a no-replace move (`os.link` + `os.unlink` for a file, or `renameat2(RENAME_NOREPLACE)` on Linux).
Cleanup: the window is microseconds wide and needs both writers on one name at once.

## What's solid

- **One guard, no way out:**
  - every action resolves its path through `safe_path`, and an entry that is itself a link is refused;
  - the root can't be moved, and a restore can't land in the trash or on the root;
  - tests cover a link out, a link inside, a folder that is a link, `..`, an absolute path and a NUL byte.
- **Never an overwrite, never a deletion:**
  - an upload opens `"xb"` under a free name, retried if the name is taken between the look and the write;
  - the trash is an ordinary folder;
  - the unit tests hold the rest of the sandbox byte-identical after each action.
- **The room never writes:** the room's token gets 403 on all five routes (and on `sandbox_images` through its
  channel), no token 401. Nothing changes and no log line is written.
- **The Mac's side:**
  - `/local/save` names the file from the path's last segment through `clean_name` (no slash, no leading dot) and
    writes create-only;
  - `/local/reveal` shows only a file this proxy saved;
  - `/local/open` takes `http` / `https` with a host and no whitespace;
  - all three need the window's key.
- **No content in the log:** a line holds `{ts, action, path, to, size, client}` only, and the test checks that an
  uploaded text's words are not in it.
- **Pictures she can't see are refused, not lost:** with `image.enabled` off, `sandbox_images` answers 422 before
  any model call.

## Fixes applied

### #1 — a download and a shown picture are logged (8cafdc8)

- **Change:**
  - `/v1/files/download` logs `download` with the path and size;
  - both turn routes log `show` once per picture of `sandbox_images`, and only when `begin_turn` runs the turn (a
    retried `turn_id` returns the stored outcome and logs nothing);
  - `_log` skips the line when no log is configured, so a download is still served without one.
- **ARCHITECTURE:** the v4.5 paragraph names the three kinds of line.
- **Regression test:** `test_review_v45_1_a_download_and_a_shown_picture_are_logged_once`:
  - two pictures shown, then the same `turn_id` again, then a streamed turn give exactly three `show` lines, with no
    content;
  - a server without a log still serves the download.
  - `test_v45_rename_trash_restore_and_download` now expects the `download` line too.

### #2 — Restore only where the log knows the origin (80f8909)

- **Change:**
  - `rowEntries` decides a row's menu: Restore only on `.trash/<date>/<name>`;
  - nothing to rename or trash inside the trash;
  - a row with no action (`.trash`, a day folder) gets no ⋯ button, instead of opening an empty menu (found while
    checking the fix).
- **Regression test:** `test_review_v45_2_restore_is_offered_only_where_the_log_knows_the_origin`.
- **End to end in headless Chrome** (the folder `notes` trashed):
  - no ⋯ button in `.trash/`;
  - «Restore…» on the trashed folder;
  - only «Download» on a file inside it.

### #3 — a file over 10 MB is never sent (675fa8f)

- **Change:** `uploadFiles` refuses a file over `UPLOAD_MAX_FILE` (10 MB, the server's largest cap) before any
  request, with «larger than 10 MB, the largest file she takes». The other files of the same drop still go.
- **Regression test:** `test_review_v45_3_a_file_over_the_largest_cap_is_never_sent`. It checks:
  - the size check comes before the fetch;
  - the page's bound equals `core.actions.UPLOAD_MAX_PICTURE`;
  - the string is in English.
- **End to end:** an 11 MB file and a small one dropped together. The small one was uploaded, the large one was
  named in the notice and never reached the server: the log shows one upload.
