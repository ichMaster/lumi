## Findings

### 1 — 🟠 MEDIUM — a rollback of an older entry undoes the later changes too, unseen

`admin/edit.py:388` `plan_rollback` restores each file the entry changed **as a whole** — the text from before that
entry. `admin/static/app.js:374` applies it at once: no diff, and on dev `askConfirm` returns `undefined`, so one click
writes.

**Failure scenario:**
1. History on dev: `ts1` `persona.think_show` → `open`, then `ts2` `instance.log_level` → `WARNING` (both in
   `settings.yaml`).
2. The owner wants `think_show` back and clicks "Roll back" on `ts1`.
3. `settings.yaml` goes back to before `ts1`, so `log_level` is reverted too, and dev restarts.

The same happens with `secrets.yaml`: rolling back an older secret entry also undoes a later rotation, and every
client loses its token. Each change is undone without a preview. Every other write in the panel has a preview.

**Fix:**
- `plan_rollback` names the later entries that touched the same files (a note: "this also undoes the later changes
  …").
- A `POST /api/history/{i}/{ts}/preview` returns the plan's preview (the diff, the changes, the notes, the hashes).
- The apply takes the preview's hashes, so a change in between is refused as stale.
- The UI previews first, shows the changes and the note in the confirmation on dev as on prod, and then applies.

### 2 — 🟠 MEDIUM — an applied change can go unaudited, or be reported as "not running"

In `admin/app.py:182`, `restart_running` catches only `ct.Refused` and `OSError` from `runner.act`. The Docker seam
can also raise `ValueError` (bad JSON from `_containers`) and `http.client.HTTPException` (`BadStatusLine`,
`IncompleteRead`). Either one escapes `write()` after `ed.apply` has written the files and the history entry. FastAPI
answers 500, and `record()` never runs.

Separately, `runner.list` reports `unknown` when Docker can't be asked. `restart_running` treats anything except
`running` as stopped and says "not running — reads the new settings when started".

**Failure scenarios:**
- *Docker drops the connection mid-restart:* the owner sees a 500. The audit log has no line for a change that is in
  the files.
- *The socket is briefly unreachable:* the apply says done, and every service is shown as "not running". In fact her
  server runs on with the old settings, and nothing is marked failed.

**Fix:** every Docker error during the restart becomes that service's `failed: …` (it lands in the audit result
`done; restart {…}`), and `unknown` becomes `failed: Docker can't say whether it runs — restart it from Services`.

### 3 — 🟡 LOW — the alert detail is capped before it is redacted

In `admin/alerts.py:150`, `_short(r.detail)` cuts each detail to 120 characters, and `_send` redacts the joined
message afterwards. When a secret straddles the cut, the message keeps the secret's first characters. The redactor
matches whole values only, so it can't find a truncated one.

The test `test_a_message_is_redacted_and_its_details_capped` puts the secret past the cap, so it passes by accident.

**Fix:** redact each detail first, then cap it. The test then places the secret across the cut.

### 4 — 🟡 LOW — promote checks only prod for staleness

`app.py:305` passes prod's hashes, and `plan_promote` re-reads dev at apply time. If dev changed after the preview, the
apply writes the new dev value to prod. The result's `changes` show it, but only after the write. With one owner and
one browser this is unlikely.

**Home: backlog.** The fix is dev's hashes in the preview, checked by the apply.

### 5 — 🟡 LOW — a panel restart of prod can raise an alert pair

A prod settings change restarts her server, and the graceful close can take a while. A health run inside that window
sees `server` red and sends "failing", then "recovered" on the next run.

**Home: backlog.** The fix is to suppress alerts for an instance for a few minutes after the panel restarts it.
LUMI-265's live run shows whether it happens in practice.

### 6 — 🟡 LOW — the agent's tick reports failure while the panel holds the lock

The guard works as designed: the agent's `LOCK_EX | LOCK_NB` fails while a panel action runs. But `deploy_agent.py`
returns 1 for it, so the timer's unit shows `failed` for that tick, and the next tick runs normally.

**Home: backlog.** A busy lock could exit 0 for `tick` only.

## What's solid

- **Secrets stay write-only end to end.** They appear:
  - in the view as set / last4;
  - in the diff as key-level lines;
  - in `changed()` and the history manifests as `(secret)`, which covers a secret misplaced in `settings.yaml`;
  - in previews and refusals redacted with the old and the new values;
  - in the audit as `(secret)`, plus the redactor.

  `parse_yaml` never quotes PyYAML's snippet of a line.
- **An invalid value never reaches a file.**
  - Every plan runs the instance's own start check (`check_texts`).
  - `set_in_text` / `unset_in_text` / `set_section` verify by re-parsing and refuse an unusual layout instead of
    rewriting it.
  - The apply re-reads under a lock and refuses a stale preview.
- **The prod confirmation comes first.** It is checked before the lock and before any plan; a cancelled prompt sends
  nothing.
- **The lock guard works both ways.** It uses a read-only descriptor with `LOCK_SH`, and the agent opens its lock
  with `"w"` (the same inode), so the read-only bind stays valid. An unreadable lock fails closed.
- **The mounts are right.** The instance folders are writable, each `data/` is read-only on top, and
  `create_host_path: false` makes a missing lock loud. Both are pinned by `test_admin_compose.py`.
- **History.**
  - Copies are 0600 and the manifests are atomic.
  - The prune touches only an entry's own manifest and copies, also with `-n` suffixes.
  - A rollback is itself a history entry.
- **Alerts never block the health runner.** The hook's exceptions are swallowed, the sender never raises, and the
  token is only in the URL path.

## Architecture impact

- **A new admin route.** `POST /api/history/{instance}/{ts}/preview` is behind the admin token, like every `/api`
  route, and is pinned by `test_admin_contract.py` test 1.
- **Rollback behaviour.** A rollback now names the later changes it undoes, and its apply refuses a stale preview
  when hashes are given. ARCHITECTURE §Deployment v2.11 says so.
- **Restart reporting.** A restart failure after an apply is always reported per service and audited, never a 500.
