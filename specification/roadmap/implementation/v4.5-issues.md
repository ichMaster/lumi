# v4.5 — Issues

Issues for phase **v4.5 — Actions from the window** (version **v4 — The window: her files, pictures, journal and
thoughts in Lili.app**), derived from the Tasks and DoD in [ROADMAP.md](../../ROADMAP.md) §v4.5 (the five actions the
owner chose on 2026-11-19), the concept [DESKTOP_VIEWS.md](../../features/DESKTOP_VIEWS.md) §Actions and the contracts
in [ARCHITECTURE.md](../../ARCHITECTURE.md). This file covers one phase; ids continue from the previous phase
(LUMI-320 → **LUMI-321…325**).

v4.5 lets the owner act on her sandbox from the window:
- **upload** a file or a picture from the Mac;
- **"show this to her"** — a sandbox picture as a turn's image;
- **download** a file to `~/Downloads`;
- **open an external link** in the browser;
- **rename**, and **move to trash** with **restore**.

It builds on v4.1–v4.4 (the sandbox reads and their guard, the owner-only routes, the Files view and the reader, the
full picture view, the proxy's key guard and binary relay) and on the v0.22 image turn. It leaves her voice (v4.6)
and dictation (v4.7) to the next phases.

**Reconciled against the code (2026-11-19):**
- **One guard for every write:** `core/files.py` `safe_path` (no `..`, no absolute path, no link out). The read side
  wraps it in `core/browse.py` `_resolve` / `_inside` and types pictures by magic bytes (`picture_type`). The write side
  reuses them; her own tools (`create_file`, `append_file`) stay as they are.
- **A turn's image** is a provider-neutral block, `core/images.py` `image_block(bytes, media_type) → {type,
  media_type, data}`. `TurnRequest.images` carries such blocks into `Core.reply(..., images=...)`; the room's turn
  refuses images (422). "Show this to her" adds `sandbox_images: [path]`: the server builds the blocks itself from
  the v4.1 picture read (`read_picture`, ≤ 10 MB, magic bytes), so the window never sends the bytes.
- **The proxy** (`desktop/proxy.py`):
  - forwards exact `(method, path)` pairs plus `FORWARDED_PATTERNS`;
  - refuses a request body over `MAX_BODY` (1 MB) — the upload route needs a larger cap of its own;
  - already serves local routes behind the window's key (`/face`, `/emoji`) — the save and open routes follow that
    pattern.
- **The data root is the server's:** `server/__main__.py` passes `thumbs_dir_of(cfg)` into `create_app`. The action log
  `<data root>/actions.jsonl` is passed the same way (`actions_log_of(cfg)`), outside her sandbox.
- **Dot folders are not hidden today.** Her file tools and Files list `.trash/` like any folder, and the gallery walk
  (`os.walk`) would show a trashed picture. The ROADMAP keeps the trash an ordinary folder in her sandbox. The Gallery
  skips `.trash/`, so a trashed picture leaves it (LUMI-322). Her tools are unchanged.
- **The reserved places in the window:**
  - Files' header `vactions` (the folder's actions);
  - the Gallery's header `vactions`;
  - the picture view's «Actions · later» area (`pvlater`).

  No design strings exist for the actions; the window's English strings are written with the features.
- **Your line in the chat:** a client turn pushes your line as a `message` (`role: user`). With `sandbox_images` it
  carries `pictures` too, as her lines do since v4.2, so another window sees what you showed her.

## v4.5 — Actions from the window

### LUMI-321 — The write side in core: upload, rename, trash and restore over the sandbox guard; the action log

**Description:**
The owner's write actions on one sandbox, beside the read side: `core/actions.py` (new), reusing `core/files.py`
`safe_path` and `core/browse.py`'s guard and picture typing.

**What needs to be done:**
- `clean_name(name) -> str`:
  - one path segment, no `/` or `\`, no leading dot, no control characters;
  - at most 120 characters, keeping the extension;
  - an empty or dot-only name is refused (`BadPath`).
- `free_name(folder, name) -> str`: the name itself if free, else `stem (2).ext`, `stem (3).ext` …
- `upload(root, folder, name, data) -> {path, size}`:
  - the folder must exist inside the sandbox (`""` the root);
  - pictures (png / jpeg / gif / webp by magic bytes) up to 10 MB; UTF-8 text without NUL up to 1 MB; anything else
    `NotServed` (415);
  - a size over the cap is `TooLarge`;
  - create-only (`open(..., "xb")` on `free_name`), never an overwrite; nothing else in the sandbox changes.
- `rename(root, path, name) -> {path, to}`:
  - a file or a folder, within its folder;
  - the new name cleaned and free, else `Conflict` (a new `BrowseError`, 409);
  - never the root, never out of the sandbox.
- `trash(root, path, today) -> {path, to}`:
  - moves into `.trash/<YYYY-MM-DD>/<free name>`;
  - refuses the root, `.trash` itself, and anything already in the trash.
- `restore(root, path, original) -> {path, to}`:
  - moves an item from `.trash/` back to `original`;
  - `original` must be free and its folder must exist (else `Conflict`).
- `ActionLog(path)`:
  - `append({ts, action, path, to, size, client})` writes one JSON line, never any content;
  - `original_of(trashed_path)` returns the latest trash entry's `path` for a trashed item, for restore.
- No deletion anywhere; every path through the guard; links out never followed.

**Dependencies:** None

**Expected result:**
The core can bring a file in, rename it, move it to the trash and back, logging each action, without ever
overwriting or deleting anything.

**Acceptance criteria:**
- [ ] Upload:
  - writes a picture and a text file under a free name;
  - a clash gets `(2)`;
  - an SVG, a binary, an oversize file and a missing folder are refused;
  - the other files are byte-identical.
- [ ] Rename refuses a taken name, `..`, `/`, a dot name and the root.
- [ ] Trash moves into `.trash/<date>/`; restore brings it back to where the log says it was, refused when that place
  is taken.
- [ ] A link out of the sandbox is never followed by any action.
- [ ] Each action appends exactly one log line, with no file content.
- [ ] **Tests:** `tests/unit/test_actions.py` (tmp sandboxes; the sandbox fingerprinted before and after).
- [ ] **Gates:** `uv run ruff check .`, `uv run pytest -q`.

### LUMI-322 — The routes: upload, download, rename, trash, restore; `sandbox_images` on a turn; `features.actions`; the API contract

**Description:**
The owner's write routes and the download in `server/app.py` over LUMI-321, the turn's `sandbox_images`, and the
contract in ARCHITECTURE and DESKTOP_VIEWS.

**What needs to be done:**
- `server/app.py`:
  - `POST /v1/files/upload?path=<folder>&name=<name>`: the raw body (read with a cap: at most 10 MB + 1 byte, so an
    oversized body is refused without being held whole) → `upload` → `{path, size}`;
  - `POST /v1/files/rename {path, name}`, `POST /v1/files/trash {path}`, `POST /v1/files/restore {path}` (restore reads
    the original from the action log);
  - `GET /v1/files/download?path=`: any regular file up to 50 MB, `Content-Disposition: attachment;
    filename*=UTF-8''…`, `nosniff`, `private`;
  - all: the owner's token (the room's 403), the v4.1 error mapping plus 409 for `Conflict`, `no-store`, never the turn
    lock. Every successful write is logged with the request's `X-Lumi-Client`.
  - `features.actions` (the sandbox and the log both configured).
  - The turn routes (`/v1/turn`, `/v1/turn/stream`) take `sandbox_images: [path]`:
    - at most 4;
    - each read with `read_picture` and turned into `image_block`s, added to `images`;
    - a bad path → 400 before the turn runs; the room's channel refuses them (422).

    Your `message` push for such a turn carries `pictures`.
- `server/__main__.py`: `actions_log_of(cfg)` → `<data root>/actions.jsonl`, passed into `create_app`.
- `core/gallery.py`: the walk skips `.trash/`.
- `specification/ARCHITECTURE.md` §Contracts: a "v4.5 (additive)" paragraph — the routes, the caps, create-only,
  nothing deleted, the log, `sandbox_images`, `features.actions`.
- `specification/features/DESKTOP_VIEWS.md`: the routes.
- `tests/contract/test_server_api_contract.py`:
  - the route set and `features`;
  - every route's 401 and the room's 403;
  - upload create-only and its caps (413 / 415);
  - rename and trash and restore, and 409 on a clash;
  - download's headers;
  - the log lines;
  - `sandbox_images` reaching the mock model as an image block, and your `message` carrying `pictures`;
  - the room refusing them;
  - the rest of the sandbox byte-identical;
  - a write answers while the turn lock is held.

**Dependencies:** LUMI-321

**Expected result:**
The owner's actions exist over the API, owner-only, create-only, logged, and never deleting.

**Acceptance criteria:**
- [ ] The five routes answer with their shapes; `features.actions`.
- [ ] Every write route: 401 without a token, 403 for the room.
- [ ] Upload never overwrites; the caps hold; an oversized body is refused while streaming.
- [ ] A turn with `sandbox_images` gives the model the picture; a bad path is 400; the room refuses them.

### LUMI-323 — The proxy: the new routes, the upload's body cap, saving to `~/Downloads`, opening a link in the browser

**Description:**
`desktop/proxy.py`: forward the five routes, let the upload's body reach 10 MB, and two local routes behind the
window's key.

**What needs to be done:**
- `FORWARDED`:
  - `POST /v1/files/upload`, `/v1/files/rename`, `/v1/files/trash`, `/v1/files/restore`;
  - `GET /v1/files/download`, its body relayed as bytes with its headers (`Content-Disposition` already passes).
- The body cap: 10 MB + a little for `POST /v1/files/upload` only; 1 MB everywhere else, as today.
- `POST /local/save {path}` (the key):
  - fetches `/v1/files/download` from the server with the token;
  - writes the file into `~/Downloads` under a free name (create-only);
  - answers `{saved: "<path>"}`.
- `POST /local/reveal {saved}` (the key): shows a file this proxy saved in Finder (`open -R`), only a path it saved.
- `POST /local/open {url}` (the key): `http` / `https` only, opened with `webbrowser.open`; anything else 400. Never a
  `file:` / `javascript:` URL, never a sandbox path.
- The local routes answer only to the window's key and `Host`, as `/face` does. The downloads folder is injectable for
  tests.

**Dependencies:** LUMI-322

**Expected result:**
The page can upload through its proxy, have a file saved on the Mac, and open a link in the browser, without the
token or the disk ever reaching the page.

**Acceptance criteria:**
- [ ] The forwarded set is pinned; the download relays byte for byte with its headers.
- [ ] A 9 MB upload passes the proxy; an 11 MB one is refused; another route still refuses 2 MB.
- [ ] Save writes into the downloads folder under a free name, never overwriting.
- [ ] Open refuses anything but http / https.
- [ ] All three local routes refuse a request without the key.
- [ ] **Tests:** `test_desktop_contract.py`, `test_desktop_proxy_flow.py` (a fake server; a tmp downloads folder; a fake
  opener).
- [ ] **Gates:** `uv run ruff check .`, `uv run pytest -q`.

## v4.5 scope notes

**Critical path:** LUMI-321 → LUMI-322 → LUMI-323 → LUMI-324 → LUMI-325.

**Phase DoD (ROADMAP.md §v4.5):**
- **Upload:** the owner uploads a picture and a text file; they appear in Files and she can read them. A taken name
  gets a new name; a file too large or of another kind is refused.
- **"Show to Lili":** sends a sandbox picture with a line, and she answers about it.
- **Download:** any file lands in `~/Downloads`.
- **Links:** an external link opens in the default browser, and nothing but http / https does.
- **Rename and trash:** both ask first; trash moves into `.trash/`, restore brings it back, and nothing is ever deleted.
- **Safety:** every action is in `actions.jsonl`; the room's token gets 403 on every write route; the other files stay
  byte-identical.
- **(Manual, owner)** on prod.

**Contracts touched:** the Server API v1 (additive: five routes, `sandbox_images` on the turn routes, `pictures` on your
`message` push, `features.actions`), pinned by `tests/contract/test_server_api_contract.py`, with ARCHITECTURE
§Contracts "v4.5 (additive)"; the proxy's forwarded routes and local routes, pinned by `test_desktop_contract.py`. No
change to the emotion contract, the memory records, the isolation invariant or the Agora space API. Her own file tools
stay non-destructive.

**Owner steps:** the manual checks — on dev before the release, then on prod after it (deployed without asking).

**Not in this phase:**
- her voice in the window (v4.6) and dictation (v4.7);
- hiding `.trash/` from her own file tools;
- deleting anything for good;
- uploading folders;
- editing a file's text in the window.

**Generated later:** `v4.5-github-report.md` (on upload), `v4.5-execution-report.md` (on execution).
