## Findings

### 1. 🟠 MEDIUM — a picture name with a space is cut at the space

**Where:** [core/agent.py:2080](../../../core/agent.py#L2080) (`capped`, LUMI-306) and
[core/agent.py:2127](../../../core/agent.py#L2127) (`_emit_image_display`, v0.23).

**Failure scenario:**
1. She calls `generate_image` with `filename: "мій кіт.png"`. The tool takes any name inside `art/`, and a Ukrainian
   name with a space is a plausible choice.
2. The tool saves `art/мій кіт.png` and returns `created art/мій кіт.png (1234 bytes)`.
3. The core reads the path as `result.split(" ", 2)[1]`, which is `art/мій`.
4. `Core.last_pictures` is `["art/мій"]`. The turn's outcome and her `message` carry that path. The window asks
   `/v1/files/raw?path=art/мій`, gets 404, and shows a broken picture named `art/мій`. The picture she made never
   shows in the chat.

The v0.23 display signal (`LUMI_IMAGE_SHOW` = viewer / telegram) has the same parse, so it names a file that doesn't
exist either.

Reproduced with the test fixtures: `last_pictures` is `['art/мій']` while the disk holds `art/мій кіт.png`.

**Proposed fix:** one parser for the tool's result, `created <path> (<n> bytes)`, that keeps the whole path, used at
both places. A regression test with a name that holds spaces.

### 2. 🟡 LOW — thumbnail decodes have no concurrency bound

**Where:** [core/gallery.py:180](../../../core/gallery.py#L180), the thumbnail route in `server/app.py`.

**Failure scenario:** a 10 MB source may still be up to 50 megapixels, which is about 200 MB once decoded as RGBA. The
Gallery asks for every thumbnail near the screen at once, and FastAPI runs the sync route on a thread pool of 40. A
folder of such pictures would decode many at the same time on the box. Today her pictures are the 768–1024 px PNGs her
image tool makes, so a decode is a few MB.

**Proposed fix:** a small semaphore around `_make_thumb` (for example 2), or a lower pixel cap. The home is v4.5,
where uploads bring pictures of any size into the sandbox.

### 3. 🟡 LOW — every page walks the sandbox again

**Where:** [core/gallery.py:142](../../../core/gallery.py#L142).

**Failure scenario:** each `/v1/images` request walks up to 10,000 files, opens each one for 12 bytes, sorts, and
reads up to 100 headers. Her sandbox holds a few hundred files, so a page costs milliseconds. At thousands of pictures,
paging through all of them repeats the walk per page.

**Proposed fix:** none now. The v9.1 gallery store indexes her pictures.

### 4. 🟡 LOW — the Gallery doesn't show `truncated`

**Where:** `renderGallery` in [desktop/ui/app.js](../../../desktop/ui/app.js).

**Failure scenario:** past 10,000 files the listing is cut and `truncated` is true. Files shows its cut line, but the
Gallery shows the partial set as if it were all of them.

**Proposed fix:** a line under the header when `truncated` is true, with a string from the design. No design string
exists yet, so it goes to the backlog.

### 5. 🟡 LOW — stale thumbnails of removed pictures stay in the cache

**Where:** `_store` in [core/gallery.py:248](../../../core/gallery.py#L248).

**Failure scenario:** a picture changed in place replaces its old thumbnail. A picture removed or renamed by hand leaves
its thumbnail in `<data root>/cache/thumbs/<user_id>/`. Her own tools never delete or rename, so this happens only by
hand. A thumbnail is about 10 KB.

**Proposed fix:** a sweep of cache files whose source is gone, for example in `lumi-cli`. Backlog.

### 6. 🟡 LOW — → at the end can do nothing while a page loads

**Where:** `stepPicture` and `galleryLoad` in [desktop/ui/app.js](../../../desktop/ui/app.js).

**Failure scenario:** the picture view is open on the last loaded picture while the grid's scroll listener has already
started the next page. `galleryLoad` is busy, so it returns `false`, and → does nothing. A second press after the page
lands works.

**Proposed fix:** let `galleryLoad` hand back the page already in flight instead of `false`. Cleanup.

## What's solid

- **Read-only and inside the sandbox:**
  - the gallery reads through the v4.1 guard (`_resolve`, `_inside`) and never follows a linked folder out;
  - FIFOs and devices are skipped by `S_ISREG` before any open;
  - the only write is the thumbnail, into a cache that is refused if it sits inside the sandbox.
- **Bounded:**
  - the walk stops at 10,000 files and a page holds at most 100 pictures;
  - a source over 10 MB or 50 megapixels (read from the header) is refused before any decode;
  - Pillow's decompression-bomb error maps to 413.
- **The routes:**
  - both are owner only; the room token gets 403;
  - they are read-only and never take the turn lock, and they make no model call;
  - errors map through the same `BROWSE_STATUS` as v4.1, and an absolute path never appears in an error line.
- **`pictures` is right on every path:**
  - the list resets at the start of every `reply`, and every published line of hers runs through `reply` under the
    service lock (the client turn, the inbox turn, the spoken turn), so a thought's picture never lands on a later line;
  - the field is absent when there are none, so outcomes stay byte-identical;
  - the TUI client reads only the keys it knows.
- **The page:**
  - every picture reaches it through `fetch` with the key into a blob: URL; the picture view keeps one picture at a
    time and releases it on each step and on close;
  - the dialog keeps the focus inside, gives it back on Esc, and stays open across a re-render (`paint`).

## Fixes applied

### #1 — a picture name with a space (ac30b48)

- **Change:** `core/agent.py` has one parser for `generate_image`'s result, `_created_path`. It reads the whole path
  from `created <path> (<n> bytes)` and returns `None` for any other result. Both `Core.last_pictures` and the v0.23
  display signal use it, so `_emit_image_display` now takes the path instead of the raw result.
- **Regression tests** (`tests/unit/test_turn_pictures.py`):
  - `test_a_name_with_spaces_keeps_its_whole_path`: a turn makes `art/мій кіт на даху.png`; the turn's pictures and
    the display signal both name that file. Without the fix the test fails with `['art/мій']`.
  - `test_created_path_reads_the_whole_path_or_nothing`: a name with brackets and spaces, an error result, and a
    result without the byte count.
- **Verification:** ruff clean; **3054 passed**.

## Architecture impact

None. The `pictures` contract is unchanged; the fix makes it name the file the tool saved.
