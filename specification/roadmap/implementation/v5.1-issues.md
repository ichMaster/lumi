# v5.1 — Issues

Issues for phase **v5.1 — Usage analytics: every paid call, its origin, her tools** (version **v5 — The admin panel
II: the server and the agent**), derived from the Tasks and DoD in [ROADMAP.md](../../ROADMAP.md) §v5.1, the concept in
[ADMIN_PANEL_II.md](../../features/ADMIN_PANEL_II.md), the design in [design/v5/handoff/](../../../design/v5/handoff/README.md)
(with its adaptation at the end of [design/v5/BRIEF.md](../../../design/v5/BRIEF.md)) and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md). This file covers one phase; ids continue from the previous phase (LUMI-339 →
**LUMI-340…345**).

The phase records every paid call and every tool call once, in the instance that makes it (the origin and the channel
on the model-call records, a media ledger, a tool ledger, the channel on each message), rolls them up in the panel's
own folder so the history outlives the 10-day trim, and replaces the v2.10–v2.11 page with the v5 design's shell, the
first Overview and the Usage and Tools views. The health history, logs, alerts, the audit and every agent view beyond
usage and tools are later phases (v5.2–v5.10); they get a place in the shell, not their content.

## v5.1 — Usage analytics: every paid call, its origin, her tools

### LUMI-340 — The usage origin and channel: every model call and every message says what started it

**Description:**
Every model call record (`cache-log.jsonl`, written by `Core._log_one_cache_event` in `core/agent.py` and
`AgoraSpace._log_usage` in `core/space.py`) gains `origin` and `channel`, and every stored message gains `channel`
(`Message` in `core/repository.py`). The entry points that start work say what started it: the server's turn
(`server/app.py` `_run_turn`), the brain's Telegram line, scheduled row, idle think and nudge (`server/brain.py`),
the typed directive (`/v1/command`, the TUI), the room and her initiative (`core/space.py`). The TUI client and the
CLI name themselves with the prefixes `tui-` and `cli-`.

**What needs to be done:**
- A small core module (e.g. `core/usage_origin.py`) with the pure pieces:
  - `channel_of(client_id)`: `desktop-` → `window`, `tui-` → `tui`, `cli-` → `cli`; a missing or unprefixed id →
    `api`;
  - the current work's origin and channel as a context the core reads when it records (a `contextvars` value set by
    the entry point for the work's duration, so the core stays interface-independent and no signature fans out);
  - the housekeeping rule: a call whose `kind` is `mood`, `session-start`, `session-close`, `compaction` or `fact` is
    `housekeeping:<kind>` whatever started the work around it.
- The origins (ADMIN_PANEL_II §Every paid call), set at the entry points:
  - `turn` with the channel: the server's `_run_turn` (the channel from `origin_of(x_lumi_client)`), the brain's
    `_inbox_turn` (`telegram`; a Telegram voice note is `telegram` too), an in-process TUI turn (`tui`);
  - `directive:<name>`: a `%directive` the owner typed (`POST /v1/command`, the TUI's `run_directive`);
  - `schedule:<row>`: the brain's `_run_scheduled` (the entry's `name`, else its directive) and the spoken turn it may
    graduate to;
  - `idle`: the brain's `_maybe_think` and `_maybe_nudge` (the v0.12 idle think and the v0.4 nudge, outside the
    schedule). **New** beside the concept's table: add it to ADMIN_PANEL_II's origin table;
  - `room` and `initiative`: the space's own calls (`AgoraSpace._log_usage`; `self.channel` tells them apart), channel
    `agora`.
- `CacheEvent` gains `origin: str = ""` and `channel: str = ""` (added to `_FIELDS`); older records load with `""`.
  The cache report (`_render_cache_report`) is unchanged.
- `Message.channel: str | None = None` (additive). `Core.reply` stamps both messages of the turn with the context's
  channel; a spoken turn of hers (a graduated thought, a nudge) stores none. Both stores already ignore unknown fields
  and serialize with `asdict`, so older records load as `None`.
- `tui/remote.py`: `client_id = "tui-" + uuid4().hex[:12]`. The CLI sends `X-Lumi-Client: cli-<hex>` on its server
  calls (`cli/main.py`).
- ARCHITECTURE: §Contracts — the model-call record's `origin` / `channel`, `Message.channel`, the prefixes and the
  origin values; the v5.1 line under the admin panel.

**Dependencies:** None

**Expected result:**
Every model call and every stored message says what started it and through which channel, and nothing else about a
turn changes.

**Acceptance criteria:**
- [ ] A turn from the window records `origin: turn, channel: window` on each of its model calls (the reply and its
      tool rounds) and `channel: window` on both messages; the mood call inside it records `housekeeping:mood`.
- [ ] A Telegram line, a scheduled row, an idle think, a typed directive and a room call each record their origin.
- [ ] A missing or unprefixed `X-Lumi-Client` is `api`; the TUI client's and the CLI's ids carry their prefixes.
- [ ] A recorder failure never breaks a turn (the existing `cache-log` rule holds for the new fields).
- [ ] **Tests:** unit — `channel_of` for each prefix and for none; the housekeeping rule; the context set and restored
      around each entry point (a nested housekeeping call, an exception inside the work); `CacheEvent` round-trip with
      and without the new fields; `Message` round-trip through both stores with and without `channel`. Integration —
      a server turn with `X-Lumi-Client: desktop-…` over the mock model → the records' origin and channel and the
      messages' channel; a brain inbox turn and a scheduled row over fakes. No paid call.
- [ ] **Contract:** the model-call record shape and `Message` (the memory-record contract test) with `channel`, the
      prefix map; ARCHITECTURE §Contracts updated in this issue.
- [ ] **Gates:** `uv run ruff check .`, `uv run pytest -q`.

### LUMI-341 — The media ledger and the tool ledger, and the prices of the non-token units

**Description:**
A new `media-ledger.jsonl` in the data root records each paid call that isn't a model call, and a new `tools.jsonl`
records each tool call, both written by the process that does the work. `core/pricing.yaml` gains the non-token units.
Touches a new `core/ledgers.py`, `server/voice.py`, `server/dictation.py`, `telegram/inbound.py`,
`telegram/outbound.py`, `core/imagegen.py` (or its tool executor), `core/weblookup.py`, the tool dispatch in
`core/agent.py` (`_turn_tools.dispatch` and the think path's executor), `core/logtrim.py`, `core/pricing.yaml`,
`core/usage.py`.

**What needs to be done:**
- `core/ledgers.py`: the two record shapes and their appenders (one JSONL line each, never raising; a failure logs one
  warning, the `cache-log` rule):
  - media: `{ts, provider, service, model, units: {chars | audio_s | images | requests, input?, output?}, latency_ms,
    outcome, origin, channel}`, `service` ∈ `tts`, `stt`, `image`, `search`, `outcome` ∈ `ok`,
    `error:<ExceptionType>`, `refused`;
  - tool: `{ts, tool, outcome, ms, result_chars, turn_id, session_id, origin, channel, input}`, `outcome` ∈ `ok`,
    `error:<ExceptionType>`, `refused:<guard>`, `not_found`; `input` is the one bounded line of `tool_calls_view`
    (`TOOL_INPUT_CHARS`); the result text is never written, only its size.
- The writers:
  - TTS: `LineVoicer._voice` (`server/voice.py`: the characters voiced, the voice model, ok or the error type) and the
    outbound daemon's "old way" `tts.synth` (`telegram/outbound.py`);
  - STT: the window's dictation (`server/dictation.py`: the audio seconds from the bytes received at `MIC_RATE`, the
    stream or batch provider) and a Telegram voice note (`telegram/inbound.py`: Telegram's own `voice.duration`);
  - image: each generation (`core/imagegen.py` through its tool, one picture, the model);
  - search: each web lookup (`core/weblookup.py`: one request, and the tokens from `usageMetadata` when the answer
    carries it);
  - tools: the reply loop's `dispatch` and the think path's executor (`core/agent.py`), timed around the executor;
    the outcome read from the executor's result (`error: …` strings, the guards' refusals, an unknown tool →
    `not_found`).
- `turn_id`: a turn's id is its `turn_ts` (the one stamp both of its stored messages carry), so v5.7's history joins a
  reply to its tools without a new id. Record this in ADMIN_PANEL_II (it names `turn_id`).
- The origin and the channel of each record come from the LUMI-340 context; the daemons write their own (`telegram`,
  origin `turn` for a voice note; `housekeeping:voice` for a pushed line voiced by the old way).
- `core/logtrim.py` `LOG_FILES` gains both files (10 days, like `cache-log.jsonl`).
- `core/pricing.yaml`: `units:` — ElevenLabs per 1 000 characters for the configured voice model, Deepgram per audio
  minute (stream and batch), Gemini image per picture, the grounded search per request (with its tokens priced as the
  model's). `core/usage.py`: a unit price lookup; a unit without a price is "not priced", never guessed.
- ARCHITECTURE §Contracts: the two record shapes; the v5.1 line.

**Dependencies:** LUMI-340

**Expected result:**
Every paid call and every tool call leaves exactly one record in the instance's data root, with its units, origin and
channel, and never its text.

**Acceptance criteria:**
- [ ] A voiced line, a dictation, a Telegram voice note, a picture and a web lookup each write one media record with
      its units, model, outcome, origin and channel.
- [ ] Each tool call writes one tool record; a failing tool records `error:<Type>` and its duration; a refused one
      `refused:<guard>`.
- [ ] No message text, prompt, audio, tool result or secret enters either ledger.
- [ ] The two ledgers are trimmed to 10 days with the others.
- [ ] **Tests:** unit — each writer over a fake TTS / STT / image / search / tool executor (one record, its units,
      the outcome on an exception); a recorder that raises leaves the turn and the voice line intact; the bounded
      input line and no result text; the unit prices and "not priced"; the trim. Integration — a turn over the mock
      model with two tool calls → two tool records with the turn's `turn_ts`. No paid call (every provider faked).
- [ ] **Contract:** the media and tool record shapes (no text field beyond `input`, no secret); ARCHITECTURE §Contracts
      updated in this issue.
- [ ] **Gates:** `uv run ruff check .`, `uv run pytest -q`.

### LUMI-342 — The panel's rollups and the agent's usage and tools API

**Description:**
The panel rolls each instance's ledgers up per closed local day into its own folder and serves the usage and tools
aggregates under the agent. Touches a new `admin/usage.py` (rollups + aggregates), `admin/registry.py` (the `agents`
map), `admin/app.py` (the routes), `admin/readers.py` (the ledger readers).

**What needs to be done:**
- The registry's `agents` map in `admin.yaml`: `lili: {name: Lili, instances: [prod, dev]}` by default (the display
  name is the interface's, "Lili"), validated like the rest (an unknown instance refused). An instance runs one agent.
- The rollups, run after every health run, idempotent:
  - `~/lumi/admin/usage/<instance>.jsonl`: one row per closed local day × provider × service × model × kind × origin ×
    channel — the summed tokens or units, the estimated cost (`core/usage.py` prices), the call count;
  - `~/lumi/admin/tools/<instance>.jsonl`: one row per closed day × tool × outcome × origin — the count, the duration
    median and p95;
  - a day is closed once, at the first run after its end; a re-read changes nothing; rows older than 400 days dropped.
    Today is computed live from the ledgers.
- The aggregates (pure functions over rollup rows + today's live rows), per range (7 / 30 / 90 days, a calendar month):
  - usage: the total to date with the per-instance split; the forecast to the month's end (the month so far per day,
    projected); the previous month; the turns (`origin: turn` reply records) and the cost per turn; the cost per day
    by provider (a day with no data marked as a gap, not zero); by model, kind (the record's `kind` / media
    `service`), origin and channel; the cache read ratio and what it saved (the cache-read tokens priced at the input
    price minus their read price); the turn latency per day (median, p25, p95) and the PRE / MODEL / POST split (the
    reply records' `pre_ms`, `latency_ms`, `post_ms`); the slowest calls;
  - tools: per tool the calls, the failures and their rate, median / p95, the last error and when, the origins that use
    it; for one tool the calls per day split ok / failed and its slowest and failed calls.
- The routes, behind the panel token: `GET /api/agents` (the registry's agents for the picker);
  `GET /api/agents/<agent>/usage?range=…` and `GET /api/agents/<agent>/tools?range=…[&tool=…]` (over the agent's
  instances, with the per-instance split); `GET /api/agents/<agent>/usage.csv?range=…`; any
  `/api/agents/<agent>/<instance>/…` for an instance that doesn't run that agent → 404. The v2.10 `/api/usage` keeps
  answering.
- The panel reads the ledgers through the existing read-only mounts; it writes only under `~/lumi/admin/`.

**Dependencies:** LUMI-341

**Expected result:**
The panel answers the Usage and Tools views from its own 400-day rollups plus today's ledgers, for both instances,
with no paid call and no write into a data root.

**Acceptance criteria:**
- [ ] A fixture day's figures (cost by provider, origin and channel; a tool's calls, failures, median and p95) match a
      hand count.
- [ ] A day older than the instance's 10-day trim is still in the aggregates after the ledger lost it.
- [ ] Closing a day twice changes nothing; a 401-day-old row is dropped.
- [ ] A day without data is a gap in the per-day series, not zero; an unpriced unit is "not priced".
- [ ] **Tests:** unit — the rollup (closed once, idempotent, the 400-day bound), each aggregate over fixture rows, the
      forecast, the gap, the cache saving, the latency band, the CSV; the registry's `agents` map (default, an unknown
      instance refused). Integration — fixture data roots for prod and dev → the API answers; the 404 for an instance
      outside the agent; every v2.10–v2.11 route still answers.
- [ ] **Contract:** the existing admin contract (`tests/contract/test_admin_contract.py`) extended to the new routes:
      the token on each, no write into a data root (fingerprinted), no secret in a response.
- [ ] **Gates:** `uv run ruff check .`, `uv run pytest -q`.
