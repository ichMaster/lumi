# v2.3 — Issues

Issues for phase **v2.3 — The live turn: streaming over the socket** (version **v2 — Client/server split:
her brain on the server, the TUI a thin client**), derived from the Tasks and DoD in
[ROADMAP.md](../../ROADMAP.md) §v2.3 and the contracts in [ARCHITECTURE.md](../../ARCHITECTURE.md). This
file covers one phase; ids continue from the previous phase (LUMI-215 → **LUMI-216…218**).

Client mode feels like v1.4 again: the server streams a turn as **Server-Sent Events** (the owner's
choice, 2026-10-10 — SSE over WebSocket: plain HTTP, the same `httpx`, `EventSource` in the browser for
v2.8) and `RemoteCore` feeds the deltas into the TUI's **existing** v1.4 streaming callbacks — the TUI
itself doesn't change. A dropped or malformed stream falls back to the blocking path **by turn id**, so a
turn is never run twice. Pushes and state events (v2.4) build on the same SSE choice.

**Design note (reconcile, 2026-10-10).** The TUI already streams through `Core.reply(…, on_delta,
on_think_delta)` (`tui/app.py::_reply_streamed`, finalized by `_finalize_streamed_reply`, which replaces
whatever deltas arrived with the final Markdown) and decides to stream from `core.stream_enabled`. So the
client side is `RemoteCore` honouring those callbacks. The real hazard is the fallback: re-POSTing a
turn after a mid-stream drop would make the server run it **twice** (the worker thread keeps running when
the client disconnects) — a duplicate message, a duplicate answer. Hence an idempotent client `turn_id`.

## v2.3 — The live turn: streaming over the socket

### LUMI-216 — The streamed turn — POST /v1/turn/stream (SSE) + an idempotent turn_id

**Description:**
`server/app.py`: a streaming turn endpoint that runs the core's v1.4 streaming `reply` and relays its
deltas as Server-Sent Events, plus an idempotency key on every turn so a retried turn returns the result
of the first instead of running again.

**What needs to be done:**
- A **turn registry** in the service: `turn_id → TurnRecord{done: threading.Event, result | error,
  buffered events}`, bounded (the last ~32), filled by **one runner thread per turn** that holds the
  service lock for the whole turn (so a client disconnect never leaves the lock held or the turn half-done).
- `POST /v1/turn/stream {text, images?, turn_id}` → `text/event-stream`: `event: delta` (`{"text"}`),
  `event: think` (`{"text"}`), then exactly one `event: done` (the same payload as `POST /v1/turn`'s
  response) or `event: error` (`{"detail"}`); JSON `data:` lines (newline-safe). The emotion is validated
  **on completion** by the core, as always — `done` carries it. If the core isn't streaming
  (`LUMI_STREAM` off) the endpoint still answers: no deltas, just `done`.
- `POST /v1/turn {text, images?, turn_id?}`: a known `turn_id` **waits for and returns** the stored result
  (in progress → wait; done → return; never a second `core.reply`); an unknown or absent id runs as in
  v2.2 (backward compatible). Same 409 rule for a *different* turn while one runs.
- `GET /v1/state` gains `stream_enabled` (the server core's `LUMI_STREAM`) so the client knows to stream.
- Docs: ARCHITECTURE §Contracts — API v1 adds the stream route, the event set, `turn_id` semantics and the
  state key (additive; v2.2 clients keep working).

**Dependencies:** None

**Expected result:**
A client can watch a turn arrive token by token, and can always retry a turn by its id without Лілі
answering twice.

**Acceptance criteria:**
- [ ] The stream yields deltas then exactly one `done` (or `error`); the assembled deltas equal the final
  `reply`; the emotion arrives only in `done`, gate-validated (a malformed mock reply → `calm`)
- [ ] The same `turn_id` twice (stream then blocking, or blocking twice) → **one** `core.reply` call, the
  same result; a different turn while one runs → 409
- [ ] A client that disconnects mid-stream doesn't stop the turn or leak the lock; the result is
  retrievable by its id
- [ ] Token required on the new route; `stream_enabled` in the state
- [ ] **Tests:** `TestClient` streaming against a mock-model core (scripted deltas via the v1.4 mock
  stream), the dedupe paths, a disconnect mid-stream, the non-streaming core; no network, no paid API
- [ ] **Contract:** `tests/contract/test_server_api_contract.py` extended (route set, the event names and
  `done` payload shape, `turn_id` semantics, the state key) + ARCHITECTURE §Contracts
- [ ] **Gates:** `ruff` + `pytest`

### LUMI-217 — RemoteCore streams into the TUI's callbacks — fallback by turn_id, never twice

**Description:**
`tui/remote.py`: `RemoteCore.reply` streams when the TUI passes its v1.4 callbacks and the server streams,
parsing the SSE events into `on_delta` / `on_think_delta`; any stream failure falls back to the blocking
`POST /v1/turn` with the **same** `turn_id`. The TUI code stays as is.

**What needs to be done:**
- `RemoteCore.stream_enabled` → the server state's `stream_enabled` (the TUI already branches on it).
- `reply(…, on_delta, on_think_delta)`: a fresh `turn_id` per turn; with callbacks + a streaming server
  → `httpx` stream of `/v1/turn/stream`; a small pure **SSE parser** (`event:`/`data:` frames, blank-line
  terminated, `:` comments ignored); deltas → callbacks; `done` → the `EmotionState` (+ snapshot, thinking,
  intent as in v2.2); `error` → `LLMError(detail)`.
- **Fallback:** a transport error, a malformed frame, or a stream that ends without `done` → `POST
  /v1/turn` with the same `turn_id` (the server returns the stored result or runs it once); a server that
  is down → `ServerUnavailable` (the TUI's readable line); the next turn reconnects naturally.
- No callbacks (blocking callers) / server not streaming → the v2.2 blocking path, unchanged.

**Dependencies:** LUMI-216

**Expected result:**
`./lumi-client` shows the reply growing and the think-box filling live; a drop mid-turn ends in the one
answer, never two.

**Acceptance criteria:**
- [ ] Streamed replies grow live and finalize to the same text as the blocking path; the think-box fills
  from `think` events
- [ ] A drop mid-stream / a garbled frame / a stream without `done` → the same `turn_id` over the
  blocking route → exactly one answer
- [ ] Server down → a readable line; when it's back the next turn works
- [ ] **Tests:** unit — the SSE parser (frames, comments, multi-line data, garbage); `RemoteCore` over a
  fake streaming transport (scripted deltas → callbacks, assembled == blocking, emotion at completion);
  drop → fallback with the same id (one server-side call, via `TestClient`); the TUI pilot in client mode
  with streaming (the stream widget grows, then finalizes); no real network
- [ ] **Gates:** `ruff` + `pytest`
