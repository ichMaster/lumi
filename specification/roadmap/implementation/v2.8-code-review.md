## Findings

### 1. 🟠 A cancelled twin run — `scripts/deploy_agent.py` `ci_verdict`

A commit collects check runs from every ref it was pushed to: `v2-dev` (gates + image), then `main` (gates + image).
Both workflows cancel an in-progress run of the same ref when a newer push arrives. **Scenario:** push B to `v2-dev`,
fast-forward `main` to B while B's `v2-dev` runs are still going, then push C to `v2-dev` → B's `v2-dev` runs end
`cancelled`; B's `main` runs succeed. `ci_verdict` reads any non-success conclusion as `red`, so `main` = B is "CI
red" for ever and dev never deploys it — the normal "merge, then keep working" flow. **Fix:** decide per check name —
a failure of any run is red; a run still going is pending; otherwise green if any run of that name succeeded (a
cancelled twin doesn't count against it); only-cancelled is red.

### 2. 🟠 A recorded `runs` that systemd contradicts — `_seed` / `_to_containers`

`runs` is seeded once and then only changed by the agent. The guide's [way back](../../../docs/LINUX_DEPLOY.md) is
by hand (`compose down`, units `enable --now`). **Scenario:** the owner goes back to the units by hand, later
restarts the timer; the next green `main` → `_to_containers` trusts `runs == "containers"`, skips retiring the units,
`up -d` fails on the port the unit holds, the "rollback" to the previous image fails the same way — the commit is
marked bad, and so is every later one (the units keep serving, so no outage, but the pipeline is stuck). **Fix:**
derive `runs` from systemd on every step (the server unit enabled → units), so the switch always retires units that
are really there.

### 3. 🟠 Images pile up — `deploy`

The image is 2.27 GB; with an unchanged lock each new commit adds its `COPY . .` layer (243 MB — the code and the
face pack). Nothing removes a superseded image. **Scenario:** ~3 dev deploys a week → ~35 GB a year on a disk with
79 GB free, shared with matrix-agora (whose 51 GB of images already hold 41 GB reclaimable). **Fix:** after a kept
deploy, remove the Lumi images that no instance runs or would roll back to (each instance's `current` + `previous`);
an image a container still uses is refused by Docker and left alone; GHCR keeps every tag, so nothing is lost.

### 4. 🟡 Unrotated container logs — `deploy/compose/compose.yaml`

The containers use Docker's `json-file` driver with no limit (`HostConfig.LogConfig.Config = {}` on the box); the
Telegram daemons log every send to stderr. Slow, unbounded growth. **Fix:** `logging: {driver: json-file, options:
{max-size: 10m, max-file: "3"}}` on every service (her own logs stay in the data root).

### 5. 🟡 Spec drift — ROADMAP §v2.8

The DoD says "the dev containers on the new `:edge` image"; the agent deploys the commit's immutable `:sha-<short>`
(so the previous one is a rollback target) and `:edge` only moves with it. **Fix:** reconcile the DoD and Tasks text.

### 6. 🟡 A refusal loops — the restart policy

The v2.6 units never restart a refusal only `.env` fixes (exit 78, `RestartPreventExitStatus`); Docker has no such
exclusion, so a taken port or a non-release prod build restarts with Docker's back-off. A deploy's smoke catches it
and goes back; after a reboot it is noise until fixed. **DEFER → backlog;** the guide's troubleshooting names it.

### 7. 🟡 Pull-failure noise — `deploy`

A pull that fails (GHCR down, a private package) is logged as a new "deploying …" every 5 minutes. Harmless (nothing
stops). **DEFER → backlog.**

### 8. 🟡 Prod and the tag's CI — `_prod`

Dev waits for every check run; prod waits for the owner and for the image to exist (a failed pull retries). A tag
cut on a red commit would deploy if the owner confirmed it — the release process forbids that tag. With #1's per-name
rule a CI gate for the tag commit becomes straightforward. **DEFER → backlog.**

### 9. 🟡 `LUMI_BUILD` from the `.env` — compose precedence

`env_file` overrides an image `ENV`, so `LUMI_BUILD=v9.9.9` in an instance `.env` would let prod run any image. The
`.env` is the owner's own file (not a security boundary). **DEFER → backlog** (pin it in `environment:` if it ever
matters).

## Architecture impact

- **The CI gate** (ARCHITECTURE §Deployment, v2.7 bullet): "all green" is now judged per check name, so a run a newer
  push cancelled no longer blocks a commit whose twin passed (#1).
- **The units-or-containers state** is read from systemd on every step, not trusted from the record (#2).
- **Superseded images are removed** after each deploy that passes; each instance keeps its current and previous (#3).
- **Docker's log copy is capped** per container (#4). None of these changes a contract test's rule; the compose
  contract gained the log cap.
- The fixes live in `scripts/deploy_agent.py` and `deploy/compose/` — they reach the box only by re-running the agent's
  `install` after the merge into `main`.
