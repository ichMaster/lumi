## Findings

### 1 · 🔴 A secret in a YAML error message
`core/settings.py` `read_yaml` raises `SettingsError(f"… is not valid YAML:\n  {exc}")`; PyYAML's `str(exc)` carries a
snippet of the line. **Scenario:** `secrets.yaml` has `anthropic_api_key: sk-ant-SECRET123: oops` → the server's
refusal prints `sk-ant-SECRET123` to stderr → docker's json log, again on every `unless-stopped` restart;
`config validate` prints it too; `config set` on that file raises a raw `ScannerError` traceback with the same line.
**Fix:** report only `exc.problem` + the line/column (`problem_mark`), never the snippet; parse through one helper
everywhere (including `set_in_text`), so a parse error is always a `SettingsError`.

### 2 · 🔴 `config set` rewrites the file
`set_in_text` verifies the line edit by re-parsing; on a mismatch it rebuilds the file from the parsed data,
excluding `STRUCTURED` and every comment. **Scenario:** a block list (`allowlist:\n    - 12345`) or a 4-space group
→ `config set telegram.allowlist 12345,678` exits 0 and `schedule:` / `models:` are gone. **Fix:** never rewrite —
if the line edit doesn't verify (the target key has the new value **and** every other key + section is unchanged),
refuse with "edit this file by hand", writing nothing.

### 3 · 🟠 The old Gemini name wins over the file
`_apply_old_names` maps `GOOGLE_API_KEY` → `GEMINI_API_KEY` inside each layer, so the env layer's old name beats
the file's new name. **Fix:** after merging, fill a setting from an old name only when the canonical name is absent
from **every** layer.

### 4 · 🟠 A schedule override's trigger keys
`merge_rows` drops all authored `TRIGGER_KEYS` when the override names any of them. **Fix:** an override replaces
the trigger only when it names a different trigger **kind** (`cron`/`between`/`at`/`every`/`idle`); `days` (for `at`)
and `every` (for `between`) merge as modifiers. An override row that ends without a valid trigger is logged, not
silently dropped. The SCHEDULER_SETUP sentence "overriding a row never re-fires it" is corrected: turning a row off
keeps its identity; changing its trigger/topic/seeds makes it a new row.

### 5 · 🟠 The units' way back after the migration
`rollback` (`runs_then == "units"`) starts the v2.6 units, whose pre-v2.9 checkout reads `~/lumi/<i>/.env` — renamed
to `.env.migrated`. **Fix:** going back to the units, the agent restores `.env` from `.env.migrated` (0600, logged)
when `.env` is missing.

### 6 · 🟠 Values that crash `load_config`
`to_env` accepts `float("inf")` / `nan` for `duration`/`float`, and `"²".isdigit()` for `int`. **Fix:** `math.isfinite`
for every number; `int()` inside `try`.

### 7 · 🟠 Duplicate keys
`yaml.safe_load` keeps the last duplicate. **Fix:** a SafeLoader subclass that refuses a duplicate key (line named),
used for the settings files.

### 8 · 🟠 A mid-session re-read; the server's exit code
`tui/app.py` `_refresh_world` (on `/new`) calls `load_config()` again. **Fix:** it reads the config loaded at start
(`self._app_cfg` — settings apply after a restart anyway); the server maps a `SettingsError` to its
configuration refusal (exit 78).

### 9 · 🟡 The migrated `.env`'s mode and wording
**Fix:** `chmod 600` `.env.migrated` after the rename; the dry run says unknown keys "are not migrated — they no
longer apply; kept for reference in `.env.migrated`".

### 10 · 🟡 Numbers for text settings
**Fix:** a `str`/`path` setting refuses a non-string YAML value, with "quote it" in the message (the migration and
`config set` already write such values quoted).

### 11 · 🟡 An incomplete new profile
**Fix:** a warning naming the missing fields when an instance's profile has no authored base and is incomplete.

### 12 · 🟡 Non-atomic writes
**Fix:** write a temp file beside the target (0600 for secrets from the first byte), `fsync`, `os.replace`.

### 13 · 🟡 The smoke's address
**Fix:** the smoke dials `LUMI_PUBLISH_HOST` / `LUMI_SERVER_PORT` from the agent's `compose/<i>.env` (what compose
publishes), falling back to the settings; the token still comes from `secrets.yaml`.

### 14 · 🟡 A missing settings folder
**Fix:** a warning when `LUMI_SETTINGS_DIR` names a folder that doesn't exist.

## What's solid

- The unmigrated guard in `deploy()` runs before the pull / stop / archive; the agent never logs the token.
- The migration's refusal paths write nothing; its round-trip check caught a real difference on its first run; the
  dry run prints only secret key names.
- `_EXPORTED` keeps an exported value from being mistaken for the real environment across repeated loads.
- The schema contract (check 6, the perturbation test) proves every setting feeds a `Config` field.
- No test-state leak was found (the loader tests clear the export state; the rest run `load_env=False` against an
  empty `LUMI_SETTINGS_DIR`).
- The YAML schedule keeps every `schedule.state` id (pinned against the old TOML).

## Architecture impact

- **The validation rule** (ARCHITECTURE §Configuration and secrets, the v2.9 bullet — updated): a duplicate key, a
  non-finite number and a YAML number for a text setting refuse; a syntax error names only the problem and its
  line/column; a deprecated env name fills its setting only when the current name is in no layer. Pinned by
  `tests/unit/test_settings_loader.py` (`test_review_*`).
- **`lumi-cli config set`** never rewrites a file: one line, the whole file verified, or a refusal; writes are atomic.
- **Schedule overrides** (`core/schedule.py` `merge_rows`): another trigger kind replaces the authored trigger, the
  same kind or a modifier merges — SCHEDULER_SETUP describes it; changing a trigger/topic/seeds is a new
  `schedule.state` key.
- **The deploy agent** (ARCHITECTURE §Deployment, the compose-contract sentence — updated): the smoke dials the
  compose parameters; the way back to the v2.6 units restores `.env` from `.env.migrated`.
- **The server** exits 78 on a settings refusal (the v2.6 configuration-refusal code), like a missing token.
- Fixes 5 and 13 live in `scripts/deploy_agent.py` — they reach the box only by re-running the agent's `install`
  after the merge into `main` (before the prod migration, so `rollback prod` in that window is safe).
