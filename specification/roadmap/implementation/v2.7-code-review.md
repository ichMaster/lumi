## Findings

### 1. 🟠 The mixed-version window — `scripts/deploy_agent.py` `_switch`

`_switch` runs `git checkout --detach <ref>` → `uv sync` → `systemctl --user restart`. Between the checkout and the
restart the **old server keeps running over the new tree**: `uv sync` replaces packages in `app/.venv` under it, and
the restart's stop runs her **session close** (summary + facts, model calls) in the old process — which imports the
new files lazily (the core has 36 function-level imports, e.g. `core/agent.py:1356` `from core.files import …`,
`:1603` `from core.news import …`). **Scenario:** a release renames a function in `core/files.py`; the dev deploy's
restart stops the old server, whose session close imports the new `core.files` → `ImportError` → her session summary
is lost. The same happens on every `rollback` (prod included — newer code running over older files) and on the
rollback after a failed smoke. (The prod deploy itself is safe: the archive step stops the server first.)
**Fix:** stop the server **before** any code moves — `stop` → `checkout` → `sync` → `start`, for every switch.

### 2. 🟠 A late crash passes the smoke — `_smoke`

The health check runs once, as soon as the server answers; after the stable minute only `is-active` is read. With
`Restart=on-failure` + `RestartSec=5` a server that **crashes at second 30** is `active` again at second 60.
**Scenario:** a release whose scheduler tick raises on its first run (~30 s after start) crash-loops every ~35 s, yet
each smoke reads `active` → prod is kept on the broken tag, no rollback. **Fix:** note each enabled unit's
`InvocationID` when the health check passes and compare it after the stable minute (a restart changes it), and ask
`/v1/health` once more at the end.

### 3. 🟠 A dropped ssh session kills a manual deploy — `main` / `confirm`

The docs run `confirm` / `rollback` from the Mac as `ssh slate-server 'python3 ~/lumi/deploy/deploy_agent.py …'`. A
prod deploy takes minutes (her session close up to 300 s + the archive + the smoke). If the Mac sleeps or the Wi-Fi
drops, the remote process gets `SIGHUP` (or `BrokenPipeError` on the next `print`) and dies wherever it is — e.g.
after the checkout, before the restart. `confirm` saves the state only at the end, so the confirmation is lost too.
**Scenario:** checkout moved to `v2.7.0`, the server still runs `v2.6.0` in memory, `state.json` says `v2.6.0`
unconfirmed; the next reboot starts `v2.7.0` with no smoke and no archive. **Fix:** ignore `SIGHUP` in `main`, never
fail on a closed stdout (the log file stays the record), and save the confirmation before the deploy starts.

### 4. 🟡 The smoke never meets the real API — `tests/unit/test_deploy_agent.py`

The smoke is tested only against a fake HTTP; ROADMAP §v2.7 Tests asks for "the smoke script against a local server
(mock model)". If `/v1/health` or `/v1/state` changed shape, every deploy would roll back while all tests stay green.
**Fix:** a contract test that routes the agent's HTTP into the real `server.app.create_app` (TestClient, mock model):
a healthy instance → `[]`; a wrong token or version → the reason.

### 5. 🟡 HTTP error statuses are lost — `_http`

`urllib` raises `HTTPError` for a 4xx/5xx; the generic `except` returns `(0, None)`, so a token mismatch reads
"/v1/state answered nothing" instead of "answered 401". **Fix:** return the `HTTPError`'s status.

### 6. 🟡 Spec drift — ROADMAP §v2.7, ARCHITECTURE §Deployment

ROADMAP: the confirmation is "a command — e.g. `lumi-cli deploy prod v2.7.0`" and "prod keeps the last N releases on
disk"; the code has `deploy_agent.py confirm v2.7.0` on the box, every release tag in the checkout and a data archive
per prod deploy. ARCHITECTURE describes the bounded turn without a provider, but only `GeminiClient` has it (the
Anthropic/OpenAI SDK clients keep their own timeouts; the hang was Gemini's). **Fix:** reconcile both texts.

### 7. 🟡 An unverified rollback — `deploy`

After a failed smoke, `_switch(previous)`'s result is ignored and no smoke runs; if the rollback fails too, the state
claims `previous` is live. Rare (the previous ref ran a minute ago) and the log records the failed command.
**DEFER → backlog.**

### 8. 🟡 The deadline vs a slow model — `core/llm.py` `TURN_DEADLINE_S`

Gemini 3.1 Pro preview answered in 1–4 min on 2026-10-17/19; a 3–4 min turn that used to arrive now ends with "the
model didn't answer within 3 minutes". The owner chose 180 s; whether real turns hit it is a prod observation (grep
`didn't answer within` in prod's `lumi.log` after v2.7.0). **DEFER → backlog (observe).**

### 9. 🟡 Node 20 deprecation — `.github/workflows/ci.yml`

An annotation, not a failure; bump the actions when Node 24 versions are current. **DEFER → backlog.**

## Architecture impact

- **The deploy sequence** (ARCHITECTURE §Deployment, LINUX_DEPLOY §Deploys): a switch now stops the server first
  and starts it after the sync (#1); downtime per deploy grows by the sync time (seconds when the lock is unchanged).
- **The smoke** now requires each service to keep its `InvocationID` across the stable minute and the health to
  answer at its end (#2).
- **The bounded turn is Gemini-only**, now stated (#6). The other providers' SDK timeouts are unchanged.
- **The box runs the agent copied at install** — these fixes reach it only by re-running `install` after the merge
  into `main` (LINUX_DEPLOY step 7 says so).
