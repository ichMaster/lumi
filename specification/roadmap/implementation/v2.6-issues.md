# v2.6 — Issues

Issues for phase **v2.6 — Remote: the Linux deploy** (version **v2 — Client/server split: her brain on the server,
the TUI a thin client**), derived from the Tasks and DoD in [ROADMAP.md](../ROADMAP.md) §v2.6 and the contracts in
[ARCHITECTURE.md](../ARCHITECTURE.md). This file covers one phase; ids continue from the previous phase
(LUMI-227 → **LUMI-228…232**).

The v2.5 server already runs her whole time (scheduler, ticks, thoughts, the Telegram bridge) with no client
attached; v2.6 puts it on the always-on home **Linux box** as systemd services and lets the Mac TUI reach it over
**LAN/Tailscale only**. Her real memory does **not** move: the box's prod unit is installed with an empty data root
and stays stopped, and the manual DoD runs on the box's **dev** instance — the prod migration and the deploy
pipelines are v2.7, TLS and the fuller hardening v4.1.

## v2.6 — Remote: the Linux deploy

### LUMI-228 — The server leaves localhost safely: a LAN/Tailscale bind guard + a remote client

**Description:**
Today `LUMI_SERVER_HOST` defaults to `127.0.0.1` and nothing stops a wildcard or public bind once it is changed;
the client builds `http://{server_host}:{server_port}` in two places (`tui/__main__.py`, `cli/main.py`). On the
box the server must bind its **LAN or Tailscale address only**, and on the Mac the same variable names the box.
Touches `server/__main__.py`, `tui/__main__.py`, `cli/main.py`, `tui/remote.py`, `specification/ARCHITECTURE.md`.

**What needs to be done:**
- `server/__main__.py`: a pure `bind_problem(host) -> str | None` — `None` for `localhost`, loopback (127.0.0.0/8,
  `::1`), RFC 1918 private (10/8, 172.16/12, 192.168/16), the Tailscale/CGNAT range 100.64.0.0/10 and IPv6 ULA
  (fc00::/7, which holds Tailscale's fd7a:115c:a1e0::/48); a readable reason for a wildcard (`0.0.0.0`, `::`,
  empty), a public address, or a hostname other than `localhost` ("bind the box's LAN or Tailscale IP"). `main()`
  checks it **before the core is built** (beside `port_free`, review v2.4 #2) and exits with the reason — no model
  call, no banner.
- One client URL helper (e.g. `server_url(cfg)` in `tui/remote.py`) used by `tui/__main__.py` and `cli/main.py`;
  an IPv6 literal is bracketed. The client may dial any host (the box's Tailscale IP or MagicDNS name) — the bind
  guard is the server's only.
- The unreachable / wrong-token lines name the URL they tried (they already carry `base_url`; keep it on every
  path, the stream included).
- The push listener on **401** (v2.4 review #5, homed here — it is this phase's auth-failure path once the
  server and client sit on different machines): stop reconnecting and say once
  "the server rejected the token — check LUMI_SERVER_TOKEN", instead of retrying forever behind the generic
  "lost the server's pushes" line.
- ARCHITECTURE.md §Server API v1 + §Configuration and secrets: `LUMI_SERVER_HOST` is the bind address on the server
  (loopback by default; the box's LAN/Tailscale address in v2.6; never a wildcard or public address — refused)
  and the address the client dials.

**Dependencies:** None

**Expected result:**
The server refuses any bind but loopback/LAN/Tailscale, and the Mac client reaches a server on another host by
its address, with readable failures.

**Acceptance criteria:**
- [ ] `bind_problem` accepts loopback, `localhost`, RFC 1918, 100.64.0.0/10 and ULA, and refuses `0.0.0.0`, `::`,
      `""`, a public IPv4/IPv6 and a non-`localhost` hostname, each with a reason naming the fix.
- [ ] `python -m server` with a refused host exits before the core is built (no model call).
- [ ] The TUI client and the CLI build their URL through one helper; an IPv6 host comes out bracketed.
- [ ] A 401 on the push channel ends the listener with one token line and no further attempts.
- [ ] **Tests:** `tests/unit/test_server_main.py` — parametrized bind cases + the refusal before `build_core`
      (patched); `tests/unit/test_remote_core.py` — a remote base URL (`http://100.101.102.103:8766`) over an
      `httpx.MockTransport` (connect, a turn), the URL helper (IPv4, hostname, IPv6); `tests/unit/test_remote_listener.py`
      — 401 → one line, the thread ends, no retry. No real network.
- [ ] **Gates:** `ruff`, `pytest`.

### LUMI-229 — The client asks the server: feature gates + the network hop in `/latency` (API additive)

**Description:**
Once the client and server sit on different machines, the client's own `.env` no longer describes the server:
`/image` and `/web` are gated on the **client's** `LUMI_IMAGE` / `LUMI_WEB_LOOKUP` (v2.2 review #8, deferred to
v2.6). And `/latency` (run on the server via `/v1/command`) cannot see the network. Both come from the server over
the API. Touches `server/app.py`, `core/agent.py`, `tui/remote.py`, `tui/app.py`, `specification/ARCHITECTURE.md`,
the contract tests.

**What needs to be done:**
- `core/agent.py`: public read-only `image_enabled` / `web_lookup_enabled` properties over the existing
  `_image_enabled` / `_web_lookup_enabled`.
- `server/app.py`: `state_snapshot` adds `features` `{image, web_lookup}`; `turn_payload` adds `timing`
  `{pre_ms, llm_ms, post_ms, total_ms}` — the core's `last_turn_timing` for this turn (`null` when absent).
- `tui/remote.py` `RemoteCore`: `image_enabled` / `web_lookup_enabled` from the snapshot; per turn the client's wall
  time (monotonic, request start → outcome, streamed or blocking) minus `timing.total_ms` is the **network hop**
  (clamped at 0; no sample without `timing`); `network_summary()` → `{last, median, n}` over the last 20 turns.
- `tui/app.py` (client mode only): `/image` and `/web` gate on the server's `features`; `/latency` appends
  `NETWORK client↔server: last … · median … /n turns` beside the existing voice-stage append (the in-process
  `/latency` is unchanged).
- **Contract:** ARCHITECTURE.md §Server API v1 gets a "v2.6 (additive)" sentence — `GET /v1/state` adds `features`,
  the turn payload adds `timing`; the client reads server state **only through the API**.

**Dependencies:** LUMI-228

**Expected result:**
On the Mac, `/image` and `/web` follow what the server can do, and `/latency` shows the client↔server time
separately from her PRE / MODEL / POST.

**Acceptance criteria:**
- [ ] `/v1/state` carries `features {image, web_lookup}`; both turn routes carry `timing` (the streamed `done` too).
- [ ] A client whose own `.env` has `LUMI_IMAGE`/`LUMI_WEB_LOOKUP` off still offers `/image` / `/web` when the
      server has them on, and refuses them when the server has them off.
- [ ] `/latency` in client mode ends with the NETWORK line; in-process output is byte-identical.
- [ ] **Tests:** `tests/unit/test_remote_core.py` — hop math (wall − total, clamped, no `timing` → no sample, the
      median over a window), features from the snapshot; a client-mode TUI gate test with a fake `RemoteCore`
      (features on/off); the `/latency` append (mock model, no network).
- [ ] **Contract:** `tests/contract/test_server_api_contract.py` pins `features` + `timing`;
      `tests/contract/test_remote_core_surface.py` admits the new members; a new contract test pins that client mode
      reads server state only through the API — building the client-mode app and running a turn + `/latency` with
      a data root whose store / mood log / schedule state raise on any read never touches them, and never builds a
      core or a repository. ARCHITECTURE.md §Server API v1 updated in this issue.
- [ ] **Gates:** `ruff`, `pytest`.

### LUMI-230 — systemd units for the box's two instances + a graceful `systemctl stop`

**Description:**
The box runs each instance (prod, dev) as three user services — the server and the two Telegram daemons — from
templated units in the repo. And `systemctl stop` must close her session like Ctrl+C does: today uvicorn, after its
graceful stop, **re-raises a captured SIGTERM with the default handler restored**, which kills the process before
`main()`'s `finally` (`brain.stop()` + `close_session` — the session summary and facts) ever runs, so every stop,
restart or reboot of the box would lose the session's close. Touches `deploy/systemd/` (new), `server/__main__.py`,
tests.

**What needs to be done:**
- `deploy/systemd/lumi-server@.service`, `lumi-telegram-inbound@.service`, `lumi-telegram-outbound@.service` — user
  units templated by instance (`%i` = `prod` | `dev`): `WorkingDirectory=%h/lumi/%i/app`, `ExecStart=` the repo
  scripts (`lumi-server`, `lumi-telegram-inbound`, `lumi-telegram-outbound`), `Environment=PATH=%h/.local/bin:…`
  (uv), `Restart=on-failure` + `RestartSec`, `After=network-online.target` (a Tailscale address not up yet → the
  bind fails → systemd retries), the server's `TimeoutStopSec=300` (closing a session makes model calls); the
  Telegram units `PartOf=`/`After=` their instance's server. No secret in any unit — the instance's `.env` (found by
  walking up from `app/core/`) holds the token and keys.
- `server/__main__.py` `serve()`: SIGTERM is handled like SIGINT (`signal.default_int_handler` installed before
  uvicorn runs), so the re-raised SIGTERM becomes the `KeyboardInterrupt` `serve()` already swallows and the
  `finally` runs. Factor the install into a small testable helper.

**Dependencies:** LUMI-228

**Expected result:**
`systemctl --user enable --now lumi-server@dev …` runs the dev instance on the box, and `systemctl --user stop
lumi-server@dev` ends her session cleanly (summary + facts), exactly like Ctrl+C.

**Acceptance criteria:**
- [ ] Three templated unit files in `deploy/systemd/`, no absolute home path, no secret.
- [ ] SIGTERM to the server runs the same shutdown as Ctrl+C (brain stopped, session closed).
- [ ] **Tests:** `tests/unit/test_deploy_units.py` — every unit parses (configparser), is `%i`-templated, sets
      `Restart=on-failure`, the server's `TimeoutStopSec` ≥ 120, its `ExecStart` names a repo script that exists and
      is executable, no line carries a token- or key-shaped value; `tests/unit/test_server_main.py` — with the helper
      installed, a SIGTERM to the test process raises `KeyboardInterrupt` (the handler restored afterwards).
- [ ] **Gates:** `ruff`, `pytest`.

**What needs to be done:**

  - prerequisites (Tailscale on both, `uv`, `git`) and install per instance — prod: a clone at the release tag,

    its own Telegram bot;

  - exposure: LAN/Tailscale only, never a router port-forward, a firewall note; **one Telegram consumer per bot**
    (stop the Mac's dev daemons before starting the box's);

    `./lumi-cli status`), troubleshooting (bind refused, port taken, 401, unreachable, the env guard);

- `docs/SERVER_SETUP.md`: replace "no exposure until v2.6" with a pointer to the guide; `/image` and `/web` now
  follow the server's features. `docs/PROD_SETUP.md`: a note that prod moves to the box in v2.7, not in v2.6.
  `.env.example`: the `LUMI_SERVER_HOST` bind rules.
- ARCHITECTURE.md §Deployment and CI/CD: the section is stale ("from v3.2", Fly.io/VPS + TLS) — rewrite to the
  current ladder: the v2.6 box (two instances as user services, LAN/Tailscale only, the client token, SIGTERM =
  a clean session close), the v2.7 pipelines + the one-time prod migration, TLS and the scans in v4.1.
- `CLAUDE.md`: list `docs/LINUX_DEPLOY.md` with the other operator guides.

**Dependencies:** LUMI-228, LUMI-229, LUMI-230

**Expected result:**
The owner can stand the box up from the guide alone, and no doc still promises localhost-only or a Fly.io deploy.

**Acceptance criteria:**
- [ ] `docs/LINUX_DEPLOY.md` covers install, units, the Mac client, exposure, logs, troubleshooting and the DoD
      checklist, with the prod unit explicitly left stopped and empty.
- [ ] SERVER_SETUP / PROD_SETUP / `.env.example` / ARCHITECTURE §Deployment / CLAUDE.md updated as above.
