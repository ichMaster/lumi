# v2.2 — Issues

Issues for phase **v2.2 — The skeleton: pure server, TUI client & CLI utility (local, blocking)** (version
**v2 — Client/server split: her brain on the server, the TUI a thin client**), derived from the Tasks and
DoD in [ROADMAP.md](../../ROADMAP.md) §v2.2 and the contracts in [ARCHITECTURE.md](../../ARCHITECTURE.md).
This file covers one phase; ids continue from the previous phase (LUMI-210 → **LUMI-211…215**).

The smallest split that runs daily: the slash commands become a **command layer in the core** (the
owner's decision, 2026-10-04 — see *Design decision* below), a **FastAPI server** wraps the core behind a
client token, the TUI gains a **client mode** (`LUMI_SERVER=on`) over a thin `RemoteCore`, and a **CLI**
manages the server. Turns are blocking; streaming (v2.3), pushes/state events (v2.4), the brain move
(v2.5) and the Linux deploy (v2.6) come later.

**Design decision (owner, 2026-10-04).** Reconcile found that the ~20 slash commands are TUI methods
calling the core directly (44 distinct `Core` members) — the ROADMAP's "generic `/command`
pass-through" had nothing on the server to pass to. Two options were weighed: a `RemoteCore` RPC of the
whole surface (commands untouched) vs. a **command layer in `core/`** that any client renders. The owner
chose the **command layer**: one implementation of every command, usable by the TUI now and the
pywebview client (v2.8) later. Accepted cost: command **output formatting** changes in the in-process
TUI too (markdown rendering), so the v2.2 "off → byte-identical" pin covers **turns and the status line**,
not command output text. With commands in the layer, the TUI's remaining (non-command) core surface is
**16 members** — that is all `RemoteCore` implements.

## v2.2 — The skeleton: pure server, TUI client & CLI utility (local, blocking)

### LUMI-211 — The command layer — slash commands as a core service any client renders

**Description:**
Move the core-state slash commands out of `tui/app.py` into a new `core/commands.py`: each command takes
the core + the session + its argument string and returns a `CommandResult` (markdown text, a kind, an
optional confirmation question). The in-process TUI routes them through the layer and renders the
result; the TUI-bound commands stay in the TUI.

**What needs to be done:**
- `core/commands.py`: `CommandResult{text: str (markdown), kind: "info"|"warning"|"error", confirm: str | None}`;
  a registry; `run_command(core, session, line, *, confirmed=False) -> CommandResult | None` (`None` →
  not a layer command). Pure over the core's public API, no TUI/Rich import (core stays interface-
  independent).
- **Into the layer** (their logic moves, output becomes markdown): `/memory`, `/forget` (returns
  `confirm=…` until re-run with `confirmed=True` — the client asks, never the core), `/prompt`,
  `/latency` (the core part — the TUI appends its local voice-stage section), `/style`, `/mood`,
  `/model`, `/model-set`, `/biorhythm`, `/closeness`, `/thoughts`, `/regen-summaries`, `/recall`,
  `/journal`, `/theme`.
- **Stay in the TUI** (client-bound): `/mode-set` (local mic/speaker), `/web` and `/image` (they are
  turns — routed as turns), `/new` (session lifecycle).
- `tui/app.py`: `_handle_input_line` sends layer commands through `run_command` and renders
  `CommandResult` (Rich `Markdown`, the kind → the existing system/warning colors); `/forget`'s
  `ConfirmScreen` asks, then re-runs with `confirmed=True`. Remove the moved handler bodies.
- Update the TUI tests that asserted exact command-output strings to the new markdown output (behavior
  unchanged: same data, same effects).
- Docs: ROADMAP §v2.2 records the design decision (the command layer; the byte-identical pin covers turns
  + the status line, not command output); ARCHITECTURE §Contracts adds the **command layer**
  (`run_command` + `CommandResult`).

**Dependencies:** None

**Expected result:**
Every slash command except the client-bound ones runs from one core implementation; the in-process TUI
behaves the same apart from the markdown look of command output.

**Acceptance criteria:**
- [ ] All 15 listed commands run through `core/commands.py`; `core` imports nothing from `tui`/Rich
- [ ] `/forget` never clears without `confirmed=True`; the TUI confirm dialog still guards it
- [ ] Unknown `/x` → `None` from the layer (the TUI's existing fallthrough unchanged)
- [ ] **Tests:** unit — every layer command against a mock-model `Core` (effects + key content of the
  markdown), the confirm protocol, unknown-command `None`; the TUI suite updated and green
- [ ] **Contract:** the command layer (`run_command`, `CommandResult`) in ARCHITECTURE §Contracts +
  `tests/contract/test_command_layer_contract.py` (result shape, confirm protocol, no TUI import);
  turns and the status line in-process unchanged (existing pins stay green)
- [ ] **Gates:** `ruff` + `pytest`

### LUMI-212 — The server — FastAPI over the core: token, turn, command, state, session

**Description:**
A new `server/` package: a FastAPI app wrapping one `Core` + one session, behind a client token, on
localhost. `python -m server` runs it with uvicorn. Blocking turns only.

**What needs to be done:**
- `pyproject.toml`: a `server` extra (`fastapi`, `uvicorn`); `fastapi` also in `dev` (the tests use its
  `TestClient`, over the already-present `httpx`); `uv.lock` updated.
- Config: `LUMI_SERVER_HOST` (default `127.0.0.1`), `LUMI_SERVER_PORT` (default `8765`),
  `LUMI_SERVER_TOKEN` (required to start — refuse readably without it); `.env.example` documents them,
  noting each instance (prod/dev) uses its own port + token.
- `server/app.py`: `create_app(core, …)`; every `/v1/*` route requires `Authorization: Bearer <token>`
  (constant-time compare; 401 otherwise; the token never logged or echoed):
  - `GET /v1/health` — `{ok, env, version}` (the only route allowed without the token);
  - `GET /v1/state` — the status snapshot: model, profile, thinking, style, last emotion, last intent,
    last stats, totals, mood, theme, env, version;
  - `POST /v1/turn {text, images?}` → `{reply, emotion, intensity, thinking?, intent?, style?, stats, state}`
    — the core's blocking `reply` (validated by the v0.3 gate as always); `images` are the existing
    v0.22 image blocks (base64), so `/image` works over the API;
  - `POST /v1/command {line, confirmed?}` → `{handled, result{text, kind, confirm}, state}` via the
    LUMI-211 layer;
  - `POST /v1/session/new` → ends the current session (its summary) and starts a fresh one.
  One turn/command at a time (a lock; a concurrent request → 409 `busy`).
- `server/__main__.py`: `load_config` → `guard_entry` (the v2.1 env guard — the server opens the data
  root) → `build_core` → `ensure_mood` + `ensure_backfill` + the ambient world snapshot (the same
  function the TUI uses today) → start the session → uvicorn. On shutdown: end the session (summary).
  The scheduler, ticks, thought-stream and the Telegram bridge do **not** run in the server yet (v2.5).
- Docs: ARCHITECTURE §Contracts — the **server API v1** (routes, payloads, the token rule).

**Dependencies:** LUMI-211

**Expected result:**
`python -m server` serves Лілі on localhost; a token-bearing client can talk to her, run commands, read
her state and start a new session.

**Acceptance criteria:**
- [ ] Every `/v1/*` route except `health` → 401 without / with a wrong token; the token never appears in
  logs or responses
- [ ] `turn` returns the validated emotion contract `{reply, emotion, intensity}` (+ the extras); a
  malformed mock reply still degrades through the gate (`calm`)
- [ ] `command` covers every layer command; the confirm protocol works over the API
- [ ] Concurrent turn → 409; the server refuses to start without a token; the env guard runs first
- [ ] **Tests:** integration via FastAPI `TestClient` against a mock-model core — a full turn, each
  command family, `/image` with a fixture image, session/new, the 401/409 paths; no network, no paid API
- [ ] **Contract:** server API v1 in ARCHITECTURE + `tests/contract/test_server_api_contract.py` (route
  set, payload shapes, the token rule, the emotion contract on `turn`)
- [ ] **Gates:** `ruff` + `pytest`

### LUMI-213 — TUI client mode — LUMI_SERVER=on over a thin RemoteCore

**Description:**
With `LUMI_SERVER=on` the TUI runs no core: a `tui/remote.py` `RemoteCore` implements exactly the TUI's
non-command core surface (16 members) over the API, layer commands go to `POST /v1/command`, and the
features the server can't host yet degrade to a readable line.

**What needs to be done:**
- `tui/remote.py` `RemoteCore` (httpx, sync — the TUI already runs `reply` off-thread):
  - `reply(text, session, …)` → `POST /v1/turn` (stream callbacks ignored — blocking; the TUI's existing
    non-streaming path renders it); `start_session()` / `end_session()` → a local handle / no-op (the
    server owns the session); `clock` → the local clock;
  - `model`, `profile`, `thinking`, `style`, `last_emotion`, `last_stats`, `totals` → from the `/v1/state`
    snapshot refreshed after every turn/command (no network per status-line render);
  - `ensure_mood`, `ensure_backfill`, `set_world_context` → no-ops (the server does them);
  - `tick_think`, `run_directive` → a "not yet in server mode" outcome.
- `tui/__main__.py`: `LUMI_SERVER=on` → build `RemoteCore` from `LUMI_SERVER_HOST/PORT/TOKEN`; **no**
  `build_core`, **no** env guard, **nothing opened in the data root** (client logs go outside it); a
  server that isn't up → a readable startup message, not a traceback.
- `tui/app.py` in client mode: layer commands → `RemoteCore.command()` → render the `CommandResult`
  (same renderer as LUMI-211); `/new` → `POST /v1/session/new`; `/web` and `/image` → turns over the API;
  **degrade with "not yet in server mode"**: `/mode-set voice`, dictation (the listen toggle), the
  Telegram bridge, the scheduler / idle nudges / thought ticks, typed `%directives`. A dropped server
  mid-session → a readable line; the next input retries.
- `LUMI_SERVER` unset/off → the in-process path untouched.

**Dependencies:** LUMI-212

**Expected result:**
`LUMI_SERVER=on ./lumi` talks to the running server with the same chat, commands and status line;
everything the server can't do yet says so instead of breaking.

**Acceptance criteria:**
- [ ] Client mode builds no core and never opens the data root
- [ ] Turns, every layer command, `/new`, `/web`, `/image` work through the API (mock-model server)
- [ ] Each unsupported feature shows the "not yet in server mode" line
- [ ] A down/unreachable server → readable messages at start and mid-session, no traceback
- [ ] **Tests:** the TUI pilot harness against a `TestClient`-backed server (an httpx transport, no
  sockets): a turn, a command, `/new`, the degrade lines, the server-down path
- [ ] **Contract:** `tests/contract/test_remote_core_surface.py` — every `self._core.*` the TUI uses
  outside the command layer is implemented by `RemoteCore` (fails when the TUI grows a new dependency);
  `LUMI_SERVER` off → in-process turn + status line unchanged (pinned)
- [ ] **Gates:** `ruff` + `pytest`

### LUMI-214 — The CLI utility — serve, status, memory, model, config over the API

**Description:**
A new `cli/` package: `python -m cli <subcommand>` — a thin management client of the same API (the
token from `.env`), plus `serve` to run the server.

**What needs to be done:**
- Subcommands: `serve` (= `python -m server`); `status` (`/v1/state` + health: env, version, model,
  session turns); `memory show` (`/memory`); `memory clear` (asks `y/N` locally, then `/forget` with
  `confirmed=True`); `model [name]` and `model-set [profile]` (the layer commands); `config` (the
  effective non-secret config — env, version, data root, provider/model, feature flags; every key/token
  masked).
- Output: the `CommandResult` markdown printed as plain text; non-zero exit on API errors (401, server
  down) with a readable message.

**Dependencies:** LUMI-212

**Expected result:**
The server can be started, inspected and managed from a shell without opening the TUI.

**Acceptance criteria:**
- [ ] Every subcommand works against a mock-model server; `memory clear` never clears without `y`
- [ ] `config` never prints a secret (keys/tokens masked — pinned by a test)
- [ ] Readable errors + non-zero exit for 401 / server down
- [ ] **Tests:** unit — argument parsing, masking; integration — each subcommand via a `TestClient`
  transport; no network
- [ ] **Gates:** `ruff` + `pytest`
