## Findings

### 1. 🔴 No lock on a data root — two brains on one memory

**Anchor:** `server/__main__.py` (`main`), `tui/__main__.py` (`main`, the in-process path).
**Scenario:** v2.2 makes two ways to run a brain on the same instance — `./lumi` (in-process) and
`./lumi-server`. Started together (or two servers on different ports, or two `./lumi`), both open the same
store: the JSON aggregates in `store.json` are rewritten by each (lost updates), both compute the day's
mood and append to `mood.log`, both open their own sessions, the recall index gets two writers. The v2.1
env guard checks *which* instance owns a root, not *how many* processes use it; the docs only warn.
**Fix:** a process-lifetime exclusive `flock` on `<data root>/brain.lock`, taken by every brain (the
server, the in-process TUI) right after the env guard; a second brain gets a readable refusal naming the
holder (role, pid, since) and, if it's a server, the hint to use `./lumi-client`. Released by the OS on
exit — no stale locks after a crash. Bus peers (the Telegram daemons, voicer, dictator), the viewer, the
client and the CLI never take it.

### 2. 🟠 A non-JSON answer escapes `RemoteCore`

**Anchor:** `tui/remote.py::RemoteCore._call` (`return res.json()`).
**Scenario:** `LUMI_SERVER_PORT` points at something else (a dev web server, a proxy error page): a 200
with HTML → `res.json()` raises `JSONDecodeError`. At client start it isn't a `ServerUnavailable`, so
`_run_client` lets a traceback through; on a command (`_layer` in a worker) it isn't an `LLMError`, so the
TUI worker dies. Verified live with an HTML transport.
**Fix:** a non-JSON body → `ServerUnavailable("… answered, but not as a Lumi server (HTTP n)")`.

### 3. 🟡 EOF / Ctrl+C at the `memory clear` prompt

**Anchor:** `cli/main.py` (`ask(...)`).
**Scenario:** `./lumi-cli memory clear < /dev/null` (a script, a pipe) → `input()` raises `EOFError` → a
traceback (the safe direction — nothing is cleared — but not the readable-error rule). Verified live.
**Fix:** EOF / Ctrl+C at the prompt = "no" → `Cancelled.`

### 4. 🟡 "offline" sticks after a successful command

**Anchor:** `tui/app.py::_emit_server_error` sets `_connected = False`; only a successful turn sets it back.
**Scenario:** the server blips, the next thing you do is `/mood` (succeeds) — the status line still says
`offline · no connection` until you send a chat line.
**Fix:** a successful remote command restores `_connected` (+ a status repaint).

### 5–9. Deferred

- **5 (backlog):** echo a dim "queued" row for a command typed during a turn — changes the in-process look;
  the owner chose not now.
- **6 (backlog):** `connect()` could wait a few seconds for a starting server.
- **7 (v2.4):** the state events replace polling `/v1/state`; snapshot consistency belongs there.
- **8 (v2.6):** once the client and server sit on different machines, feature gates must come from the
  server's state, not the client's `.env`.
- **9 (v4.1):** request-size limits belong to the security hardening phase.

## What's solid

- **The token rule** — every guarded route rejects a missing/wrong token in constant time; the token never
  appears in a response or log; no docs/schema endpoints; the server refuses to start without one.
- **The emotion contract over the wire** — `turn` returns the gate-validated state; a malformed model reply
  still lands as `calm`.
- **The command layer is truly interface-free** (pinned by an AST test) and the in-process output stayed
  identical — the pre-existing suite passed untouched.
- **The client never touches a data root** (pinned) and its core surface is pinned against the TUI.
- **The CLI's `config`** masks every key/token — checked against the real dev `.env`.

## Architecture impact

- **One brain per data root (fix 1)** — a new invariant: every process that runs the core over a data root
  holds `<root>/brain.lock`; the second one is refused. Recorded in ARCHITECTURE §Configuration and secrets
  ("One brain per data root (v2.2)") and docs/SERVER_SETUP.md. Consequence the owner accepted: two `./lumi`
  on one instance no longer start. Future brains (the pywebview client is **not** one; the v2.5 server
  hosting the scheduler **is** the same brain) inherit the rule.
