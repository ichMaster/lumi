## Findings

### 1. 🟠 A retract right after the store keeps the reply — `core/space.py` `retract`

**Scenario:**
- A room turn passes its store-or-drop step (under the state lock) and stores her reply, but has not yet reached its
  `finally`, so `_running` still names it.
- matrix-agora's retract arrives in that instant. `retract` sees the turn as running, marks it abandoned and returns
  `True`, without removing anything.
- The turn's `finally` then clears the mark. The reply stays in the room's session and vectors: she remembers saying
  what the room never saw, and the bridge was told `{retracted: true}`.

v3.1 review #1's `abandon` closes the same window by also removing a stored reply. `retract` must do the same.

**Fix:** in `retract`, a running turn is marked *and* a stored reply is removed (line, vector, kept outcome).
Either one makes it `True`.

### 2. 🟡 A retracted reply in the running digest — deferred to the backlog

The running digest covers lines that have scrolled out of the last 20. A retract usually comes within a minute (the
bridge's own 60 s timeout), long before that. If one came later:
- the digest would still paraphrase the retracted reply;
- `upto` (a count of the session's oldest lines) would then skip one line.

This is rare and bounded; a fix needs digests keyed by line ids, not a count.

### 3. 🟡 A failed call counts — deferred (by design)

The cap counts model calls started, including those that then fail (`502`) or time out (`504`). That is the cost it
bounds, and matrix-agora's R5 asked for a cap on calls, so it stays.
