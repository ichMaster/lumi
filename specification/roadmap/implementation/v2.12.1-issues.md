# v2.12.1 — Issues

Issues for sub-phase **v2.12.1 — The chat** of phase **v2.12 — pywebview client: chat + face in one window**
(version **v2 — the server platform**), derived from the Tasks and DoD in [ROADMAP.md](../ROADMAP.md) §v2.12, the
contracts in [ARCHITECTURE.md](../ARCHITECTURE.md) and the owner's design in [design/v2.12/](../../../design/v2.12/).
This file covers one sub-phase (released as `2.12.1`, as v1.6.1 was); ids continue from v2.11
(LUMI-265 → **LUMI-266…269**).

The chat half of the desktop window: a Python shell opens a pywebview window onto a static page, the page holds a
whole conversation with the server — a streamed reply, her unasked messages, lines from Telegram and the terminal,
slash commands and `%directives`, a clean reconnect. The portrait panel, the think block, the quiet-thoughts strip and
inline pictures are **v2.12.2**.

**Reconciled with the real code (2026-11-14):**
- **The page can't call the server directly.** The roadmap says the page "speaks WS/HTTP directly to the server" with
  "no server changes", but the server sends no CORS headers, so a page in pywebview can't reach
  `http://192.168.1.197:8766` at all. **The owner chose a local proxy** (2026-11-14): the shell serves the page on
  `127.0.0.1` and forwards `/v1/*` to the server, adding the token itself.
  - No server change.
  - The token never enters the page.
  - The page uses relative `/v1` URLs, so v4.3 can serve it from the server unchanged.
  - v2.12.2 serves the local `faces/` pack from the same place.
- **The folder is `desktop/`, not `webview/`.** pywebview's import name is `webview`, so a `webview/` package would
  shadow it. The launcher is `./lumi-desktop`.
- **Settings are files.** The shell reads the tree's `settings.yaml` / `secrets.yaml` (`server.host`, `server.port`,
  `server.token`) through `core.config.load_config`, not `.env` (removed in v2.10). The URL comes from
  `tui.remote.server_url`. No new setting.
- **The push and stream protocol is the one `tui/remote.py` speaks** — the page mirrors it:
  - `POST /v1/turn/stream` streams `think` / `delta` / `done` / `error`, carrying a `turn_id`; a broken stream fetches
    the same id from `POST /v1/turn`, so she never answers twice;
  - `GET /v1/events` (SSE) sends `state` first, then the replay, then `message` / `turn` / `thought` / `state`, with
    `id:` fields for `Last-Event-ID` resume;
  - `X-Lumi-Client` names the client, and its own echoes come back with that `origin`;
  - `POST /v1/command` (`{line, confirmed}` → `{handled, result{text, kind, confirm, turn}}`);
  - `POST /v1/directive`;
  - `POST /v1/session/new`.
- **The interface is English** (the owner, 2026-11-14): `design/v2.12/handoff/strings.en.json`. Only her own content
  stays Ukrainian.

## v2.12.1 — The chat

### LUMI-266 — The desktop shell: the pywebview window + a local proxy that serves the page and forwards `/v1/*` with the token

**Description:**
A new `desktop/` package: `desktop/__main__.py` (`python -m desktop`) and `desktop/proxy.py`.

The shell reads the tree's client settings, starts a local proxy on `127.0.0.1`, and opens a pywebview window onto
it. The proxy serves the static page from `desktop/ui/` and forwards the public API to the server, adding the
`Authorization` header itself. No server change.

**What needs to be done:**
- **The config glue** (`desktop/proxy.py`, pure):
  - `load_config()` of the tree → `tui.remote.server_url(cfg)` + `cfg.server_token`.
  - No token or no host → the proxy still starts, and every `/v1` call answers `503
    {"kind": "no_server", "detail": …}`, so the page shows its "no server set" screen.
  - The token lives only in the proxy object (`repr` hides it) and never reaches a response or a log line.
- **The local server** (`ThreadingHTTPServer`):
  - It binds `127.0.0.1` on a free port (port 0).
  - `GET /` and `GET /<file>` serve `desktop/ui/`. A resolved path outside that folder is 404.
  - `index.html` is served with a per-launch random **key** in `<meta name="lumi-desktop-key">`.
- **The forwarding:**
  - Only the routes the page uses are forwarded: `GET /v1/health`, `GET /v1/state`, `GET /v1/events`,
    `POST /v1/turn`, `POST /v1/turn/stream`, `POST /v1/command`, `POST /v1/directive`, `POST /v1/session/new`.
    Anything else is 404.
  - Every forwarded request carries `Authorization: Bearer <token>`.
  - The page's `Content-Type`, `X-Lumi-Client` and `Last-Event-ID` pass through; its own `Authorization` (it has
    none) never does.
  - The response status passes through, and an SSE body is streamed **chunk by chunk** (flushed per chunk, no
    buffering), so `delta` frames arrive as she writes.
  - The server unreachable → `502 {"kind": "unreachable", "detail": …}`.
  - The server's 401 → `401 {"kind": "token_refused", "detail": …}`.
- **The local guard** (another app or a web page can reach `127.0.0.1` too):
  - every `/v1` request needs the launch key in `X-Lumi-Desktop-Key` (else 403);
  - the `Host` header must be `127.0.0.1:<port>` (else 403 — DNS rebinding);
  - the proxy never sends CORS headers, so a cross-origin page can't read anything back.
- **The window:**
  - `webview.create_window("Lili", url, width=1200, height=800, min_size=(720, 520))`, then `webview.start()`.
  - pywebview is imported lazily. Missing → a readable line ("the desktop extra isn't installed — run
    `./lumi-desktop`, which installs it"), exit 1.
  - Closing the window stops the proxy.

**Dependencies:** None

**Expected result:**
`python -m desktop` opens a window whose page reaches the configured server through `127.0.0.1`, with the token never
in the page.

**Acceptance criteria:**
- [ ] The proxy serves `desktop/ui/`, refuses a path outside it, and templates the launch key into `index.html`.
- [ ] Every allowlisted `/v1` route is forwarded with the token; any other path is 404; the page never sees the token.
- [ ] An SSE response is relayed frame by frame (the first frame reaches the client before the upstream finishes).
- [ ] `Last-Event-ID` and `X-Lumi-Client` pass through; 401 / unreachable / no server come back as `{kind, detail}`.
- [ ] A request without the key, or with a foreign `Host`, is 403; no response carries a CORS header.
- [ ] **Tests:**
  - unit — the config glue (URL, token, no-token → `no_server`);
  - integration — the proxy against a **fake upstream** (a local `ThreadingHTTPServer`; no real server, no
    network): static serving + traversal, the key and `Host` guard, the token added, SSE relayed incrementally, the
    headers passed, 401 / 502 / 503;
  - contract (`tests/contract/test_desktop_contract.py`) — the forwarded route set is exactly the public API the page
    uses; nothing serves the server's disk; no CORS header; the token never in a response body or header.
- [ ] **Gates:** `ruff`, `pytest`.

### LUMI-267 — The page — the chat: streamed replies, pushes, the input with the queue and slash commands, the status line, the connection states

**Description:**
`desktop/ui/` — `index.html` + `style.css` + `app.js` + `tokens.css` + `strings.en.json`. Vanilla JS, no framework, no
bundler.

The chat column of the owner's design ([design/v2.12/handoff/README.md](../../../design/v2.12/handoff/README.md)) at
high fidelity: flat, zero radius, 2px rules between regions and 1px hairlines inside, the per-theme accent from
`tokens.css`, the English strings. The portrait panel is v2.12.2, so in this sub-phase the chat takes the full width.

**What needs to be done:**
- **The assets:**
  - `tokens.css` and `strings.en.json` are copied from `design/v2.12/handoff/`.
  - Fonts: the system stack (`-apple-system`, SF Pro), never Google Fonts, so the window needs no network.
  - The root gets `data-theme` from `state.theme` and `data-appearance="dark"`.
  - No title bar of its own: the native window has one.
- **Connecting:**
  - `GET /v1/state`, then the push channel `GET /v1/events`, read with `fetch` + a `ReadableStream` SSE parser
    (`EventSource` can't send the key header).
  - The parser mirrors `tui.remote.parse_sse_frames`: event / id / data, `:` heartbeats, multi-line data.
  - Resume with `Last-Event-ID`. No byte for ~45 s means the stream is dead.
  - Backoff 5 → 10 → 15 → 30 s, with the "connecting" / "the server isn't answering" (live countdown, "Retry now") /
    "connection restored" banners. Missed lines are inserted under the "While offline · N" divider.
  - `{kind: "token_refused"}` → the token-refused screen; `{kind: "no_server"}` → the no-server screen. The copy is
    from `strings.en.json`.
- **A turn:**
  - `POST /v1/turn/stream` with a fresh `turn_id` and `X-Lumi-Client: <this page's id>`.
  - Before the first `delta`: the thinking indicator (three accent squares + "thinking…").
  - Then the text as it arrives, with the block caret. `think` frames are read and dropped (the think block is
    v2.12.2).
  - `done` → the final render + the status numbers (first character, whole reply, tokens).
  - A broken stream → `POST /v1/turn` with the same `turn_id`, so she never answers twice.
  - `error` → "The reply was cut off · Retry".
  - The server's 409 (busy with another client) → the line waits in the queue and is retried.
- **Her replies in markdown** — a small safe subset: paragraphs, bold / italic, inline code + code blocks, quotes,
  lists, links (`http`/`https` only, opened outside the window). It is built as DOM nodes, never `innerHTML`.
- **Pushes:**
  - `message` from another channel → a row with the source tag (Telegram / Terminal).
  - Her own unasked line (`source` `thought` / `nudge`) → the "wrote first" marker.
  - The page's own echoes (`origin` == its client id) are skipped.
  - `state` → the status line, the theme accent and the empty state's mood.
  - `turn` and `thought` are kept for v2.12.2 and not rendered now.
  - The replay on connect fills the current session's conversation.
- **The input:**
  - Enter sends; Shift+Enter adds a line (not while an IME is composing). The textarea grows to 6 rows.
  - Lines sent while she answers queue (dimmed, "queued", the counter) and go out one by one after each `done`.
  - The slash popover lists the commands from `strings.en.json`: prefix filter, ↑ ↓ (wrapping), Tab inserts, Esc
    closes, Enter on an exact command sends.
  - `/new` → `POST /v1/session/new` + the "New session" divider.
  - `/web <q>` (`/search`, `/w`) → a normal turn with `<q>`.
  - `%…` → `POST /v1/directive`, and its outcome shows as a line.
  - Any other `/…` → `POST /v1/command`:
    - `handled` → the command block (key–value or free text);
    - `confirm` → the window's confirm dialog, then resent with `confirmed: true`, or "cancelled";
    - `turn` → run as a normal turn;
    - not handled → "not a command in this window".
  - `/image` (sharing a local file) is the terminal's for now → a readable line.
- **The status line:**
  - ready / answering / connecting / offline.
  - A DEV badge when `state.env != "prod"`.
  - "Lumi <version> · details" opens the panel: environment, version, model, profile, thinking, style (the English
    label from `strings.en.json`), first character, whole reply, tokens, exchanges.
  - The chat text size: A− / A+ and ⌘− / ⌘+, 14–22 px, kept in `localStorage` (wrapped in try/catch; it works
    without it).
- **The empty state:** a new session shows the mood of the day large ("Mood of the day · <weekday>, <date>"), and the
  input stays.
- **Accessibility:**
  - `role="log"` on the list;
  - real `<button>` / `<label>`;
  - `:focus-visible` in the accent;
  - every animation off under `prefers-reduced-motion`.

**Dependencies:** LUMI-266

**Expected result:**
In the window, a whole conversation with the server works the way it does in the TUI client — streamed, with
pushes, commands and reconnects — in the owner's design.

**Acceptance criteria:**
- [ ] A turn streams into the chat (the indicator, then the text with the caret, then the final markdown render), and
      a broken stream recovers its outcome by `turn_id`, never a second answer.
- [ ] Her unasked line shows with "wrote first"; Telegram and terminal lines carry their tag; the page's own echoes
      are not doubled.
- [ ] Lines sent while she answers queue and go out in order; the slash popover and every command path work (block,
      confirm, turn, `/new`, `/web`, `%directive`, not handled).
- [ ] A dropped server → the banner with the countdown, the input disabled; back → the missed lines under the
      divider and the "restored" banner; 401 and no-server → their screens.
- [ ] Every UI string comes from `strings.en.json` (no Cyrillic in `app.js` / `index.html`); no `innerHTML`; the
      markdown links are `http`/`https` only.
- [ ] **Tests:**
  - static (`tests/unit/test_desktop_static.py`, as `test_admin_static.py` does) — no `innerHTML` / `outerHTML` /
    `insertAdjacentHTML` / `document.write`; no Cyrillic in the page's own files; every `strings.en.json` key the
    page uses exists; the turn path keeps a `turn_id` and falls back to `POST /v1/turn` (there is no JS runtime in
    CI, so the parser's behaviour is checked live in LUMI-269);
  - integration — the proxy serves the whole page (`index.html` with the key, `app.js`, `style.css`, `tokens.css`,
    `strings.en.json`).
  - No browser automation in CI (the ROADMAP rule): rendering is LUMI-269's manual check.
- [ ] **Gates:** `ruff`, `pytest`.
