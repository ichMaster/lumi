## Findings

### 1. 🟠 Acts after the stop; drained lines lost

**Anchor:** `server/brain.py::inbox_tick` / `scheduler_tick` (the loops), `server/__main__.py` (stop order).
**Scenario:** three Telegram lines arrive in one burst; `inbox_tick` drains all three (the pointer jumps past
them) and starts the first turn. Ctrl+C: uvicorn stops, `brain.stop()` gives up after 2 s (a turn is running),
`close_session` waits for the lock. The first turn ends; the loop goes on to line 2 and asks for the lock
again — racing `close_session`. If the close wins, `end_session` summarizes and `main` returns while the host
starts line 2 on the **closed session** and is killed at exit mid-turn; either way lines 2–3 never get an
answer, and the pointer says they were handled. The scheduler's loop over several due entries has the same
shape.
**Fix:** the host checks its stop flag before every act (the first Ctrl+C asks it to stop, alongside closing
the event streams), and the server advances the inbox pointer **per line, after its turn** — an unreached line
waits for the next start (at-least-once: a hard kill mid-turn may answer that line twice, never lose it).

### 2. 🟡 The startup mood runs outside the lock

**Anchor:** `server/__main__.py` (`_background("mood", …)`), `core/agent.py::_housekeeping_reply`.
**Scenario:** v2.4 #3: housekeeping calls flip `llm._thinking` off on the client the turns share. In v2.5 every
host act takes the lock, so the one remaining unserialized model call is the startup mood (~30 s). A client
turn — or a host catch-up act — in that window can run with the thinking flag flipped (no thinking config /
no headroom → the '…' risk), or restore it wrongly.
**Fix:** run the startup mood as the server's own act (`service.background()`): a client turn waits for it
(the first turn needed today's mood anyway — the v2.4 single-flight), the host's acts serialize with it.

### 3. 🟡 A stale idle anchor

**Anchor:** `server/brain.py::_maybe_think`.
**Scenario:** `idle_tick` sees the lock free, `_maybe_think` computes `anchor = max(last_input, last_think)`,
then waits for the lock — a client turn that grabbed it in between finishes and moves `last_input`, but the
think runs with the old anchor and may fire (even speak) right after you spoke.
**Fix:** compute `now` and the anchor inside the lock.

### 4–6. Deferred

- **4 (backlog):** in-process the catch-up acts run as workers beside the inbox poll; here they run first. A
  short catch-up is the normal case; run it on the beat if it ever matters.
- **5 (v2.8):** the API never carries images (by contract); a "📷 sent a picture" `message` line or the face
  client's gallery is the place for it.
- **6 (backlog):** fine for her current acts (a news brief is ~1 min); a queue position line would be the
  better UX if acts grow.

## What's solid

- **One mind at a time:** every host act holds the lock as the server's own; client requests wait for it, two
  clients still `409`; the scheduler never fires while a turn runs and never loses a due entry to a busy tick.
- **The single outbox writer:** every outbox write happens under the lock; no echo of an inbox line.
- **The replay is exact:** subscribe-and-replay is atomic with publish; ids are boot-scoped; a resume replays
  only what was missed; replayed lines are flagged and introduced once in the TUI; own lines are skipped.
- **In-process unchanged:** the moves re-export, the shared decisions are pinned (the spoken seed lives in one
  place), the TUI suites pass untouched.
- **The live DoD held end to end** (a scheduled thought to Telegram with no client, then the replay on open).
