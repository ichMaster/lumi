# v2.8 — Issues

Issues for phase **v2.8 — Lumi in Docker: one image, a compose project per instance** (version **v2 — Client/server
split: her brain on the server, the TUI a thin client**), derived from the Tasks and DoD in
[ROADMAP.md](../ROADMAP.md) §v2.8 and the contracts in [ARCHITECTURE.md](../ARCHITECTURE.md). This file covers one
phase; ids continue from the previous phase (LUMI-237 → **LUMI-238…243**).

v2.8 replaces the v2.6 systemd user units with **one Docker image** (built by CI, pushed to GHCR) and a **compose
project per instance** on the box — the matrix-agora pattern on the same machine. The v2.7 deploy agent keeps its
decisions, smoke and rollback but deploys **image tags** instead of git checkouts. Settings stay in each instance's
`.env` (YAML is v2.9); the admin panel is v2.10–v2.11.

## v2.8 — Lumi in Docker

### LUMI-238 — The image: `Dockerfile` + `.dockerignore`, the guards' container mode, the baked build

**Description:**
One image runs every Lumi process on the box (the server, both Telegram daemons). Inside a container the two v2.x
guards need a **container mode**: the v2.6 bind guard refuses `0.0.0.0` (`server/__main__.py` `bind_problem`), and
the v2.1 env guard (`core/envguard.py`) today only *warns* and skips the clean-tagged check when there is no git
checkout — so prod would start from any image. Touches `Dockerfile` (new), `.dockerignore` (new),
`server/__main__.py`, `core/envguard.py`, `specification/ARCHITECTURE.md` §Configuration, tests.

**What needs to be done:**
- `Dockerfile` (the agora pattern, `matrix-agora/agents/Dockerfile`): `python:3.13-slim` (CI's Python); `ffmpeg` (her
  Telegram voice replies) and `tzdata` (her local day — the mood, quiet hours and the scheduler run on local time);
  `uv` copied from `ghcr.io/astral-sh/uv`; `uv sync --frozen --all-extras --no-install-project` into `/app/.venv` (the
  lock exactly, as `./lumi-server` runs today); the code at `/app` (no `.git`, no `.env`, no data); a non-root user
  `1000:1000` (the box's `ich` owns both data roots); `PYTHONUNBUFFERED=1`; `ENV LUMI_CONTAINER=1`; `LUMI_HOME=/data`
  as the default; the build ref baked as `ARG LUMI_BUILD` → `ENV LUMI_BUILD` (+ OCI labels `org.opencontainers.image.
  version` / `.revision`); `HEALTHCHECK` on `/v1/health` (stdlib urllib, the port from `LUMI_SERVER_PORT`); `CMD
  ["python", "-m", "server"]`. The daemons run the same image with another command (LUMI-240).
- `.dockerignore`: `.git`, `.env*`, `.lumi/`, `.venv/`, `tests/`, `specification/`, `docs/`, caches — no secret and
  no lived data can enter a build context.
- **The bind guard's container mode:** `bind_problem` allows the wildcard (`0.0.0.0`, `::`) only when **both**
  `LUMI_CONTAINER=1` and `/.dockerenv` exist (an env var alone on the host doesn't open it); exposure is then the
  compose publish rule's job (LUMI-240). Everything else is unchanged.
- **The env guard's container mode:** in a container (same test) there is no checkout to inspect; prod requires the
  baked `LUMI_BUILD` to be a release tag `vA.B.C` (the image built from a tag) — the container twin of "a clean,
  tagged checkout"; dev runs any build; `LUMI_ALLOW_DIRTY_PROD=1` keeps its emergency meaning; the marker checks are
  unchanged. The badge / `/v1/health` version stays the image's `VERSION` file.
- ARCHITECTURE §Configuration: the container mode of both guards.

**Dependencies:** None

**Expected result:**
`docker build .` produces one image whose server starts in a container on `0.0.0.0` and refuses to run as prod from a
non-release build.

**Acceptance criteria:**
- [ ] The image builds from the lock (`--frozen --all-extras`), runs as `1000:1000`, has ffmpeg + tzdata, carries no
      `.env`, `.git`, test data or secret, and reports its build in `LUMI_BUILD` + the OCI labels.
- [ ] In a container the server binds `0.0.0.0`; outside one, `LUMI_CONTAINER=1` alone does not open the wildcard.
- [ ] Prod in a container refuses a non-release build (`edge`, `sha-…`) with a readable line and accepts `vA.B.C`;
      dev accepts any; the override and the marker checks behave as before.
- [ ] **Tests:** `bind_problem` and the env guard's container mode as pure functions over an injected
      "in a container" predicate + environ (no Docker); a Dockerfile/.dockerignore lint test (non-root user,
      `HEALTHCHECK`, `--frozen --all-extras`, ffmpeg + tzdata, `LUMI_CONTAINER`, `.git`/`.env*`/`.lumi` ignored, no
      secret-shaped value). No network, no paid API.
- [ ] **Contract:** the env guard + bind guard rules (ARCHITECTURE §Configuration updated); `test_envguard_contract.py`
      extended for the container case.
- [ ] **Gates:** `ruff`, `pytest`.

### LUMI-239 — CI builds the image and pushes it to GHCR, with a container smoke

**Description:**
A second workflow builds the LUMI-238 image on every push and pushes it to GHCR with the workflow's own token — no
extra secret (the v2.7 `ci.yml` keeps its read-only, secret-free test). Touches `.github/workflows/image.yml` (new),
`tests/unit/test_image_workflow.py` (new).

**What needs to be done:**
- `.github/workflows/image.yml` (the agora job, `matrix-agora/.github/workflows/ci.yml`): on `push` (every branch, so
  a pull request's image builds too) and on tags `v*`; `permissions: contents: read, packages: write`;
  `docker/setup-buildx-action` → `docker/metadata-action` → `docker/login-action` (`ghcr.io`, `github.actor`,
  `secrets.GITHUB_TOKEN`, push events only) → `docker/build-push-action` (`linux/amd64`, GHA cache). Tags:
  `:edge` + `:sha-<short>` on `main`; `:vA.B.C` + `:latest` on a release tag; pushed only from `main` and tags (a
  branch build is built and smoked, not pushed). `LUMI_BUILD` build-arg = the tag on a release, `sha-<short>`
  otherwise.
- **A container smoke** in the same job, before the push: run the built image with a test config — `LUMI_ENV=dev`,
  a throwaway `LUMI_SERVER_TOKEN`, a temporary data dir mounted at `/data`, a dummy provider key (the server never
  calls the model to start) — and require `/v1/health` to answer `{"ok": true, "env": "dev", "version": <VERSION>}`
  within a timeout; then `docker stop` and require a clean exit (the SIGTERM path). No paid call.
- The v2.7 agent counts **every** check run of a commit, so these jobs gate the dev deploy by themselves: a `main`
  commit is "green" only once its image exists.

**Dependencies:** LUMI-238

**Expected result:**
A push to `main` publishes `ghcr.io/ichmaster/lumi:edge` + `:sha-<short>`; a release tag publishes `:vA.B.C` +
`:latest`; each image was seen answering `/v1/health` first.

**Acceptance criteria:**
- [ ] The workflow builds on every push, pushes only from `main` and `v*` tags, with exactly those tags.
- [ ] The container smoke runs before the push and fails the job if `/v1/health` doesn't answer as `dev` with the
      image's version, or the container doesn't stop cleanly.
- [ ] **Tests:** a workflow lint test — the triggers, `packages: write` only here, the only secret is
      `GITHUB_TOKEN`, the tag rules, the smoke step before the push; `test_ci_workflow.py` still passes unchanged.
- [ ] **Gates:** `ruff`, `pytest`; the workflow green on its first push.

### LUMI-240 — A compose project per instance: three services, the data root bind-mounted, LAN-only

**Description:**
One compose file, parameterized per instance, runs the server and both Telegram daemons from the image, sharing the
instance's data root (the file bus needs one filesystem) and its `.env`. Touches `deploy/compose/compose.yaml` (new),
`deploy/compose/prod.env` + `dev.env` (new — instance parameters, no secret), `tests/contract/test_compose_contract.py`
(new).

**What needs to be done:**
- `compose.yaml`: `name: lumi-${LUMI_INSTANCE}`; `image: ghcr.io/ichmaster/lumi:${LUMI_IMAGE_TAG:?…}` — **no default**,
  so a hand-run `compose up` never silently takes `:edge` (the agent always passes the tag); services `server`,
  `telegram-inbound` (`python -m telegram.inbound`), `telegram-outbound` (`python -m telegram.outbound`); each with
  `env_file: ${LUMI_INSTANCE_DIR}/.env` (the instance's settings, unchanged — compose reads `KEY=value  # comment`
  lines) and `environment:` overriding what differs inside a container: `LUMI_HOME=/data`, `LUMI_SERVER_HOST=0.0.0.0`,
  `TZ=${LUMI_TZ}`; `volumes: ${LUMI_INSTANCE_DIR}/data:/data`; `user: "1000:1000"`; `init: true` (tini as PID 1 —
  SIGTERM reaches python and ffmpeg children are reaped); `restart: unless-stopped`; `stop_grace_period` ≥ the units'
  `TimeoutStopSec` (300 s — the session close makes model calls). The server publishes **only** on the LAN address
  (`${LUMI_PUBLISH_HOST}:${LUMI_SERVER_PORT}:${LUMI_SERVER_PORT}`); the daemons publish nothing and disable the
  image's healthcheck (they run no server).
- `prod.env` / `dev.env`: `LUMI_INSTANCE`, `LUMI_INSTANCE_DIR` (`/home/ich/lumi/<instance>` — compose needs an absolute
  path), `LUMI_PUBLISH_HOST=192.168.1.197`, `LUMI_SERVER_PORT` (8765 / 8766 — the same as the instance's `.env`, the
  ufw rule unchanged), `LUMI_TZ=Europe/Kyiv`. No key, no token.
- The brain lock (`data/brain.lock`, a `flock`) holds across the host and the containers (one kernel), so a v2.6 unit
  and a container can never run two brains on one root during the move.

**Dependencies:** LUMI-238

**Expected result:**
`LUMI_IMAGE_TAG=… docker compose --env-file deploy/compose/dev.env -f deploy/compose/compose.yaml up -d` runs dev's
three services on its data root, reachable only on the box's LAN address.

**Acceptance criteria:**
- [ ] Three services from one image; the data root bind-mounted at `/data`; settings only through `env_file`; the
      LAN-only publish; init, restart policy, grace period, uid as above; the daemons without a healthcheck.
- [ ] `docker compose config` resolves for both instances with a tag, and fails without one.
- [ ] **Tests:** a contract test over the YAML — the data root bind-mounted, the publish host a LAN (RFC 1918) address
      and never `0.0.0.0` on the host side, no secret-shaped value in `compose.yaml` / `prod.env` / `dev.env`,
      `LUMI_HOME=/data` + `LUMI_SERVER_HOST=0.0.0.0` overridden, `stop_grace_period` ≥ 300 s, no image default.
- [ ] **Contract:** the compose files bind-mount the data root, publish only on a LAN address and carry no secret
      (ARCHITECTURE §Deployment) — pinned by `test_compose_contract.py`.
- [ ] **Gates:** `ruff`, `pytest`.

### LUMI-241 — The deploy agent deploys images; the v2.6 units retired on the first container deploy

**Description:**
`scripts/deploy_agent.py` keeps its decisions (`ci_verdict`, `dev_action`, `prod_action`), its smoke and its rollback,
but a switch becomes `docker compose pull` + `up -d` with an image tag instead of `git checkout` + `uv sync` +
`systemctl`. Touches `scripts/deploy_agent.py`, `tests/unit/test_deploy_agent.py`,
`tests/contract/test_deploy_smoke_meets_the_api.py`, `deploy/systemd/lumi-deploy.service` (if its PATH needs docker).

**What needs to be done:**
- **Refs → image tags:** dev deploys `sha-<short>` of the green `main` commit (immutable, so the previous one is a
  rollback target; `:edge` stays the moving pointer for humans); prod deploys `vA.B.C`. The state keeps the git ref
  it already holds and derives the tag; the "contains what dev runs" rule still reads git (`merge-base`, via the dev
  checkout kept for that — no code runs from it).
- **The switch:** `docker compose -p lumi-<instance> --env-file <compose>/<instance>.env -f <compose>/compose.yaml pull`
  then `up -d` with `LUMI_IMAGE_TAG=<tag>` in the environment. A recreate stops each old container first (SIGTERM →
  her session close inside the old image — no mixed-version window by construction). Prod keeps the archive before
  the switch (`compose stop server` → `tar` → switch). A failed pull deploys nothing.
- **The smoke** over containers: `/v1/health` on the instance's address (as the instance, the expected version — the
  image's `org.opencontainers.image.version` label), `/v1/state` with its token, each of the three containers
  `running` with the **same container ID and `RestartCount`** across the stable minute (the v2.7 review #2 rule,
  translated from `InvocationID`), the health again at its end, no new `ERROR` in `data/lumi.log`.
- **The units retired:** before an instance's first container deploy, if its v2.6 units are enabled, the agent
  stops and disables them (`systemctl --user disable --now lumi-server@<i> lumi-telegram-inbound@<i>
  lumi-telegram-outbound@<i>`) — the port and the brain lock are then free; it never removes the unit files.
- `install` also copies `deploy/compose/` into `~/lumi/deploy/compose/` (the agent never runs compose from a checkout).
- `status` shows each instance's image tag.

**Dependencies:** LUMI-239, LUMI-240

**Expected result:**
A green `main` commit reaches dev as its `sha-` image; a confirmed tag reaches prod as `vA.B.C`; a failed smoke rolls
back to the previous image tag; the units are gone from the running set after the first container deploy.

**Acceptance criteria:**
- [ ] dev: green `main` → `sha-<short>` pulled + up + smoke; red / pending / behind → nothing (the v2.7 rules).
- [ ] prod: only the confirmed newest tag; archive first; a failed smoke → the previous tag; `rollback prod` one
      command.
- [ ] A crash-restart inside the stable minute fails the smoke (container ID / `RestartCount` changed).
- [ ] The first container deploy disables the instance's units; later deploys don't touch systemd.
- [ ] **Tests:** the fake world over `docker compose` / `docker inspect` / `systemctl` (no Docker, no network): the
      command sequences (deploy, smoke fail → rollback, archive → switch, units retired once), the tag derivation, the
      smoke's container checks; the v2.7 contract kept — a full deploy + rollback leaves `data/` and `.env`
      byte-identical; the real-API smoke contract still passes.
- [ ] **Gates:** `ruff`, `pytest`; the agent still loads on the box's Python 3.10.
