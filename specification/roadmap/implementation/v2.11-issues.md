# v2.11 — Issues

Issues for phase **v2.11 — The admin panel: configure** (version **v2 — Client/server split: her brain on the
server, the TUI a thin client**), derived from the Tasks and DoD in [ROADMAP.md](../../ROADMAP.md) §v2.11, the
design in [ADMIN_PANEL.md](../../features/ADMIN_PANEL.md) §v2.11 and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md). This file covers one phase; ids continue from the previous phase
(LUMI-258 → **LUMI-259…265**).

The v2.10 panel starts **changing** settings. A schema-driven editor validates every value, shows the diff and
applies it atomically with the restart it needs; prod needs a typed confirmation. Secrets are write-only. Every apply
keeps the previous file, and one click rolls it back. The schedule and model-profile overrides get their own editors,
a setting tried on dev can be promoted to prod, every action lands in an audit log, and a dedicated admin bot sends
one Telegram alert when a prod check fails and one when it recovers. Users and the allowlist in the panel are v4.4.

**Grounded in the real code (2026-11-11):**
- **What `core/settings.py` already has:**
  - the schema `SETTINGS` (key, alias, type, default, description, `secret`, `restart`, choices / range);
  - `problem` / `to_env` (validation), `parse_cli_value`;
  - `set_in_text` (one line, verified, or a refusal);
  - `write_atomic` / `write_private` (temp + `os.replace`, `0600` from the first byte);
  - `check_folder`, and the `models:` / `schedule:` checks (`_check_models` / `_check_schedule`).

  Missing: replacing a whole structured section.
- **The v2.10 panel** mounts each instance folder **read-only**, so v2.11 must open the folder for writing while
  `data/` stays read-only. The v2.10 contract test pins "no write into a data root" — it stays.
- **The deploy agent** holds `fcntl.flock(LOCK_EX | LOCK_NB)` on `~/lumi/deploy/agent.lock` during a step. A panel
  action in that window fails the agent's smoke (v2.10 review #4, deferred to here).
- **Restarts.** Every setting is `restart=True`. The instance containers bind-mount `settings.yaml` / `secrets.yaml`
  as single files, and an atomic `os.replace` gives the file a new inode, so the running container keeps the old
  content until it is restarted. The apply restarts the instance's three services, which re-resolve the mount.
  Verified live in LUMI-265.

### LUMI-259 — The edit engine: settings as a view, validate → diff → apply with history, rollback, write-only secrets

**Description:**
Pure-ish functions over an instance folder that read its settings as a schema-driven view and change them safely.
Touches `admin/edit.py` (new), `core/settings.py` (`unset_in_text`, `last4`), tests.

**What needs to be done:**
- **The view.** Per group, for every schema setting:
  - its key, env name, type, choices / range, default, description and `restart`;
  - its current value in the files and its source (`default` / `settings.yaml` / `secrets.yaml`);
  - for a secret: `set` / `unset` and the **last four characters** only — never the value.

  It also names the settings the container's environment overrides: the compose `environment:` names `LUMI_HOME`,
  `LUMI_SERVER_HOST`, `LUMI_SERVER_PORT` and `LUMI_SETTINGS_DIR`.
- **Preview** `{key: text}`:
  - each value is parsed (`parse_cli_value`) and validated (`problem`), and every refusal names the key and the
    allowed values;
  - the change is applied to the file texts in memory (`set_in_text` / `unset_in_text`);
  - the result is a unified diff of `settings.yaml`. For `secrets.yaml` only key-level lines are shown
    (`server.token: •••a1b2 → •••c3d4`), never a value.
- **Apply** (the same input + the expected current file hashes, so a concurrent edit is refused):
  1. copy the current `settings.yaml` / `secrets.yaml` to `~/lumi/<instance>/config-history/<ts>-<file>` (the secrets
     copy `0600`);
  2. write the new files atomically (`write_atomic` / `write_private`);
  3. report which services need a restart.

  An invalid value **never** reaches a file.
- **Rollback** `<ts>`:
  - restore that history entry's files atomically;
  - the current files go to history first, so a rollback can itself be rolled back.
- **History list:** timestamps, the files, the changed keys. Secret keys are named, never valued.
- **Write-only secrets:**
  - set / rotate (a new value) / clear (remove the line);
  - the result is `set` / `unset` + last4;
  - rotating `server.token` names who needs the new one (the clients' `secrets.yaml`; the deploy agent and the panel
    read it from the instance).

**Dependencies:** None

**Expected result:**
Given an instance folder, a change is validated, previewed as a diff, applied atomically with the previous files
kept, and rolled back with one call; a secret is set or cleared without ever being returned.

**Acceptance criteria:**
- [ ] Preview and apply over fixture folders:
  - the diff is exact;
  - an invalid value is refused with the allowed values and both files stay byte-identical;
  - a stale hash is refused.
- [ ] Apply keeps the previous files in `config-history/` (the secrets copy is `0600`). Rollback restores them, and
      rolling back that rollback works.
- [ ] Secrets: set / rotate / clear; the view and every result show only `set` + last4. A known secret value appears
      in no returned structure.
- [ ] **Tests:** `tests/unit/test_admin_edit.py`; `tmp_path` only.
- [ ] **Gates:** `uv run ruff check .` + `uv run pytest -q` green.

### LUMI-260 — The schedule and model-profile editors + promote dev → prod

**Description:**
The instance's overrides of `core/schedule.yaml` and `core/models.yaml` are its `settings.yaml` `schedule:` and
`models:` sections (v2.9). They are edited as YAML text, validated by the existing checks and applied through the
LUMI-259 engine. A setting tried on dev is promoted to prod. Touches `core/settings.py` (`set_section`),
`admin/edit.py`, tests.

**What needs to be done:**
- `set_section(text, name, data)` replaces one top-level section (`schedule` / `models`) of `settings.yaml`, keeping
  every other line and comment. It is verified by re-parsing; an empty value removes the section.
- **The section editors:**
  - the input is the section as YAML text, validated by `_check_schedule` / `_check_models` (an unquoted `19:00` is
    refused, as in v2.9);
  - preview shows the diff; apply / history / rollback go through LUMI-259;
  - the merged result is shown: the authored rows / profiles plus the instance's changes (`core.schedule.merge_rows`
    / the profile merge).
- **Promote dev → prod:**
  - the input is a list of keys;
  - a secret, and a per-instance setting (`instance.env`, `instance.home`, `server.host`, `server.port`,
    `server.client_mode`), are refused with the reason;
  - the result is the prod diff (dev's values over prod's), applied on prod only with the typed confirmation.

**Dependencies:** LUMI-259

**Expected result:**
An instance's schedule and profiles change in its own `settings.yaml` from the panel, validated and reversible, and
a dev setting reaches prod only through its diff and the confirmation.

**Acceptance criteria:**
- [ ] `set_section`:
  - replace, add and remove keep the other lines and comments;
  - an invalid section (`at: 19:00`, a profile that isn't a mapping) is refused with nothing written.
- [ ] The merged schedule shows an overridden row and an added row; the authored ids are kept.
- [ ] Promote: the prod diff of the chosen keys; secrets and per-instance keys refused; nothing written without the
      confirmation.
- [ ] **Tests:** extend `tests/unit/test_admin_edit.py` + a `set_section` test in `tests/unit/test_settings_loader.py`.
- [ ] **Gates:** `uv run ruff check .` + `uv run pytest -q` green.

### LUMI-261 — The audit log for every action + the deploy-agent lock guard on every action

**Description:**
Every admin action — a service start / stop / restart (from v2.10), an apply, a rollback, a section edit, a promote,
a secret set / rotate / clear — appends one line to `~/lumi/admin/audit.jsonl`. No action runs while the deploy agent
holds its lock (v2.10 review #4). Touches `admin/audit.py` (new), `admin/guard.py` (new), tests.

**What needs to be done:**
- **The audit line:** `{ts, action, instance, target, changes, result}`.
  - `changes` is `{key: [old, new]}` for a plain setting and `{key: "(secret)"}` for a secret — **never** a secret
    value.
  - `result` is `done` / `refused: <why>` / `failed: <why>`; a refused action is logged too.
  - Appended under a lock, rotated at a size cap.
- `read(limit, instance?)` returns the newest first, for the page.
- **The agent-lock guard:**
  - `agent_busy(lock_path)` tries `flock(LOCK_SH | LOCK_NB)` on a read-only handle of `~/lumi/deploy/agent.lock`
    (mounted read-only);
  - held → "a deploy step is running — try again in a minute", and the action is refused (and audited);
  - a missing file → not busy.

**Dependencies:** LUMI-259

**Expected result:**
Every action the panel takes or refuses is one audit line without a secret value, and no action collides with a
deploy.

**Acceptance criteria:**
- [ ] Lines for each action kind. A secret change is logged as `(secret)`, and its value is absent from the file
      (asserted).
- [ ] `agent_busy`:
  - true while another process holds `LOCK_EX` (a subprocess in the test);
  - false when released or missing;
  - the guard refuses and audits the refusal.
- [ ] **Tests:** `tests/unit/test_admin_audit.py`; `tmp_path` only.
- [ ] **Gates:** `uv run ruff check .` + `uv run pytest -q` green.

### LUMI-262 — Alerts: a dedicated admin bot — one message when a prod check fails, one when it recovers

**Description:**
After each health run, an alert state machine sends the owner one Telegram message when an instance starts failing
(any check red) and one when it recovers, through a **dedicated admin bot** — never her prod or dev bot.
Touches `admin/alerts.py` (new), `admin/registry.py` (the `alerts:` block), `admin/health.py` (a hook after
`run_once`), tests.

**What needs to be done:**
- **Configuration:**
  - `admin.yaml` `alerts: {chat_id: <the owner's Telegram id>, instances: [prod]}`;
  - the bot token is `secrets.yaml` `alerts.telegram_token` — its own BotFather token, never logged;
  - no token or no chat id → alerts off, the page says so.
- **The machine** (pure, the clock injected):
  - per instance, the set of red checks;
  - none → some red: one "⚠ prod failing: server (down — unreachable), state (…)" message;
  - some → none: one "✓ prod recovered after 3 min" message;
  - a change inside the failing episode sends nothing more;
  - **rate limit:** at most one failing message per instance per 10 minutes; a recovery is always sent after a
    failing message, and never without one.
- **The sender:** `TelegramSender` (stdlib `urllib`, `sendMessage` to the one chat, a short timeout) and a fake.
  A send failure is logged without the token, never raised into the health runner.

**Dependencies:** None

**Expected result:**
Stopping prod's server sends exactly one alert, and its restart exactly one recovery message, through the admin bot.

**Acceptance criteria:**
- [ ] The machine over scripted runs:
  - green → red(server, state) → red(server) → green sends exactly two messages, naming the checks and the
    duration;
  - a flapping instance within 10 minutes sends one failing message;
  - dev is ignored unless listed.
- [ ] The sender:
  - over a fake HTTP, the URL carries the token only in the path and the body has the chat id and text;
  - a failure is swallowed and logged with no token in the log (asserted).
- [ ] Alerts are off (the health runner unaffected) without a token or a chat id.
- [ ] **Tests:** `tests/unit/test_admin_alerts.py`; no network, no real Telegram.
- [ ] **Gates:** `uv run ruff check .` + `uv run pytest -q` green.

### LUMI-263 — The API + the UI: Settings, Secrets, History, Schedule & Models, Promote, Audit

**Description:**
The routes and the page for everything above. Every action restarts what the change needs through the container
runner, refuses during a deploy, needs the typed confirmation on prod, and is audited. Touches `admin/app.py`,
`admin/static/{index.html,app.js,panel.css}`, `tests/integration/test_admin_api.py`,
`tests/contract/test_admin_contract.py`, `tests/_admin_world.py`, `specification/ARCHITECTURE.md`.

**What needs to be done:**
- **Routes** (all behind the admin token):

  | Route | Does |
  |---|---|
  | `GET /api/settings/{i}` | the view |
  | `POST /api/settings/{i}/preview` | the diff, or the refusals |
  | `POST /api/settings/{i}/apply` | `{changes, hashes, confirm}` → write + restart the instance's services + audit |
  | `POST /api/secrets/{i}` | `{key, value?, clear?, confirm}` |
  | `GET /api/history/{i}` | the history list |
  | `POST /api/history/{i}/{ts}/rollback` | `{confirm}` |
  | `GET` / `POST /api/sections/{i}/{schedule\|models}` | preview / apply |
  | `POST /api/promote` | `{keys, confirm}` |
  | `GET /api/audit` | the audit log |
  | `GET /api/alerts` | the alert state, on / off |

  The v2.10 service actions are audited and lock-guarded too.
- **The UI:**
  - a **Settings** tab: the instance switcher (prod red), a form per group (inputs typed by the schema; enums as
    selects; the default and the description shown), "Preview" → the diff, then "Apply" (prod asks for `prod`);
  - **Secrets:** `set` / `unset` + `•••last4`, set / rotate / clear;
  - **History:** a list with "Roll back";
  - **Schedule & Models:** YAML text areas, preview → apply;
  - **Promote:** dev keys that differ from prod → diff → apply;
  - **Audit:** the newest first.

  The result of every action stays on the page (the v2.10 review #1 rule).
- **Contracts** (extending v2.10's):
  - the token on every route;
  - no write into a **data root**;
  - no secret in any API response **or the audit log**;
  - an invalid value never reaches a file;
  - a prod write without the confirmation never reaches a file.

**Dependencies:** LUMI-259, LUMI-260, LUMI-261, LUMI-262

**Expected result:**
From the panel a dev setting is changed with its restart done and rolled back with one click; a prod change shows
its diff and applies after the confirmation; secrets are set but never shown.

**Acceptance criteria:**
- [ ] **Integration** (fixture instances, a fake runner, a fake agent lock):
  - edit → preview → apply → the three services restarted → the value in the file;
  - rollback restores it;
  - prod without the confirmation is a 409 with nothing written;
  - a promote;
  - a section edit;
  - a secret rotated, never echoed;
  - every action in the audit log;
  - an action while the lock is held is a 409, audited.
- [ ] **Contract:** the route enumeration covers the new routes. Every route is called with known secret values in
      play; none appears in a response or in `audit.jsonl`. An invalid value and an unconfirmed prod write leave the
      files byte-identical. `data/` is fingerprinted unchanged.
- [ ] ARCHITECTURE §Deployment, the v2.10 bullet extended: the panel now writes an instance's `settings.yaml` /
      `secrets.yaml` / `config-history/` (never `data/`); the audit; the alerts; the lock guard.
- [ ] **Gates:** `uv run ruff check .` + `uv run pytest -q` green.
- [ ] **Manual (owner):** the browser UI (LUMI-265).
