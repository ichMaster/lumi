# v4.4 — Issues

Issues for phase **v4.4 — State, schedule and a turn's tools** (version **v4 — The window: her files, pictures,
journal and thoughts in Lili.app**), derived from the Tasks and DoD in [ROADMAP.md](../../ROADMAP.md) §v4.4, the
concept [DESKTOP_VIEWS.md](../../features/DESKTOP_VIEWS.md), the design handoff
[design/v4/handoff/](../../../design/v4/handoff/README.md) §9–§11 and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md). This file covers one phase; ids continue from the previous phase
(LUMI-313 → **LUMI-314…319**).

v4.4 lets the owner see three more things from the window:
- **her day** — the mood reading in full, the three biorhythms with their cycles, the closeness level;
- **her timetable** — every directive of the schedule with its rule, its last firing and its next due time;
- **the tools she called** in the last reply, in the details panel.

It builds on v4.1–v4.3 (the owner routes, the view row and the right panels, the strings and tokens of the handoff),
v0.6/v0.8/v0.10 (mood, biorhythms, closeness), v0.42 (the scheduler, run by the v2.5 brain host) and the v0.19 tool
trace. It leaves every action (v4.5) to the next phase and the day's plan to v5.7.

**Reconciled against the code and the live setup (2026-11-18):**
- **The mood keeps its full reading but no time.** `core/mood.py` `MoodState{date, resolution, reading, theme}`; the
  reading is the raw model text (the body, then the «РЕЗОЛЮЦІЯ:» line and the resolution, then «ТЕМА:»). It is
  restored from the mood log after a restart, and the log's header (`===== YYYY-MM-DD =====`) holds no time, so a
  `made_at` would be true only for a fresh call. DESKTOP_VIEWS allows `made_at: null`; v4.4 keeps it `null` and
  adds no field. The view's header shows the day only (`state.made_at` stays unused).
- **The State shows the body of the reading, not the resolution twice.** A new `mood_body(reading)` returns the text
  before the resolution line with the theme line removed (`strip_theme`, the `split_resolution` marker rule).
- **The mood may be yesterday's.** `Core.mood` returns `_mood.resolution` whatever its `date`; the mood is computed
  at startup and lazily on the first turn of a new day. `/v1/today` returns `mood: null` unless `_mood.date` is
  today, so the window shows «Today's state isn't ready yet» instead of yesterday's reading. No model call: the route
  never computes it.
- **Biorhythms are computed, so they are always available.** `core/biorhythm.py` keeps `Cycle{name, value, label}`
  (labels high / low / rising / falling / critical) and `PERIODS` (23 / 28 / 33). The trend and the day in the cycle
  are new, from the birth date in the natal file (`parse_birth_date`) and the clock: `biorhythm_detail(birth, today)`.
  `mood.biorhythms: true` on prod and dev. The design's own level (≥ .33 high, ≤ −.33 low, else mid) is the
  window's; the core's label rides along.
- **The theme's name and scene are already in the window** (`strings.en.json` `themes[slug]`, v2.12.2), so
  `/v1/today` carries only the slug.
- **The scheduler lives in the brain host.** `server/brain.py` builds `core/scheduler.py` `Scheduler` from
  `load_schedule(cfg.schedule_path, cfg.schedule_overrides)` and `cfg.schedule_state_path`, with
  `day_cap=cfg.sched_day_cap` and `quiet_hours=cfg.thoughts_quiet_hours`. The Scheduler:
  - keeps only enabled entries (`self._entries`), so the view needs the whole list to show the disabled ones;
  - keeps `schedule.state` in memory (`_state`, written on each fire) and today's counts in memory (`_day_count`,
    `_per_dir`, reset at local midnight and on restart);
  - quiet hours veto every trigger **except** `at` (`_quiet_vetoed`) — the design's footnote says so;
  - `per_dir_cap` defaults to the day cap.

  `core/schedule.py` `due(now, last_fired, trigger, last_input=)` is pure; `idle` is anchored on the server's
  `service.last_input`. No next-due computation exists yet. On prod and dev: `scheduler.enabled: true`,
  `day_cap: 2400`, `thoughts.quiet_hours: 1-7`, no `schedule:` overrides, 11 / 10 entries in `schedule.state`.
- **`create_app` doesn't know the brain host.** `server/__main__.py` builds `BrainHost(service, cfg)` after
  `create_app` and keeps it in `app.state.brain`. The schedule route reads the brain host's scheduler at request time;
  with the scheduler off there is nothing to show (`features.schedule` false, 404).
- **The tool trace exists.** `Core.last_tool_calls: list[(name, input, shown)]` is reset each turn and filled only
  while `files.trace` is on (`_file_tool_trace`); an image result is already a short marker (`_tool_trace_repr`).
  The TUI prints it (`tui/app.py` `_show_tool_trace`); the TUI client keeps an empty list. `files.trace: true` on
  prod and dev. Inputs can be large (a `create_file` body), so the outcome carries a bounded copy.
- **The details panel** is `renderDetails` in `desktop/ui/app.js`: the cells grid, then the controls (portrait, inner
  voice, text size). The tool list goes between them (handoff §11).
- **The design strings are not merged yet:** the `state.*` (22 new), `schedule.*` (21) and `tools.*` (2) keys of
  `strings.en.add.json`. `state.try_again` and `state.nothing` already exist from v2.12.

### LUMI-314 — Her day in core: the reading's body, the biorhythms' trend and day, `Core.today_view`

**Description:**
The structured form of `/mood`, `/biorhythm` and `/closeness` for the window: `core/mood.py`, `core/biorhythm.py`,
`core/agent.py`.

**What needs to be done:**
- `core/mood.py`: `mood_body(reading) -> str` — the reading before its «резолюція» line, with the theme line removed;
  the whole stripped reading when there is no marker (the resolution then comes from the fallback rule).
- `core/biorhythm.py`: `biorhythm_detail(birth, today) -> list[dict]` — for physical, emotional and intellectual:
  `{name, value, label, trend: rising|falling, period, day}`; `trend` from tomorrow's value, `day` the place in the
  cycle (`(today − birth).days % period`). The values and labels equal `biorhythms(birth, today)`.
- `core/agent.py` `Core.today_view() -> dict`:
  - `date` (today, from the clock);
  - `mood`: `{resolution, reading: mood_body(...), theme, made_at: None}` when today's mood is computed, else `None`;
  - `biorhythms`: `biorhythm_detail` when `mood.biorhythms` is on and the natal file has a birth date, else `[]`;
  - `closeness`: `{level, name}` from `closeness_status()`;
  - `plan`: `None` (v5.7).

  Read-only: no model call, never computes the mood, never writes.

**Dependencies:** None

**Expected result:**
The core answers "what is her day" with the same mood, biorhythms and closeness the commands show, without a model call.

**Acceptance criteria:**
- [ ] `mood_body` drops the resolution and the theme line, keeps the body; without a marker it keeps the reading.
- [ ] `biorhythm_detail` matches `biorhythms()` value for value and label for label; the trend and the day are right on
  a known birth date (a rising and a falling cycle, day 0).
- [ ] `today_view` gives today's mood, `None` for yesterday's or none, `[]` biorhythms when off or without a birth
  date, the closeness by name, `plan: None`; no model call (the mock records none).
- [ ] **Tests:** `tests/unit/test_today_view.py`, with an injected clock and a mock model.
- [ ] **Gates:** `uv run ruff check .`, `uv run pytest -q`.

### LUMI-315 — The schedule in core: the next due time, the scheduler's view of every entry

**Description:**
When each directive fires next, computed by the scheduler's own rules: `core/schedule.py` and `core/scheduler.py`.

**What needs to be done:**
- `core/schedule.py`:
  - `next_due(now, last_fired, trigger, *, last_input=None, quiet_hours=None, horizon_days=8) -> datetime | None` —
    the first minute from `now` on where `due(...)` holds and the quiet hours don't veto it (`at` beats quiet hours,
    as `_quiet_vetoed` does). `every`, `idle` and `between` start from their earliest possible time
    (`last_fired + interval`, `last_input + interval`) and step by the minute. `None` past the horizon;
  - `trigger_view(trigger) -> dict` — the structured trigger: `{kind, interval_s, at, days, window, cron}`
    (`at` as `"HH:MM"`, the window as two `"HH:MM"`, the days as weekday numbers).
- `core/scheduler.py`:
  - the `Scheduler` keeps the whole list (enabled or not) beside the enabled one it fires from;
  - `Scheduler.view(now, *, last_input) -> dict`:
    - `entries:[{name, directive, seeds, show, enabled, trigger, last_fired, next_due, if_silent}]` in the
      schedule's order (`if_silent` for `idle`; `next_due` `None` for a disabled entry);
    - a capped day (the day cap, or the directive's own cap) moves an entry's next due past local midnight;
    - `quiet_hours`, `day_cap`, `fired_today` (the in-memory count) and `now`.
  - Read-only: it changes no state, stamps nothing, writes no file. The dict copies are taken whole.

**Dependencies:** None

**Expected result:**
The core says, for every directive, when it last fired and when it is next due, by the same rules that fire it.

**Acceptance criteria:**
- [ ] `next_due` for each kind: `every` (never fired → now; else last + interval); `idle` (last input + interval,
  later than the last fire); `at` (today's minute or tomorrow's; the weekdays); `between` (inside and outside the
  window, wrapping midnight); `cron`.
- [ ] Quiet hours push every kind but `at` to their end; `at` inside quiet hours keeps its minute.
- [ ] A capped day moves the next due past midnight; a disabled entry has none; each `next_due` is a minute where
  `due()` holds.
- [ ] `Scheduler.view` lists the disabled entries too, matches `schedule.state` for `last_fired`, and leaves the state
  file and the counts unchanged.
- [ ] **Tests:** `tests/unit/test_schedule_next_due.py` (pure, an injected `now`).
- [ ] **Gates:** `uv run ruff check .`, `uv run pytest -q`.
