### LUMI-234 — The bounded turn: one deadline across the stream, the fallback and the retries

**Description:**
v2.6 review #4: behind a slow Gemini (2026-10-17/19) a streamed turn waits 120 s, falls back to a blocking call with
120 s and two retries — up to ~8 minutes, while the client's next line (`/model` included) waits for the turn. Give a
turn **one deadline** (≈180 s, a constant) across everything it does in the model client. Touches `core/llm.py`
(`GeminiClient`: `_post`, `_sse_lines`, `_run`, `reply_structured_stream`, the tool loops; `_call_with_retries`),
`core/agent.py` (the readable failure line), `specification/ROADMAP.md`, `specification/ARCHITECTURE.md`.

**What needs to be done:**
- A per-turn deadline in the Gemini client, **thread-local** (thoughts and housekeeping share the client): set when a
  turn's call starts; every `urlopen` timeout becomes `min(120, remaining)`; no retry and no stream → blocking fallback
  once the remaining time is too short; past the deadline → `LLMError("the model didn't answer in time")`.
- `_call_with_retries` learns an optional deadline (never sleeps or retries past it) — the other clients unchanged.
- The turn's failure surfaces as the usual readable "model unavailable" line (TUI, server 502) — never a hang.
- **Reconcile the roadmap:** v2.7's "a slash command is never queued behind a running turn" doesn't hold — the server
  serves one request at a time by design (v2.2) — so the guarantee is that **a command waits at most the deadline**.
  ROADMAP §v2.7 and ARCHITECTURE §Deployment say so.

**Dependencies:** None

**Expected result:**
A turn behind a hanging model ends within ~3 minutes with a readable line, and whatever waited behind it runs right
after.

**Acceptance criteria:**
- [ ] A hanging stream + a hanging blocking fallback + retries end by the deadline with an `LLMError`, not ~8 min.
- [ ] A fast model is unaffected (the same calls, the same timeouts' upper bound).
- [ ] A background call (a thought) on another thread keeps its own budget.
- [ ] **Tests:** a fake transport that hangs (an injected monotonic clock — no real waiting) → the deadline fires
      across stream → fallback → retries; the retry helper stops at the deadline; the thread-local isolation; the
      server answers 502 with the readable line. No paid API.
- [ ] **Gates:** `ruff`, `pytest`.

### LUMI-235 — The deploy agent: `main` → dev, a confirmed tag → prod, smoke + rollback

**Description:**
A pull-based agent on the box (owner, 2026-10-20): a systemd user timer runs it every few minutes; it looks at GitHub
itself (nothing reaches into the box, no deploy secret anywhere). Touches `scripts/deploy_agent.py` (new, stdlib-only),
`deploy/systemd/lumi-deploy.service` + `lumi-deploy.timer` (new), tests.

**What needs to be done:**
- **Pure decisions** (unit-tested over fixtures): `dev_action(state, main_sha, ci)` — deploy a new **green** commit of
  `main` (CI's check runs all successful), never a commit already marked bad; `prod_action(state, tags, confirmed)` —
  deploy the newest release tag **only when the owner confirmed exactly that tag**; `smoke_verdict(...)` — health ok,
  the state readable, the expected version (prod: the tag), the services still active a minute later, no new `ERROR`
  in `lumi.log` since the restart.
- **The runner** — `tick`: `git fetch` in the instance's checkout → `checkout --detach <sha|tag>` → `uv sync --frozen
  --all-extras` → `systemctl --user restart lumi-server@<instance>` → the smoke → on failure **roll back** to the
  previous sha/tag (and mark the bad one) and log why. The CI status from the public GitHub API (unauthenticated, within
  its rate limit). State + log under `~/lumi/deploy/` (`state.json`, `deploy.log`).
- **Commands:** `confirm <tag>` (the owner's approval for prod), `status`, `rollback <dev|prod>` (one command),
  `install` (copies the agent to `~/lumi/deploy/` — so it never runs from a checkout it is updating — and installs +
  enables the timer).
- **Never touches data or settings:** no write under a data root, no `.env` change — the agent moves code only.

**Dependencies:** LUMI-233

**Expected result:**
A green push to `main` reaches the box's dev by itself; a release reaches prod only after `confirm`; a failed smoke
rolls back; rollback is one command.

**Acceptance criteria:**
- [ ] `tick` deploys a new green `main` commit to dev and keeps it on a green smoke; a red CI is never deployed.
- [ ] A new tag waits for `confirm <tag>`; a confirmed tag deploys to prod; a failed smoke rolls back to the previous
      tag; `rollback prod` restores the previous tag in one command.
- [ ] The agent runs from its own copy (`install`), not from an instance checkout.
- [ ] **Tests:** the decisions and the smoke verdict over fixtures; the runner's command sequence (deploy, smoke fail
      → rollback) over a fake command runner and a fake GitHub; `confirm`/`status`/`rollback` over a temp state dir.
      No network, no systemctl, no paid API.
- [ ] **Contract:** the deploy path writes no data root and no settings file — a test runs a full deploy + rollback
      over fixture instance dirs and asserts their `data/` and `.env` are byte-identical.
- [ ] **Gates:** `ruff`, `pytest`.
