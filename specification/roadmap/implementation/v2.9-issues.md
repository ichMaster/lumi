# v2.9 — Issues

Issues for phase **v2.9 — Settings as files: `.env` → YAML, one schema** (version **v2 — Client/server split: her
brain on the server, the TUI a thin client**), derived from the Tasks and DoD in [ROADMAP.md](../../ROADMAP.md)
§v2.9, the design in [ADMIN_PANEL.md](../../features/ADMIN_PANEL.md) §v2.9 and the contracts in
[ARCHITECTURE.md](../../ARCHITECTURE.md). This file covers one phase; ids continue from the previous phase
(LUMI-243 → **LUMI-244…251**).

Every setting of an instance moves from its ~28 KB `.env` (155 keys set on each box instance on 2026-11-10; 213
names read by `core/config.py`) into `settings.yaml` + `secrets.yaml` (`0600`), described by **one typed schema**
that the loader, the example files, the migration, `lumi-cli` and (later) the admin panel all read. The authored
`core/models.toml` / `core/schedule.toml` become YAML. Both box instances end up running from the two files with no
`.env`. The admin panel itself (watch v2.10, configure v2.11) is not in this phase.

## v2.9 — Settings as files

### LUMI-244 — The settings schema + the YAML loader (default < `.env` < YAML < env), every `LUMI_*` consumer through it

**Description:**
Today `core/config.py` `load_config()` calls `load_dotenv()` (which copies `.env` into `os.environ`) and then reads
about 213 names with `os.getenv`, parsing and defaulting each inline. A few modules read the environment directly:
`telegram/__init__.py` (`LUMI_LOG_LEVEL`), `core/weblookup.py` and `core/imagegen.py` (the `GEMINI_API_KEY` /
`GOOGLE_API_KEY` fallback), and `core/envguard.py` (`LUMI_ALLOW_DIRTY_PROD`). This issue adds **one typed schema**
of every setting and a loader that layers the sources, and routes every consumer through it. The existing parsing
(and so every existing config test) stays as it is: the loader produces the merged name → raw-value mapping, and
`load_config` reads that mapping instead of `os.environ`. Touches `core/settings.py` (new), `core/config.py`,
`core/envguard.py`, `core/weblookup.py`, `core/imagegen.py`, `telegram/__init__.py`, `pyproject.toml` + `uv.lock`
(`pyyaml>=6` as a direct dependency — today it is only transitive), `tests/conftest.py`, tests.

**What needs to be done:**
- **The schema** (`core/settings.py`): one entry per setting with its `key` (the YAML name inside its group, e.g.
  `memory.window`), `alias` (the `LUMI_*` / `*_API_KEY` env name), `type` (bool / int / float / str / path / enum /
  list / duration / hours / probability), `default`, `group` (model, instance, server, memory, mood, closeness,
  recall, thoughts, scheduler, tools, image, telegram, voice, dictation, viewer, paths, providers, …), a one-line
  `description`, `secret`, `restart` (needs a restart, or applies live; every setting is `restart=True` until a
  later phase proves one live), and the allowed `choices` / `min` / `max`. Every name `load_config` reads appears
  exactly once.
- **Not settings:** the image-baked process facts `LUMI_CONTAINER` and `LUMI_BUILD`, the compose-only parameters
  (`LUMI_IMAGE_TAG`, `LUMI_INSTANCE`, `LUMI_INSTANCE_DIR`, `LUMI_PUBLISH_HOST`, `LUMI_TZ`) and `LUMI_SETTINGS_DIR`
  itself stay environment-only. A named exemption list in the schema module, pinned by a test, holds them.
- **The files:** `settings.yaml` (every non-secret setting, nested by group) and `secrets.yaml` (the `secret=True`
  ones: the provider API keys, the Telegram bot token, `LUMI_SERVER_TOKEN`, `LUMI_NEWS_API_KEY`, …). They are found
  in `LUMI_SETTINGS_DIR` when set (the containers, LUMI-249), else at the repo root (the dev tree), else in the repo's
  parent directory (the v2.6 units' `~/lumi/<instance>/app` layout, so the way back keeps working). A secret found in
  `settings.yaml`, or a non-secret in `secrets.yaml`, is refused with a readable message. A `secrets.yaml` readable
  by group or others gets a warning naming `chmod 600`.
- **Precedence, weakest → strongest:** the schema default < `.env` (**deprecated**, read with `dotenv_values` into
  its own layer, no longer copied into `os.environ`; a start-up warning names `scripts/env_to_settings.py`) <
  `settings.yaml` / `secrets.yaml` < the process environment (a `LUMI_*` variable still wins: tests, compose's
  `environment:`, an emergency hatch). With no YAML and no `.env`, the result is byte-identical to today.
- **Validation:** each value in the YAML files is checked against its type, choices and range. A wrong one stops the
  process with one readable message naming the file, the key, the value and the allowed values (for a `secret` key
  the value is shown as `(hidden)`). An unknown key is a warning, never a refusal, so a rollback to an older image
  still starts on a newer file. Environment values keep today's lenient parsing (unknown → the default).
- `load_config(*, load_env=True, settings_dir=None)`: `load_env=False` skips the file layers (`.env` and YAML), so
  the 119 hermetic tests stay hermetic. An explicit `settings_dir` reads that folder even then (for the loader's own
  tests). `tests/conftest.py` points `LUMI_SETTINGS_DIR` at an empty temp folder, so a developer's real
  `settings.yaml` at the repo root never leaks into a test.
- Route the direct readers through the loader: `LUMI_LOG_LEVEL` (becomes a schema setting), the Gemini key fallback
  (`GOOGLE_API_KEY` becomes a deprecated alias of `GEMINI_API_KEY`) and `LUMI_ALLOW_DIRTY_PROD` (the env guard asks
  the loader; the hatch still works from the environment). The bind guard already reads `cfg.server_host`; a test
  pins that a host set only in `settings.yaml` is the one it checks.
- The refusal and hint messages that name `.env` (`core/llm.py`, `server/__main__.py`, `tui/__main__.py`,
  `cli/main.py`) name `secrets.yaml` / `settings.yaml` instead.

**Dependencies:** None

**Expected result:**
Any process started with a `settings.yaml` + `secrets.yaml` (and no `.env`) gets the same `Config` it would get from
the equivalent `.env`, and an invalid value in a file stops it with a message that names the key and the allowed
values.

**Acceptance criteria:**
- [ ] The schema covers every name `load_config` reads; the exemption list covers the rest; a test greps
      `core/config.py` and fails on a name in neither.
- [ ] Precedence default < `.env` < YAML < env is proven per layer on one key of each type, plus the "nothing set →
      byte-identical `Config()`" case.
- [ ] A wrong value (an enum outside its choices, an int out of range, a non-bool) refuses with the file, key, value
      and allowed values in the message; for a secret the value never appears (asserted on the message text).
- [ ] A secret in `settings.yaml` is refused; an unknown key only warns.
- [ ] `.env` present → one deprecation warning; `.env` and YAML both set a key → the YAML value wins.
- [ ] **Tests:** `tests/unit/test_settings_loader.py` — fixture folders under `tmp_path`, no network, no paid call;
      the existing config / env-guard / server-main / CLI tests pass unchanged through the new loader.
- [ ] **Contract:** the configuration contract (ARCHITECTURE §Configuration and secrets: where settings and secrets
      live, the precedence) is updated in this issue, and `test_settings_loader.py` pins the precedence.
- [ ] **Gates:** `uv run ruff check .` + `uv run pytest -q` green.

### LUMI-245 — `settings.example.yaml` + `secrets.example.yaml` generated from the schema; `.env.example` retired; the schema contract test

**Description:**
The example files are generated from the schema, so they can't drift: every setting appears with its description,
its default and its allowed values as comments, grouped like the real files. They replace `.env.example`. Touches
`scripts/settings_examples.py` (new: writes both files; `--check` exits non-zero when they are stale),
`settings.example.yaml` + `secrets.example.yaml` (new, generated), `.env.example` (removed), `.gitignore` +
`.dockerignore` (`settings.yaml`, `secrets.yaml`), `scripts/prod_update.py` (its "new knobs" report reads the schema
instead of `.env.example`), tests.

**What needs to be done:**
- The generator: groups in schema order, each setting as `key: <default>` with `# description · allowed: … ·
  restart` above it. Optional settings with no default are written commented out. `secrets.example.yaml` lists every
  secret key with an empty value and a pointer to where the key comes from.
- `.gitignore` ignores `settings.yaml` and `secrets.yaml` (both kept at the dev repo root). `.dockerignore` keeps
  them **out of every image**, so a local `docker build` from the dev tree can never bake a key in.
- Remove `.env.example`. `scripts/prod_update.py` (the v2.6 units' way back) reports the schema settings that the
  instance's files don't set, instead of diffing `.env.example`.
- The **schema contract test**: (1) the committed example files equal the generator's output; (2) every schema
  setting has a non-empty description and a group; (3) every key in either example file is known to the schema;
  (4) no `secret=True` key appears in `settings.example.yaml`, and no non-secret in `secrets.example.yaml`; (5) every
  schema default equals what `load_config` yields with nothing set, so the schema and the loader can't disagree
  about a default; (6) every `Config` field is fed by a schema setting or is a documented derived field
  (`app_version`, `schedule_state_path`, `closeness_tuning` from its own keys, …).

**Dependencies:** LUMI-244

**Expected result:**
`settings.example.yaml` and `secrets.example.yaml` document every setting, are regenerated by one command, and a
contract test fails the build the moment the schema, the examples and the loader disagree.

**Acceptance criteria:**
- [ ] `uv run python scripts/settings_examples.py` regenerates both files; `--check` passes on a fresh tree and fails
      after a schema edit without a regeneration.
- [ ] `.env.example` is gone; `settings.yaml` / `secrets.yaml` are in `.gitignore` and `.dockerignore`
      (`tests/unit/test_dockerfile.py` asserts the `.dockerignore` lines).
- [ ] `scripts/prod_update.py` reports unset settings from the schema; its existing tests are adapted.
- [ ] **Tests:** `tests/contract/test_settings_schema.py` (the six checks above), no network.
- [ ] **Contract:** schema ↔ example files ↔ loader, pinned by `test_settings_schema.py`; ARCHITECTURE
      §Configuration and secrets names the example files.
- [ ] **Gates:** `uv run ruff check .` + `uv run pytest -q` green.

### LUMI-246 — `core/models.yaml` + `core/schedule.yaml` (the TOMLs converted), per-instance overrides in `settings.yaml`

**Description:**
The two authored TOMLs become YAML: `core/models.toml` (the `/model` aliases and the per-family model profiles,
loaded by `core/config.py` `_load_models_file`) and `core/schedule.toml` (the `[[schedule]]` rows, loaded by
`core/schedule.py` `parse_schedule` / `load_schedule`). An instance can also override one model profile, or one
schedule row, in its own `settings.yaml` without editing the authored files. Touches `core/models.yaml` +
`core/schedule.yaml` (new, converted with their comments kept), `core/models.toml` + `core/schedule.toml`
(removed), `core/config.py`, `core/schedule.py`, `core/settings.py` (the `models:` / `schedule:` sections), the
default paths (`DEFAULT_MODELS_PATH`, `DEFAULT_SCHEDULE_PATH`), tests.

**What needs to be done:**
- Convert both files to YAML with the same content and comments. The loaders read YAML; a path that still ends in
  `.toml` (an old `LUMI_MODELS_FILE` / `LUMI_SCHEDULE_PATH`) still parses, with a deprecation warning, for this one
  release.
- **The schedule ids stay the same.** `ScheduleEntry.id` is content-stable and keys `schedule.state`, so every row
  must parse to an equal entry with an equal id from YAML as from the TOML. A test compares the two files row by row
  before the TOML is deleted (kept as a fixture).
- **Model overrides:** `settings.yaml` `models.aliases` / `models.profiles.<name>` merge over `core/models.yaml` by
  name. The merge order is code defaults < `core/models.yaml` < `settings.yaml` < the `LUMI_MODEL_*` / profile
  variables (today's env vars still win).
- **Schedule overrides:** a schedule row may carry an optional `name`. A `settings.yaml` `schedule:` row with the
  same `name` replaces the authored row (for example `enabled: false` turns one off on prod only), and a row with a
  new name is added. Unnamed rows behave exactly as today.
- Malformed rows and profiles are still skipped, never fatal (today's rule). A wrong type inside a known field is
  reported by the LUMI-244 validator.

**Dependencies:** LUMI-244

**Expected result:**
Her model profiles and thought schedule load from YAML with identical results and identical schedule-state keys,
and one instance can change a profile or a schedule row in its own `settings.yaml`.

**Acceptance criteria:**
- [ ] `core/models.yaml` and `core/schedule.yaml` load to the same aliases, profiles and entries (equal ids) as the
      TOMLs did (fixture comparison).
- [ ] A `settings.yaml` profile override and a named schedule-row override (replace + add) take effect; unnamed rows
      are untouched.
- [ ] A `.toml` path still loads, with one warning.
- [ ] **Tests:** extend `tests/unit/test_schedule.py` + `tests/unit/test_model_profiles.py`; plain data, injected clock, no network.
- [ ] **Gates:** `uv run ruff check .` + `uv run pytest -q` green.

### LUMI-247 — `scripts/env_to_settings.py` — `.env` → the two files, dry-run diff first, unknown keys reported

**Description:**
A one-time migration for each instance (and the dev tree): read a `.env`, sort every set key into `settings.yaml`
or `secrets.yaml` by the schema, report what it can't place, and show the result before writing anything. Touches
`scripts/env_to_settings.py` (new), tests.

**What needs to be done:**
- `env_to_settings.py <.env path> [--out <dir>] [--apply]`. Without `--apply`, a dry run prints the planned
  `settings.yaml` (complete) and the list of secret **keys** going into `secrets.yaml` (values never printed), plus
  the unknown keys. With `--apply` it writes both files (`secrets.yaml` created `0600`), then renames the `.env` to
  `.env.migrated`.
- Only keys that are **set** (uncommented) move. Each value is converted to its schema type (`on` → `true`, `5h` →
  the duration, `23-7` → the hours range, comma lists → lists) and validated. A value that fails validation stops
  the migration with the key and the allowed values, and nothing is written.
- Unknown keys (not in the schema or the exemption list) are listed and not written. The run still succeeds, and the
  keys stay readable in `.env.migrated`.
- It refuses to overwrite an existing `settings.yaml` / `secrets.yaml` (no `--force`: remove them by hand first).
- Round-trip check before writing: `load_config` over the new files equals `load_config` over the old `.env` for
  every schema setting. A difference stops the run with the key names.
- It runs on the box from the image, with the same Python and schema that will read the files:
  `docker run --rm -v ~/lumi/<i>:/instance ghcr.io/ichmaster/lumi:<tag> python scripts/env_to_settings.py /instance/.env --out /instance`.

**Dependencies:** LUMI-244

**Expected result:**
A fixture `.env` turns into a valid `settings.yaml` + a `0600` `secrets.yaml` that load to the same `Config`, with
unknown keys reported and the old file kept as `.env.migrated`.

**Acceptance criteria:**
- [ ] Dry run writes nothing and prints no secret value (asserted on the captured output).
- [ ] `--apply` writes both files (`secrets.yaml` mode `0600`), renames `.env` → `.env.migrated`, and the
      round-trip `Config` is equal.
- [ ] Unknown keys are reported; an invalid value aborts with nothing written; an existing target is refused.
- [ ] **Tests:** `tests/unit/test_env_to_settings.py` — a fixture `.env` covering every setting type, a secret, an
      unknown key and a commented key; `tmp_path` only.
- [ ] **Gates:** `uv run ruff check .` + `uv run pytest -q` green.

### LUMI-248 — `lumi-cli config get | set | validate`, secrets masked on every output

**Description:**
`lumi-cli config` today prints the effective config, masking fields whose name contains key/token/secret/password
(`cli/main.py` `mask_config`). It grows three subcommands that work on the instance's files directly (no server
needed), and masking follows the schema's `secret` flag. Touches `cli/main.py`, `core/settings.py` (a small write
API that keeps the file's comments and order), tests.

**What needs to be done:**
- `config` with no subcommand (or `config show`): the effective config as today, masked by the schema's `secret` flag.
- `config get <key>`: the effective value and where it came from (default / `.env` / `settings.yaml` /
  `secrets.yaml` / env). A secret shows `•••set•••` or `(unset)`, never the value.
- `config set <key> <value>`: validate against the schema. A wrong value is refused, naming the key and the allowed
  values or range, and nothing is written. A valid value is written to `settings.yaml`, or to `secrets.yaml` for a
  secret (kept `0600`). It prints `restart needed` when the setting's `restart` flag is set, and notes when a process
  environment variable would still override the file. The value of a secret set is never echoed.
- `config validate`: check both files completely (types, ranges, misplaced secrets, unknown keys as warnings). Exit
  0 when clean, non-zero with one line per problem.
- `--dir <folder>` on every config subcommand (default: the loader's discovery), so the owner can run it on the box
  through the image against `~/lumi/<instance>`.
- **No secret in any output or log:** a test runs every subcommand over a fixture with known secret values and
  asserts that none of them appears in stdout, stderr or the captured log records.

**Dependencies:** LUMI-244

**Expected result:**
A setting changed with `lumi-cli config set` is validated (a wrong value refused with the allowed ones) and lands
in the right file, and no secret value ever reaches the terminal or a log.

**Acceptance criteria:**
- [ ] `get` / `set` / `validate` / `show` behave as above over fixture folders.
- [ ] A wrong value is refused with the allowed values and the file is unchanged byte for byte.
- [ ] `set` keeps the other lines and comments of the file; a secret goes to `secrets.yaml` with mode `0600`.
- [ ] The no-secret-anywhere test passes for every subcommand.
- [ ] **Tests:** extend `tests/unit/test_cli.py`; no server, no network.
- [ ] **Gates:** `uv run ruff check .` + `uv run pytest -q` green.

### LUMI-249 — The containers read the YAML: compose mounts the two files, the deploy agent's smoke reads them

**Description:**
Each box instance today gets its settings through compose `env_file: ~/lumi/<i>/.env` (required). After the
migration the containers must read `~/lumi/<i>/settings.yaml` + `secrets.yaml`, and the deploy agent's smoke (which
reads `LUMI_SERVER_HOST` / `_PORT` / `_TOKEN` from the `.env`, `scripts/deploy_agent.py` `_env` / `_smoke`) must find
them there. Rolling back to a pre-v2.9 image must keep working. Touches `deploy/compose/compose.yaml`,
`scripts/deploy_agent.py`, `Dockerfile` (comment only), `tests/contract/test_compose_contract.py`, `tests/unit/test_deploy_agent.py`.

**What needs to be done:**
- compose: mount `${LUMI_INSTANCE_DIR}/settings.yaml` and `secrets.yaml` read-only into `/settings/`, and set
  `LUMI_SETTINGS_DIR=/settings`. Use the long bind syntax with `create_host_path: false`, so a missing file fails
  `up` (the agent then rolls back) instead of Docker silently creating an empty directory in its place. The
  `environment:` block (LUMI_HOME, the host/port inside the container, TZ) still wins over the files.
- Keep `env_file: .env` with `required: false`, so the way back below v2.9 works: a pre-v2.9 image only reads the
  environment, so rolling back means `mv .env.migrated .env` (documented in LUMI-250). With no `.env` present it
  adds nothing.
- The agent's `_env` reads `settings.yaml` + `secrets.yaml` (the agent runs on the box's system Python, outside the
  image, so it uses a small reader for the three keys it needs), falling back to `.env`, then `.env.migrated`. The
  token is still only sent to the instance and never logged.
- The agent's `install` copies the new compose file. The agent is re-installed from `main` after the merge
  (LUMI-251), as in v2.8.

**Dependencies:** LUMI-244, LUMI-247

**Expected result:**
An instance with `settings.yaml` + `secrets.yaml` and no `.env` comes up under compose with its own settings, and
the deploy agent's smoke still reaches it with the right host, port and token.

**Acceptance criteria:**
- [ ] The compose contract test asserts the two read-only mounts, `create_host_path: false`, `LUMI_SETTINGS_DIR`, the
      optional `env_file`, and that no secret lives in the compose files.
- [ ] The agent's smoke reads host/port/token from the YAML files, then `.env`, then `.env.migrated`; the token never
      appears in `deploy.log` (asserted).
- [ ] **Tests:** `tests/unit/test_deploy_agent.py` (fake runner, fixture instance folders); no Docker, no network.
- [ ] **Gates:** `uv run ruff check .` + `uv run pytest -q` green; `scripts/compose_check.sh` (`docker compose
      config`) passes where Docker is available.
