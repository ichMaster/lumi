## Detailed Results

### LUMI-259 — the edit engine (#259)
`admin/edit.py` + `core/settings.py` helpers (`parse_mapping`, `check_texts`, `last4`, `unset_in_text`):
- an instance's `settings.yaml` + `secrets.yaml` as a schema-driven view (secrets shown only as set / `•••last4`);
- a `Plan` built as old → new texts and checked by the instance's own start check (`check_texts`), so an invalid
  value never reaches a file;
- the diff, and a per-process HMAC of each file so a stale preview is refused;
- the atomic apply (`os.replace`) with history copies (`config-history/<ts>-<file>`, 0600) and a `<ts>.json`
  manifest, the newest 200 kept;
- one-click rollback to any history entry, which itself becomes a history entry;
- write-only secrets (set / unset; the value never returned).

### LUMI-260 — sections + promote (#260)

`plan_section` (the `schedule:` / `models:` sections, verified by re-parsing) and `promotable` / `plan_promote`
(dev → prod for chosen keys; the per-instance keys — env, home, port, host, client mode — never promoted).

### LUMI-261 — audit + the lock guard (#261)
`admin/audit.py`: one 0600 JSON line per action, done or refused, `{ts, action, instance, target, changes, result}`,
secrets as `(secret)` plus a redactor over the line, rotated at 2 MB to `.1`. `admin/guard.py`: every panel action
holds the deploy agent's `agent.lock` **shared** for its duration (the v2.10 code review #4) — refused while the
agent deploys, and the agent's own `LOCK_EX | LOCK_NB` waits while the panel acts.

### LUMI-262 — alerts (#262)

machine over the health runs — one failing message, one recovery only after a failing message, a 600 s rate limit
per instance, a failed send retried; `TelegramSender` keeps the token in the URL path only and never logs it. Off
without `alerts.chat_id` + `alerts.telegram_token`, with the reason shown.

### LUMI-263 — the API + the UI (#263)
