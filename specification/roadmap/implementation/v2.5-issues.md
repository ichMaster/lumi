# v2.5 — Issues

Issues for phase **v2.5 — The brain moves: scheduler, ticks, thoughts, Telegram beside the server** (version
**v2 — Client/server split: her brain on the server, the TUI a thin client**), derived from the Tasks and DoD
in [ROADMAP.md](../../ROADMAP.md) §v2.5 and the contracts in [ARCHITECTURE.md](../../ARCHITECTURE.md). This
file covers one phase; ids continue from the previous phase (LUMI-222 → **LUMI-223…227**).

Her time moves into the server process: the v0.42 scheduler (with its startup catch-up), the fast tick, the
legacy idle think/nudge and the Telegram inbox/outbox all run in a **brain host** inside `./lumi-server`, so
she keeps living with no client attached. The TUI becomes a pure window: it shows every conversation line the
server produces (Telegram turns, spoken thoughts, other clients' turns) and, when it opens, **what happened
meanwhile**. In-process mode (`./lumi`) keeps running everything exactly as today.

**Design note (owner, 2026-10-11).** "Opening the client shows what happened meanwhile" is an **in-memory
replay in the push channel**: the server keeps the last ~50 conversation events (`message` / `thought`); a
fresh listener gets them first, then live ones; a reconnecting listener resumes after its `Last-Event-ID`
(SSE ids, scoped to the server's boot), so nothing shows twice. No store change; a server restart starts with
an empty buffer (and a new session). A history route over the store was declined: it needs per-message
source/hidden flags (a memory-record contract change).

**Reconcile notes (the real code, 2026-10-11).** `tui/scheduler.py` (`Scheduler`, `TickService`,
`graduates`) and `tui/bridge.py` (`drain_inbox_records`, `mirror_reply` / `mirror_thought` / `mirror_user` /
`mirror_photo`, `make_photo_sink`, `set_listen_flag`) are already free of Textual; the act glue
(`_sched_tick` / `_run_scheduled` / `_scheduled_text` / `_maybe_think` / `_think_tick` / `_maybe_nudge` /
`_drain_inbox`, the spoken seed «(ти щойно подумала: …)») lives in `tui/app.py`. No code registers a fast-tick
handler yet (the needs arrive in v3), so the tick moves as a seam. `Message` has no source/hidden fields — a
hidden seed is stored as a user line (hence the replay design). The v2.3 review's note holds: background work
must take the turn lock.

### LUMI-223 — Her clock and her bus, host-neutral — the scheduler/tick/bus modules out of `tui/`

**Description:**
Move the Textual-free brain modules out of the TUI package so the server can host them without importing
`tui/`: `tui/scheduler.py` → `core/scheduler.py`, `tui/bridge.py` → `state/bus.py`, plus the act glue's pure
decisions extracted from `tui/app.py`. The old modules stay as re-exports; nothing changes in-process.

**What needs to be done:**
- `core/scheduler.py`: `Scheduler`, `TickService`, `graduates` (moved as is) + the pure act decisions the TUI
  and the server will share: the text to fire for an entry (a `seeds` row picks a line, no immediate repeat),
  "loud" (`show` or an open `%name!`), the spoken self-turn seed («(ти щойно подумала: «…» — напиши йому
  перша…)»).
- `state/bus.py`: the inbox drain + the outbox mirrors + `make_photo_sink` + `set_listen_flag` (moved as is).
- `tui/scheduler.py` / `tui/bridge.py` re-export the moved names (existing imports and tests keep working);
  `tui/app.py` calls the shared decisions instead of its inline copies.

**Dependencies:** None

**Expected result:**
The brain's clock and bus are importable by any host; `./lumi` behaves byte-for-byte as before.

**Acceptance criteria:**
- [ ] The server can import the scheduler, tick and bus without importing `tui/`
- [ ] In-process behavior unchanged — the existing scheduler / tick / bridge / TUI suites pass untouched
- [ ] **Tests:** unit tests for the extracted decisions (entry text incl. a seeds row, loud, the spoken seed);
  a pin that the TUI uses them; no network, no paid API
- [ ] **Gates:** `ruff` + `pytest`

### LUMI-224 — The brain host — scheduler, fast tick, idle think/nudge running in the server

**Description:**
`server/brain.py`: a `BrainHost` that runs her time inside `./lumi-server` — the scheduler (with its startup
catch-up), the fast tick, and (when the scheduler is off) the legacy idle think/nudge — on a background thread,
with an injected clock. Every act takes the service's turn lock, so the core never runs two things at once.

**What needs to be done:**
- `BrainHost(service, cfg, clock)` with a pure `tick(now)` (tests drive it) and `start()` / `stop()` (a daemon
  thread ticking ~1 s); started in `server/__main__` after the app, stopped before the session closes.
- Scheduler: the same `LUMI_SCHEDULE_PATH` / `schedule.state` / day caps / quiet hours; `due_now` only when no
  turn holds the lock; `last_input` = the last real turn (client or Telegram) the host saw.
- An act runs `run_directive` under the lock: a loud thought → a `thought` push (origin `null`); a loud idle
  muse that graduates → a spoken self-turn (`core.reply` with the spoken seed, hidden) → `message` push
  (`source: "thought"`) + face + state; the legacy nudge → a hidden opener turn (`source: "nudge"`). Silent
  thoughts are recorded only.
- The fast tick runs `TickService` (no handlers yet — the v3 needs register theirs).
- The lock: a client request that finds **the server's own act** running **waits** for it (bounded) instead of
  `409`; two client requests still `409` (v2.2 rule). A background act waits for a client turn.
- Config: the server honors `LUMI_SCHEDULER` / `LUMI_THOUGHTS` / `LUMI_IDLE_NUDGE` (+ their tuning) from its
  own `.env`; off → nothing runs (byte-identical v2.4 server).
- Docs: ARCHITECTURE — the scheduler/tick host is "the brain's process" (the in-process TUI or the server);
  the lock rule for background acts.

**Dependencies:** LUMI-223

**Expected result:**
With `./lumi-server` running and no client attached, her scheduled and idle acts fire on time, server-side.

**Acceptance criteria:**
- [ ] The scheduler suites re-run against the host (fake clock, mock model): due entries fire once, quiet
  hours veto, day caps hold, the startup catch-up fires a missed `at:` once
- [ ] A loud thought is pushed; a graduating one becomes a spoken turn pushed as `message`; a silent one only
  lands in `/thoughts`
- [ ] A client turn during a background act waits and runs after it — never interleaved; two client requests
  still `409`
- [ ] All proactive flags off → the server behaves as v2.4 (pinned)
- [ ] **Tests:** the host driven by `tick(now)` with an injected clock + mock model; the lock interleavings
  driven explicitly; no network, no paid API
- [ ] **Contract:** the waiting rule in the API contract test + ARCHITECTURE
- [ ] **Gates:** `ruff` + `pytest`

### LUMI-225 — Telegram beside the server — inbox/outbox on the server, `message` events, the meanwhile replay

**Description:**
The brain host consumes the inbox and produces the outbox (the v0.13 file bus, now beside the server: the
Telegram daemons run on the server's data root, no TUI needed); every conversation line the server produces is
pushed as a `message` event and kept in a bounded replay buffer that new and reconnecting listeners receive.

**What needs to be done:**
- The host drains the inbox (`LUMI_BRIDGE`, ~1 s): each record → under the lock → a turn → the reply mirrored
  to the outbox (`kind="lili"` + emotion) — echo-free as before (an inbox line is never mirrored back).
- Client turns (`/v1/turn`, `/v1/turn/stream`) mirror your line (`mirror_user`) and her reply to the outbox
  when the bridge is on — the parity of in-process keyboard turns; a loud scheduled thought goes to the
  outbox under `LUMI_SCHED_SHOW_TO_OUTBOX` as in-process. The server builds the core with the photo sink
  (`send_image`) when bridge + image are on. The server is the **single outbox writer**.
- `message` events `{role: "user"|"lili", text, source: "client"|"telegram"|"thought"|"nudge", emotion?,
  intensity?, origin}` for every conversation line (client turns too — a client skips its own by origin);
  hidden seeds are never pushed.
- SSE ids `id: <boot>-<seq>` on every bus event; a replay buffer of the last ~50 `message` / `thought` events:
  a listener without `Last-Event-ID` (or from another boot) gets the buffer after the first `state`, one with
  it gets only what came after; replayed events carry `replay: true`.
- Docs: ARCHITECTURE §Contracts — `message`, ids + `Last-Event-ID` + replay; the server as the bus consumer /
  producer in server mode.

**Dependencies:** LUMI-224

**Expected result:**
A Telegram line sent while no client is open gets her answer from the server, and the conversation waits in
the replay for the next client.

**Acceptance criteria:**
- [ ] The inbox pointer advances server-side; each line runs once; replies land in the outbox; no echo
- [ ] Client turns mirror to the outbox like in-process keyboard turns; a shown scheduled thought reaches the
  outbox when `LUMI_SCHED_SHOW_TO_OUTBOX` is on
- [ ] A fresh listener receives the recent conversation; a reconnect with `Last-Event-ID` receives only the
  missed events; another boot's id → the full buffer
- [ ] **Tests:** the bus round-trip (a fake inbox → the host → the outbox + pushes); replay / resume over the
  events route; mock model; no network, no paid API
- [ ] **Contract:** the event set (`message`), ids + replay, in the API contract test + ARCHITECTURE
- [ ] **Gates:** `ruff` + `pytest`
